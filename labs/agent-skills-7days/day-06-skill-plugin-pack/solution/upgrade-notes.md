# 升级说明与版本策略：team-conventions

## 判据：什么改动要升版本

判据不是「改没改文件」，是「**用户的行为会不会因此变化**」。

| 改动                         | 要升版本吗         | 理由                                                       |
| ---------------------------- | ------------------ | ---------------------------------------------------------- |
| 改了任何一条 `description`   | **要**             | 描述是唯一的触发面，改宽了会抢别的任务，改窄了会突然不触发 |
| 改了正文的工作流步骤         | **要**             | 模型照着它做事，步骤变了产出就变了                         |
| 增删了一条「坑」             | **要**             | 坑就是行为约束，删掉一条等于放开一种错法                   |
| 改了脚本的参数或输出格式     | **要**             | 调用方要跟着改                                             |
| 新增一个 skill               | **要**（次版本号） | 触发面变大了，可能和用户已有的 skill 抢                    |
| 删掉一个 skill               | **要**（主版本号） | 对用户是能力消失，必须写迁移                               |
| 修正错别字、补注释、调整排版 | 不用               | 行为不变                                                   |
| 改 README                    | 不用               | 它不进模型的上下文                                         |

**最容易漏的是第一行。** 大家都记得改脚本要升版本，却常觉得「我就是把描述改得更准了一点」不算变更。它是这个包里最该升版本的一类改动。

## 版本号怎么走

- **主版本号**：删掉 skill、改包名、改调用名。这三件都会让用户那边直接断掉。
- **次版本号**：新增 skill、扩大某条描述的覆盖面。
- **修订号**：正文步骤与坑的调整，触发面不变。

**版本只写在包自己的清单里**，不要在市场清单里再写一份。两边优先级不同，不一致时会得到一个自己都解释不清的状态。

## 升级期的两个坑

**改包名。** 包名是命名空间，改名等于把包里所有技能的调用名一起改掉。用户那边任何写死了调用名的地方（文档、别的 skill 的正文、脚本）都会断。真要改，按主版本号发，并在说明里给出新旧调用名的对照表。

**跨包挪动 skill。** 把 `release-report` 从这个包挪到另一个包，对用户来说就是「装了 team-conventions 的人突然少了一个能力」。必须在升级说明里显式写出「装另一个包」这一步，不能指望他们自己发现。

## 怎么确认升级没升坏

把第三天那套触发测试当回归跑：改描述前后各跑一次**同一组**正负例，比的是触发率，不是感觉。这一步尤其要盯的是**新增 skill 之后老 skill 的触发率有没有掉**——触发面互相挤占是新增时最常见的回退。
