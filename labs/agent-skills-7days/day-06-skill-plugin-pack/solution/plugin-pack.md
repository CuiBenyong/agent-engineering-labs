# 插件包的目录与三份 SKILL.md

## 目录结构

```text
team-conventions/
├── .claude-plugin/
│   └── plugin.json
├── skills/
│   ├── commit-message/SKILL.md
│   ├── code-review/SKILL.md
│   └── release-report/SKILL.md
└── README.md
```

**只有 `plugin.json` 在 `.claude-plugin/` 里。** `skills/` 必须在插件根下——把它塞进 `.claude-plugin/` 是官方文档专门标出来的最常见错误，症状是包能装上但一个技能都不出现。

## 清单

```json
{
  "name": "team-conventions",
  "description": "某团队的提交、评审与发布规范，装上即生效，覆盖提交信息、代码评审意见与发布报告三件事",
  "version": "1.0.0",
  "author": { "name": "Platform Team" }
}
```

## skills/commit-message/SKILL.md

```markdown
---
name: commit-message
description: 当用户要提交代码、要写或修改一条提交信息、或问这次提交该怎么写时使用。只产出提交信息文本，不负责拆分提交，也不写 Pull Request 描述。
---

## 工作流

1. 先跑 `git diff --staged --stat` 看清这次改了什么，不要凭对话里的描述猜。
2. 按下面的格式写一条，类型只能从六个里选，多一个都不行。
3. 写完自查三条坑，任何一条不过就重写。

## 格式

    <类型>(<范围>): <一句话，祈使句，不加句号>

    <可选正文，说清为什么这么改，不复述改了什么>

类型只有六个：feat、fix、docs、refactor、test、chore。
范围用目录名，比如 payments、miniapp、content。

## 坑

- **范围写成了模块的中文名。** 必须用仓库里真实存在的目录名，写错的范围让人搜不到。
- **正文复述了 diff。** 正文只写「为什么」，「改了什么」看 diff 就行，重复一遍是浪费。
- **一条信息里出现两个类型。** 那说明这次提交该拆了，停下来告诉用户，不要硬凑一条。
```

## skills/code-review/SKILL.md

```markdown
---
name: code-review
description: 当用户要评审一段改动、要写评审意见、或问某个 Pull Request 有没有问题时使用。只产出意见文本，不改代码、不跑测试、不给合并或拒绝的结论。
---

## 工作流

1. 先读改动本身，再读被改动文件的上下文，最后才写意见。
2. 每条意见按「位置、现象、影响、建议」四段写，缺一段就不算一条合格意见。
3. 按下面的分级标注，**一条意见只能有一个级别**。

## 分级

- **必改**：正确性、安全、数据一致性。不改就不能合。
- **建议**：可读性、命名、重复。作者可以不采纳，但要回复。
- **提问**：你没看懂的地方。用问号结尾，不要写成结论。

## 坑

- **把风格问题标成必改。** 风格交给格式化工具，标成必改会让真正的必改被淹掉。
- **一条意见里塞三个问题。** 拆开，否则作者只会回复其中一个。
- **给了结论没给证据。** 「这里有并发问题」不算意见，要说清两个请求怎么交错才出问题。
```

## skills/release-report/SKILL.md

```markdown
---
name: release-report
description: 当用户要写发布报告、版本说明、上线记录，或要整理某一版包含哪些改动时使用。只填写报告文本，不执行发布、不改版本号、不碰任何部署命令。
---

## 工作流

1. 用 `git log --oneline <上一版标签>..HEAD` 拉出这一版的全部提交。
2. 按类型归类：新功能、修复、其它。**类型为 chore 与 test 的不进报告。**
3. 按模板填写，每一栏都要有内容，没有就写「无」，不要留空。

## 模板

    ## <版本号>（<日期>）

    ### 新功能
    ### 修复
    ### 需要人工确认的事项
    ### 回滚方式

## 坑

- **回滚方式写成「回滚上一版」。** 要写清具体命令与数据迁移是否可逆，这一栏是出事时唯一被读的一栏。
- **把 chore 提交也列进去。** 报告是给使用方看的，构建配置的改动对他们没有信息量。
- **需要人工确认的事项留空。** 真的没有就写「无」，留空会让读的人以为你忘了填。
```
