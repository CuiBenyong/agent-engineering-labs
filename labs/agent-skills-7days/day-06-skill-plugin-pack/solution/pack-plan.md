# 插件包设计：team-conventions

> 这份文档在写任何一行 SKILL.md 之前填完。**包的边界一旦发出去就很难改**，因为包名是命名空间。

## 清单三字段

| 字段          | 取值                                                                                 | 定这个值的理由                                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | `team-conventions`                                                                   | 它就是命名空间，包里三个技能会变成 `team-conventions:commit-message` 这样的调用名。用「团队 + 规范」而不是「工具 + 集合」，因为它约束的是做法不是能力 |
| `description` | 某团队的提交、评审与发布规范，装上即生效，覆盖提交信息、代码评审意见与发布报告三件事 | 这句话给的是**装不装**的判断，不是触发判断。要写清覆盖哪三件事，让人一眼知道自己缺的那件在不在里面                                                    |
| `version`     | `1.0.0`                                                                              | 首发。对外发布必须写死版本，不写的话 Git 来源会拿提交哈希当版本，每推一次内容用户就更一次                                                             |

## 为什么是一个包，不是三个

判据是**它们是否一起被采纳、一起被淘汰**。这三件事都围着同一份团队规范文档转，一个新人入职要么全套都要、要么一件都用不上，所以合成一个包。

反例：我个人那个「用中文解释报错」的 skill 没有放进来。它是个人习惯不是团队规范，塞进去等于逼每个装这个包的人接受我的偏好。

## 三个 skill 的边界

| 技能             | 什么时候触发                                                         | 明确不管什么                                           | 和相邻技能怎么区分                                                       |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| `commit-message` | 用户要提交改动、要写或改一条提交信息、问「这次提交怎么写」           | 不管分支命名、不管要不要拆提交、不写 Pull Request 描述 | 它只负责**一条提交信息的文本**。一旦话题变成「这个改动该怎么拆」，交给人 |
| `code-review`    | 用户要评审一段改动、要写评审意见、问「这个 Pull Request 有什么问题」 | 不管跑测试、不管自动改代码、不给合并结论               | 它只**产出意见文本**，不做判断也不动代码。改代码是另一件事               |
| `release-report` | 用户要写发布报告、版本说明、上线记录                                 | 不管发布本身、不管改版本号、不碰任何部署命令           | 它只**填一份报告**。真正的发布动作由流水线做，这个 skill 一步都不碰      |

三条描述互斥性自查：把「帮我写个提交信息」「帮我看看这个改动有没有问题」「这一版要上线了，写个说明」各说一遍，每句只应该命中一个。形似负例是「帮我把这几个提交合成一个」——三个都不该触发，因为那是操作不是文本。

## 这个包不管什么

- **分支与提交拆分策略**：属于团队工作流规范，不在这个包里，去看内部工程手册。
- **CI 配置与部署**：那是流水线的事，skill 不碰任何有副作用的动作。
- **代码风格自动修复**：交给格式化工具与静态检查，不要用 skill 去做确定性的事。

有人要上面这三件里的任何一件，答案是「这个包不管，去找 X」，而不是往包里再加一个 skill。**包的价值一半来自它明确不做什么。**
