# D6 实验：一个含三个 skill 的插件包

> 目标：把前几天散在各处的三个 skill 收成一个能交给别人的包——有清单、有命名空间、有版本、有升级说明。**今天的产出是文档和一个目录结构，不是程序**，但每一条边界都要经得起「那这个场景归谁管」的追问。

## 你会学到

- 按「是否一起被采纳、一起被淘汰」这条判据决定哪些 skill 该合成一个包
- 插件的目录约定与清单四字段，以及包名为什么就是命名空间
- 本地开发模式加载：不发布、不安装，直接把目录挂进去逐个触发验证
- 版本策略：什么改动要升、什么不用，以及**为什么描述的改动最容易被漏掉**

## 目录

- `starter/`：四份挖空的模板，骨架与提示问句都写好了，待填处是 `> TODO：` 引用块
- `solution/`：填好的示范样例，用的是一个叫 `team-conventions` 的包

两个目录里的文件名一一对应：

| 文件               | 干什么用                                                                      |
| ------------------ | ----------------------------------------------------------------------------- |
| `pack-plan.md`     | 先想清楚边界：清单三字段、为什么合成一个包、三个 skill 各管什么与明确不管什么 |
| `plugin-pack.md`   | 包的目录结构、清单，以及三份 SKILL.md 的正文                                  |
| `load-log.md`      | 本地加载、结构自检、逐句触发记录与命名空间验证                                |
| `upgrade-notes.md` | 版本策略、升级期的坑与变更记录                                                |

**填的顺序是固定的**：`pack-plan.md` → `plugin-pack.md` → `load-log.md` → `upgrade-notes.md`。边界没想清楚就先写 SKILL.md，你会在三条描述互相抢的时候推倒重来。

## 怎么用

这一天没有代码，所以**不需要** `pnpm install`、不需要 `MOCK=1`、也没有自检脚本要跑。

1. 通读 `solution/` 的四份样例，特别是 `pack-plan.md` 里那张边界表——注意每个 skill 的「明确不管什么」都写得和「什么时候触发」一样具体。
2. 回到 `starter/`，把每个 `> TODO：` 换成**你自己的**内容。三个 skill 用你在 D2、D3、D4 写过的那几个，或者你团队里真实存在的三条规范。
3. 按 `plugin-pack.md` 里的结构在磁盘上真的把这个目录建出来，用本地开发模式挂上去。
4. 把 D6 正文里那段结构自检脚本拿来跑一遍，再逐句触发，把结果填进 `load-log.md`。
5. 最后对着「验收标准」逐条自检。

## 验收标准

1. 插件目录结构正确：清单在 `.claude-plugin/plugin.json`，三个 skill 在**插件根下**的 `skills/` 里；把 `skills/` 塞进 `.claude-plugin/` 是最常见的错误，症状是包装上了但一个技能都不出现。
2. 三个 skill 各写清了「什么时候触发」与「明确不管什么」，且任意两个的触发场景不重叠；`load-log.md` 里至少有**两句形似但都不该触发**的负例，且实际确实都没触发。
3. 本地开发模式加载成功，三个技能各触发一次，`load-log.md` 里记下了带包名前缀的完整调用名。
4. `upgrade-notes.md` 的表格把每一类改动都判了「升 / 不升」，并且**把 `description` 的改动明确归进要升的那一类**，理由写的是「描述是唯一的触发面」。
5. `pack-plan.md` 里有一节「这个包不管什么」，列了至少 3 条并各自注明该去找谁。

## 常见坑

1. **把组件目录塞进 `.claude-plugin/`。** 这个目录里只放 `plugin.json` 一个文件，`skills/`、`agents/`、`hooks/` 全在插件根下。放错了不会报错，只是技能一个都不出现——先查这一条再查描述。
2. **包名随便起。** 包名就是命名空间，包里所有技能的调用名都带它作前缀。改名等于把全部调用名一起改掉，用户那边写死了调用名的地方会一起断。**一次想好。**
3. **三个 skill 的描述互相抢。** 最典型的是「写提交信息」和「写发布说明」都覆盖了「整理这一版有哪些改动」。写完把三条描述单独抽出来，用 D3 那套正负例跑一遍，别靠感觉。
4. **只写「管什么」，不写「不管什么」。** 包发出去两周内一定会有人问「为什么这个场景它不管」。提前写清楚，省下的是往后每一次的解释成本。
5. **改了描述不升版本。** 大家都记得改脚本要升，却觉得把描述改准一点不算变更。描述是触发面：改宽了开始抢别的任务，改窄了突然不触发。**描述的每一次改动都是行为变更。**
