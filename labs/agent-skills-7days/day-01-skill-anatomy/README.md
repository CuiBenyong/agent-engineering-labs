# D1 实验：一张读懂并触发三个现成 skill 的记录表

> 目标：在动手写自己的 skill 之前，先把三个现成的拆开看一遍——把 description 的触发面、正文的分层、附件目录的用法逐栏填进一张表，从而知道「一个写得好的 skill」长什么样。今天的产出是文档，不是程序。

## 你会学到

- 对着 SKILL.md 逐栏读出 name、description、正文分层与附件目录
- 用「会触发 / 形似但不该触发」一对句子，把 description 的边界量出来
- 数出 description 字符数与 SKILL.md 行数，对照规范的两条预算线做判断
- 找出正文里「什么条件下读哪个文件」这类语句，理解渐进式加载的第三阶段靠什么触发

## 目录

- `starter/skill-anatomy.md`：挖空的记录表，骨架和提示问句都写好了，待填处是 `> TODO：` 引用块
- `solution/skill-anatomy.md`：填好的示范
- `solution/sample-skill/`、`solution/sample-skill-2/`、`solution/sample-skill-3/`：示范里用到的三个自带 skill

**示范为什么不用 `anthropics/skills` 里的 skill？** 因为上游仓库随时会变，写死的行数与字符数第二天就对不上了。自带的三个 skill 结构齐全、数字可以自己 `wc -l` 数出来，适合当尺子。**你做的时候换成仓库里真实的三个。**

## 怎么跑

这一天没有代码，所以**不需要** `pnpm install`、不需要 `MOCK=1`、也没有自检脚本。

1. 打开 `https://github.com/anthropics/skills`，挑三个你一眼能看懂它在解决什么问题的 skill。别挑最复杂的。
2. 通读 `solution/skill-anatomy.md`，看清楚每一栏应该填到什么颗粒度。
3. 数字栏用命令数，别用眼睛估：

   ```bash
   wc -l path/to/SKILL.md
   ```

4. 回到 `starter/skill-anatomy.md`，把每个 `> TODO：` 换成你自己的内容。
5. 最后对着「验收标准」逐条自检。

## 验收标准

1. 记录表里三个 skill 各填满一行，每行都写出了它的 name、description 的触发面、正文分成了哪几段、带了哪些可选目录。
2. 每个 skill 都写出了一句会触发它的话，和一句形似但不该触发它的话，并说明两者的差别在哪个词上。近似负例必须与该 skill 共享关键词，否则这一栏无效。
3. 三个 skill 的 description 字符数与 SKILL.md 行数都数出来了，并对照 1024 字符与 500 行两条线各给出了一个超标或不超标的判断。
4. 表格末尾写了一段不超过五行的总结，指出这三个 skill 里你最想抄的一个写法是什么。

## 常见坑

1. **近似负例写成了完全无关的句子。** 「今天天气怎么样」当然不会触发任何 skill，但它什么也没测出来。有效的近似负例必须和 skill 共享关键词而目标动词不同——「帮我把这份 CSV 转成 JSON」对一个 CSV 校验 skill 才是真正的考验。
2. **description 只读了前半句就下结论。** 好的描述往往在末尾还有一句边界（「不负责判断该不该发布」）。这半句决定了它在什么时候**不该**被触发，比前半句更能看出作者的水平。
3. **行数用眼睛估。** 500 行是一条真实的建议线，估出来的数字没法拿来判断。用 `wc -l`。
4. **把「有 references 目录」当成加分项。** 关键不是有没有这个目录，而是正文里有没有写清楚「什么条件下去读它」。写了「细节见 references 目录」等于没写——模型不知道什么时候该看。
