# D2 触发验证记录（示范）

> 这份记录来自一次真实的调试过程：第一版描述漏掉了口语说法，第 2 轮没触发，
> 补了一句之后第 2 轮和第 3 轮都过了。**把失败那一轮留在记录里，比只留成功的有用。**

## 安装位置

- 客户端：Claude Code
- 放在哪个目录：项目级、跨客户端约定目录，即 `.agents/skills/commit-message/SKILL.md`
- 客户端的 skill 列表里看到它了吗：是。第一次其实没看到，原因是目录名写成了 `commit_message`，与 frontmatter 的 `name` 不一致，改成连字符之后才出现。**这一步排在改描述前面，省了一轮瞎猜。**

## 触发记录

| 轮次 | 我说的原话                     | 期望   | 实际                   | 没触发时改了描述的哪一处                                                                        |
| ---- | ------------------------------ | ------ | ---------------------- | ----------------------------------------------------------------------------------------------- |
| 1    | 帮我按规范写一下这次的提交信息 | 触发   | 触发，输出了模板格式   | 不适用                                                                                          |
| 2    | 这几个文件我要提交了           | 触发   | 第一次没触发，改后触发 | 描述里原本只有「写 commit message」这种术语说法，补了「这几个文件我要提交了」这一类**口语说法** |
| 3    | 这次改动该怎么描述             | 触发   | 触发                   | 不适用                                                                                          |
| 4    | 这次改动该不该现在提交         | 不触发 | 未触发，正确           | 不适用；靠的是末尾那句「不负责决定该不该提交」                                                  |

第 4 轮与第 1 到 3 轮共享「提交」「改动」两个关键词，但目标动词是「该不该」，属于决策而不是生成。这是一个有效的近似负例。

## 一句话复盘

改了一轮。最有效的一次改动是**补口语说法**——术语说法我写的时候自然就想到了，因为那是我脑子里的叫法；而用户真正会说的是「这几个文件我要提交了」，那句话里一个专业词都没有。写描述时的盲区就在这儿：**你熟悉这个领域，所以你想不到不熟悉的人会怎么说。**
