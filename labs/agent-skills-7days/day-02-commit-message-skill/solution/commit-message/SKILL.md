## 工作流

1. 跑 `git diff --staged --stat` 看这次到底改了哪些文件，改动为空就直接告诉用户暂存区是空的，不要凭猜写。
2. 定类型：只能从 `feat` `fix` `docs` `refactor` `test` `chore` 六个里选一个。一次改动跨了两个类型，说明这次提交该拆成两次，先提醒用户。
3. 定作用域：取改动集中的那个目录名或包名，改动散在三个以上目录时整个省略作用域，不要写 `misc` 这种没信息量的词。
4. 写正文：第一行不超过 50 个字符、用中文、结尾不加句号；正文段落说清「为什么改」而不是「改了什么」，改了什么看 diff 就有。
5. 自检：对着下面「坑」那一段逐条过一遍，再把结果交给用户。

## 输出模板

```text
<类型>(<作用域>): <一句话，不超过 50 字符，不加句号>

<为什么要做这次改动，两三句，可省略>

<关联的 issue 或工单号，可省略>
```

作用域省略时冒号前只留类型，不要留一对空括号。

## 坑

- **类型只有六个，多一个都不行。** 常见的越界写法是 `perf` 和 `style`，这两个在我们这儿分别归 `refactor` 和 `chore`。
- **第一行不写「修改了」「更新了」这类动词开头。** 写 `修复订单金额四舍五入错误`，不写 `修复了订单金额的四舍五入错误`。
- **正文段落不要复述 diff。** 「把 amount 从 float 改成 integer」是 diff 里就有的信息，「金额用浮点数存在四舍五入误差，改成以分为单位的整数」才是提交信息该承载的东西。
- **改动跨类型时不要硬选一个。** 这种情况下正确的动作是提醒用户拆分，而不是挑一个看起来占比大的类型糊过去。
