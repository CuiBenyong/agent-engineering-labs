## 工作流

这是一个「先规划、再校验、后执行」的流程，**三步不能合并**。中间那步校验才是这个技能存在的理由。

- [ ] 第 1 步：分析模板，拿到字段清单

  ```bash
  pnpm analyze assets/template.md
  ```

  它输出一行 JSON，列出模板需要的每个字段的名字、类型与是否必填。**不要凭记忆猜字段名。**

- [ ] 第 2 步：写一份取值计划 `values.json`，每个字段一项。摘要字段允许你自己写，其余字段的值必须来自用户提供的材料，材料里没有就问用户，不要编。

- [ ] 第 3 步：校验计划

  ```bash
  pnpm validate fields.json values.json
  ```

  退出码 0 表示通过。非 0 时读它给的错误列表，**改 `values.json` 之后重新校验，直到通过为止**。不要跳过这一步直接填。

- [ ] 第 4 步：填充并输出

  ```bash
  pnpm fill assets/template.md values.json report.md
  ```

- [ ] 第 5 步：把生成的报告读一遍，确认摘要那一段说的是「为什么发这一版」，不是「改了哪些文件」。

## 坑

- **接口数与破坏性变更是有类型的。** 接口数必须是数字，写成「七个」会被校验挡下来；破坏性变更必须是布尔值，写成「有」同样过不去。这两个字段最常被写成中文字符串。
- **校验报的「模板里没有字段 X」几乎总是拼写错误。** 错误信息里带了可用字段列表，照着改，不要新增字段——模板不会因为你多写一项就多出一栏。
- **回滚方案不能留空。** 它是必填字段，而且是这份报告里唯一在出事时真正会被人读的一段。写不出来就去问发布负责人。
- **填充脚本不做校验。** 它发现还有没填的占位符时会直接报错退出，而不是写出一份带着两对花括号的文档——那种文件会被当成填好的直接发出去。

## 可用脚本

- `scripts/analyze.ts`：模板转字段清单。退出码 1 表示模板里一个占位符都没有，多半是路径给错了。
- `scripts/validate.ts`：字段清单加取值计划，输出通过与否与错误列表。退出码 1 表示有错误，2 表示用法或文件的问题。
- `scripts/fill.ts`：填充模板。不给输出路径就打到标准输出。
