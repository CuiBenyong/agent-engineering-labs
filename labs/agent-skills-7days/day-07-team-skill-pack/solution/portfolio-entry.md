# 作品集条目

## 简历上的一条（中文）

**团队规范 Agent Skills 包（个人项目）**：把一份 31 页的团队工程手册拆成 3 个 Agent Skills 并打成可分发的插件包；用 15 条带断言的评估用例做带与不带的对照，规范符合率从 53% 提升到 87%（同一模型、同一提示，两组子代理只差是否预加载 skill，其中 2 条为人工判定）。

## 一条（英文）

**Team convention Agent Skills pack (personal project)**: Decomposed a 31-page engineering handbook into 3 Agent Skills packaged as a distributable plugin; measured with 15 assertion-based eval cases, convention compliance rose from 53% to 87% (same model and prompt, the two subagent arms differing only in preloaded skills, 2 cases human-judged).

## 追问准备

**为什么不直接写进系统提示？**
两个成本。第一是钱：系统提示每一轮都要重发，这三份规范加起来 312 行，一次五十轮的会话要重复计费几十万 token。第二更贵——注意力：一份塞了三件不相干事情的系统提示，会让模型在做第三件事时被第一件的规则干扰。**skill 的价值不在于装得多，而在于平时都关着**：每轮只有名字与描述，正文只在命中时才进来。

**这 31 页怎么变成 312 行的？**
按触发场景聚类而不是按章节切，得到 11 个场景，其中 3 组能聚成「同一个时刻」，其余 5 个场景频次太低或需要人来判断，没做成 skill。文档里约 60% 的内容（历史、价值观、每条规则的「为什么」）一个字都没进——判据是「不写这条，模型会不会做错」。

**放弃了什么？**
第一，放弃了确定性规则写进正文，类型取值和版本号格式沉淀成了一个校验脚本，正文只留一句「写完跑一次校验」。第二，放弃了「一个包管全套」，分支命名、依赖升级这些场景明确不管，写进了包的「不管什么」一节。第三，放弃了全自动评估，2 条判断性用例老实标成人工判定，而不是硬凑一个假绿的断言。

**这个数字可靠吗？**
只在这 15 条任务上可靠。小样本不能外推成通用效率提升。失败明细显示不带 skill 的 7 条失败全部集中在格式与取值范围这类事实性约束上，这与「skill 补的是经验缺口而不是能力缺口」这个预期一致，是个正面的旁证，但不是证明。下一版会扩到 40 条以上重跑。
