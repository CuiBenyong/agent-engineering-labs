# 从规范文档到三个 skill：拆分表

源文档：《某团队前端工程手册》，31 页，7 章。

## 第一步：只记场景，不记内容

通读一遍，把「什么时候有人会用到这一段」列出来。得到 11 个场景：

1. 我要提交这批改动了
2. 提交信息类型该选哪个
3. 这次提交是不是该拆开
4. 有人让我评审一个 Pull Request
5. 评审意见该写多严厉
6. 这一版要上线了
7. 上线出问题了要回滚
8. 新建一个分支该叫什么
9. 依赖要升级了
10. 某个接口要废弃了
11. 线上报错了要定位

## 第二步：按「同一个时刻」聚类

| 聚类           | 包含的场景      | 落成哪个 skill         |
| -------------- | --------------- | ---------------------- |
| 我要提交了     | 1、2            | `commit-message`       |
| 有人让我评审   | 4、5            | `code-review`          |
| 这一版要上线了 | 6、7            | `release-report`       |
| 其余           | 3、8、9、10、11 | **不做成 skill**，见下 |

场景 3「这次提交是不是该拆开」和场景 1 在同一章里，但它是另一个时刻，而且结论需要人来定，不做成 skill。场景 8 到 11 各自独立、频次低，做成 skill 只会把触发面搅浑，留在手册里给人读。

**注意聚类结果和文档章节几乎不重合**：`commit-message` 的内容来自第 2 章和第 5 章的附录，`release-report` 的内容横跨第 4、6、7 三章。这正是「按触发场景切、不按章节切」的样子。

## 第三步：三个 skill 的边界与互斥检查

| 技能             | 触发场景                         | 明确不管什么                                           | 来自文档哪几段                                 |
| ---------------- | -------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| `commit-message` | 要提交改动、要写或改一条提交信息 | 不管提交要不要拆、不管分支命名、不写 Pull Request 描述 | 2.1 提交格式、2.3 类型表、附录 A 范围取值      |
| `code-review`    | 要评审一段改动、要写评审意见     | 不跑测试、不改代码、不给合并或拒绝的结论               | 3.2 评审原则、3.4 意见分级                     |
| `release-report` | 要写发布报告、版本说明、上线记录 | 不执行发布、不改版本号、不碰部署命令                   | 4.5 版本说明格式、6.1 回滚要求、7.2 上线检查项 |

互斥检查（每句只应命中一个）：

| 说的那句话                             | 应命中         | 实测                                  |
| -------------------------------------- | -------------- | ------------------------------------- |
| 这几个文件我要提交了，帮我写个提交信息 | commit-message | 通过                                  |
| 帮我看看这个 Pull Request 有什么问题   | code-review    | 通过                                  |
| 这一版要上线了，写个版本说明           | release-report | 通过                                  |
| 帮我把这几个提交合并成一个             | 都不该命中     | 通过（这是操作不是文本）              |
| 整理一下这一版都改了什么               | release-report | 第一轮**失败**：commit-message 也抢了 |

第一轮失败的那条，原因是 `commit-message` 的描述里写了「整理改动」。改法是把它收窄成「一条提交信息的文本」，并在「不管什么」里显式排除「整理一版的改动清单」。改完重跑通过。

## 没进任何 skill 的内容

文档 31 页里，大约 60% 没有进任何 skill：

- **第 1 章全部**：团队历史与工程价值观。对人有价值，对模型是纯负担。
- **各章的「为什么这么定」小节**：判据是「不写这条，模型会不会做错」，不会，所以不进。
- **类型取值与版本号格式**：这是确定性规则，沉淀成了一个校验脚本，`commit-message` 的正文里只留一句「写完跑一次 `scripts/check-commit.py`」。

三个 SKILL.md 加起来 312 行。**31 页压成 312 行是正常的，不是漏了什么。**
