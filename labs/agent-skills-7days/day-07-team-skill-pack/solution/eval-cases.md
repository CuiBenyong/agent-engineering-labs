# 评估用例与断言

## 设计口径

- 用例总数 **15 条**：正例 8、边界例 4、负例 3（约五比三比二）。
- 每条 2 到 4 条断言，**一条断言只查一件事**，判定的是事实成不成立，不是产出好不好。
- 判不了的老实标「人工」，不硬凑断言。

## 正例（8 条）

| 编号 | 提示                                                                      | 期望               | 断言                                                                                            |
| ---- | ------------------------------------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------- |
| P1   | 这几个文件我要提交了，帮我写个提交信息（暂存了 payments 目录下 2 个文件） | 一条合规提交信息   | A1 类型取自六个值之一；A2 范围等于 `payments`；A3 首行不超过 50 字符                            |
| P2   | 同上，但同时改了 payments 与 miniapp                                      | 提示该拆分         | A1 产出里出现「拆」或「两个类型」字样；A2 没有硬凑出一条混合类型的信息                          |
| P3   | 帮我写个提交信息，这次是补测试                                            | 类型为 test        | A1 类型等于 `test`；A2 正文没有复述 diff 的文件名列表                                           |
| P4   | 帮我看看这个改动有什么问题（一段带并发缺陷的代码）                        | 至少一条必改级意见 | A1 至少一条标了「必改」；A2 每条意见都有位置、现象、影响、建议四段；A3 没有直接给出修改后的代码 |
| P5   | 同上，改动只有命名不规范                                                  | 全是建议级         | A1 没有「必改」；A2 至少一条标了「建议」                                                        |
| P6   | 这一版要上线了，写个发布说明                                              | 四栏齐全的报告     | A1 四个二级标题齐全；A2 没有留空栏；A3 回滚栏里出现具体命令                                     |
| P7   | 同上，这一版只有 chore 提交                                               | 报告里不列 chore   | A1 新功能与修复两栏写「无」；A2 正文里不出现 chore 提交的标题                                   |
| P8   | 写个评审意见，这段代码你看不懂                                            | 用提问级           | A1 至少一条标「提问」且以问号结尾；A2 没有把不确定的事写成结论                                  |

## 边界例（4 条）

| 编号 | 提示                       | 期望                                       | 断言                                                            |
| ---- | -------------------------- | ------------------------------------------ | --------------------------------------------------------------- |
| B1   | 整理一下这一版都改了什么   | 命中 release-report，不命中 commit-message | A1 `commit-message` 未被激活；A2 `release-report` 被激活        |
| B2   | 这次提交要不要拆开？       | 都不命中，交给人                           | A1 三个 skill 均未被激活                                        |
| B3   | 帮我写个 Pull Request 描述 | 都不命中（包不管这个）                     | A1 三个 skill 均未被激活；A2 产出里说明了这不在规范包覆盖范围内 |
| B4   | 这个改动能合吗？           | code-review 可命中，但不给合并结论         | A1 产出里没有「可以合并」或「不能合并」这类结论                 |

## 负例（3 条）

| 编号 | 提示                     | 期望     | 断言                     |
| ---- | ------------------------ | -------- | ------------------------ |
| N1   | 帮我把这段代码格式化一下 | 都不命中 | A1 三个 skill 均未被激活 |
| N2   | 这个分支该叫什么名字     | 都不命中 | A1 三个 skill 均未被激活 |
| N3   | 帮我升级一下这个依赖     | 都不命中 | A1 三个 skill 均未被激活 |

## 需要人工判定的

- P4 的「这条意见有没有抓住真问题」——写不出可靠断言，随机抽 2 条自己看。
- P6 的「回滚方式写得够不够具体」——只能人判。

**结论里必须注明有 2 条为人工判定。**
