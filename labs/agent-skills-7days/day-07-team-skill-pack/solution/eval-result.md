# 对照结果

## 两组的定义

两份子代理定义**只差 `skills` 这一行**，其它逐字相同：

```text
---
name: convention-runner-with          # 对照组叫 convention-runner-without
description: 按团队规范完成提交、评审与发布类任务
tools: Read, Grep, Bash
model: sonnet
skills:                               # 对照组这两行整个删掉
  - team-conventions:commit-message
---

你是一个严格按团队规范工作的执行者。只做被要求的那一件事，
不要额外改动文件。产出交回之前，逐条对照规范自查一遍。
```

跑之前把两份定义并排 diff 了一遍，确认只有这一处差异。

## 测量条件

| 项       | 取值                                   |
| -------- | -------------------------------------- |
| 用例数   | 15（正例 8、边界例 4、负例 3）         |
| 模型     | 两组同一个模型，未改任何参数           |
| 提示     | 两组逐字相同                           |
| 会话     | 每条用例各起一个干净子代理，互不复用   |
| 运行时间 | 同一天连续跑完两组，中间未改任何 skill |
| 人工判定 | 2 条（P4、P6 的其中一项断言）          |

## 结果

| 组         | 通过 | 总数 | 通过率 |
| ---------- | ---- | ---- | ------ |
| 不带 skill | 8    | 15   | 53%    |
| 带 skill   | 13   | 15   | 87%    |

**不带 53% → 带 87%，提升 34 个百分点。**

## 失败明细

不带 skill 的 7 条失败：

- P1 / A1、P3 / A1：类型用了 `update` 与 `chore(test)`，都不在六个值里。
- P1 / A2：范围写成了「支付模块」，不是目录名。
- P4 / A2：意见只写了现象和建议，缺位置与影响。
- P6 / A1、P6 / A3：报告只有两栏，回滚栏写成「回滚上一版」。
- P7 / A2：把 chore 提交列进了报告。

**全部集中在「格式与取值范围」这类事实性约束上**，也就是模型不可能自己猜到的那部分——正是 skill 该补的缺口。

带 skill 的 2 条失败：

- B4 / A1：仍然给出了「可以合并」的结论。已把这条坑补进 `code-review` 的正文，待下一版验证。
- P2 / A1：没有提示拆分，硬凑了一条混合类型的提交信息。这条属于判断性任务，`commit-message` 的坑段里补了一条。

## 一个诚实的说明

15 条用例是小样本，这个数字只支撑「在这一批任务上」的结论，**不能外推成通用的效率提升**。负例三条全部通过，说明触发面目前没有过宽，但三条也不足以证明什么。下一版会把用例扩到 40 条以上再重跑。
