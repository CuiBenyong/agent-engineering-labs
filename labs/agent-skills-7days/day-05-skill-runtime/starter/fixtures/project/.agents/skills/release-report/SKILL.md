## 什么时候用这份手册

这份手册管的是「一次发布结束后，写给别人看的那份报告」。它不管要不要发布、也不管怎么回滚，那是另外两件事。

判断标准很简单：如果读者是没有参与这次发布的人（值班的同事、下游团队、老板），就用这份手册；如果读者是正在处理故障的你自己，那要写的是事故时间线，不是发布报告。

## 报告的固定六节

顺序固定，一节都不能少，也不要自己加节。缺内容的那节写「本次无」，不要删掉标题，因为下游有人按标题抓取。

### 一、本次发布了什么

一句话说清这次发布的主题，不要罗列提交。读者要的是「支付超时的问题修了」，不是「合并了 14 个 PR」。

主题最多两个。超过两个说明这次发布攒得太大，在报告开头显式写一句「本次发布合并了多个不相关主题」，让读者知道回滚的粒度很粗。

### 二、变更条目

每条一行，格式是「类型：做了什么（影响面）」。类型只能从下面六个里选：

- `feat` 新增能力，用户能感知
- `fix` 修复缺陷，写清修的是哪个现象
- `perf` 性能改善，必须带前后数字
- `refactor` 内部重构，用户不可感知
- `chore` 依赖升级、构建脚本、配置
- `revert` 回滚，写清回滚的是哪次发布

影响面写「全量用户」「仅国内区域」「仅内部后台」这种范围词，不要写百分比，除非是灰度发布且你真的知道比例。

条目里出现字段名或状态码时，去读 `references/FIELDS.md` 核对写法，不要凭印象写。字段名写错会让下游按错误的名字去改代码。

### 三、数据库与配置改动

这一节最容易漏，也最容易出事。逐条列出：

1. 新增或修改的表与列，写清是否可空、有没有默认值。
2. 数据迁移脚本的执行时机：是随发布自动跑，还是要人工触发。
3. 新增的环境变量与配置项，写清缺省行为。**没有缺省行为的必须标红**，因为它意味着老实例读不到配置就会崩。
4. 是否有不可逆改动。删列、改列类型、清数据都算不可逆。

不可逆改动必须在这一节的开头单独写一句「本次包含不可逆改动」，不要埋在列表第四条里。

### 四、验证与结果

写清发布后实际做了哪些验证，每条带结论。只写「已验证」等于没写。

至少覆盖三类：核心链路的冒烟结果、关键指标在发布前后各半小时的对比、报错日志有没有新增的错误类型。

指标对比要给绝对值，不要只给涨跌幅。从 2 涨到 4 也是涨了一倍，但它什么都说明不了。

### 五、已知问题与后续动作

发布完还没修完的东西写在这里，每条要有责任人和时间点。没有责任人的条目等于不存在，会在下次发布时被原样复制粘贴过去，一直挂着。

这一节写「本次无」是可以的，但要真的确认过，不要因为懒而写。

### 六、回滚方案

写清三件事：回滚命令、回滚后数据会处于什么状态、回滚的时间窗口。

如果这次发布包含不可逆的数据改动，回滚方案要写「不可整体回滚」，然后逐条说明哪部分能回、哪部分只能向前修。这比写一句假的回滚命令有用得多。

## 常见的写坏方式

- **把提交日志直接粘进变更条目**。提交信息是写给代码库的，报告是写给人的，两者的详略完全不同。
- **把风险藏在中间**。不可逆改动、缺省行为缺失、不可回滚，这三件事都要在所在小节的开头就说。
- **验证一节只写做了什么，不写结论**。读者没法从「跑了冒烟测试」推出「冒烟测试过了」。
- **已知问题不写责任人**。这一条会让问题在报告之间无限漂流。
- **为了报告好看而合并条目**。两个不相关的修复合成一条，回滚时就找不到该回哪个。

## 输出前的自检

逐条过一遍，全部为「是」才输出：

1. 六节标题齐全，顺序没变。
2. 每条变更都带类型和影响面。
3. 涉及字段名或状态码的条目，已经对照过 `references/FIELDS.md`。
4. 数据库一节写清了可逆性。
5. 验证一节每条都有结论和数字。
6. 已知问题每条都有责任人和时间点。
7. 回滚一节说清了数据状态，不是只有一条命令。
