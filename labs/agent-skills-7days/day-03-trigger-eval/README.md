# D3 实验：skill 触发测试脚本

> 目标：把「我试了三句话感觉还行」换成一张能重复跑的表——喂进一组带标注的查询，输出逐条触发率、训练集与验证集两个通过率，并当场比较两版描述哪一版更好。

## 你会学到

- 设计一组带标注的查询：正例在措辞与详略上铺开，负例必须是共享关键词的近似负例
- 每条跑三次取触发率，而不是跑一次就下结论
- 按六比四拆训练集与验证集，训练集指导改写、验证集只用来挑版本
- 用「边界句」把落在相邻能力上的请求推开，并在数字上看到它起了作用

## 目录

```
src/
├── catalog.ts   两版被测描述 + 两个陪跑 skill，拼成发现阶段那份目录
├── cases.ts     带标注的查询集（含 split 与离线模拟用的意图信号）
├── judge.ts     判定一次触发：离线模拟分支 + 真模型分支
└── index.ts     跑完全部查询，打印逐条表与两个通过率，最后比较版本
```

- `starter/`：挖了 5 个练习点，`MOCK=1` 下可以直接跑，但通过率会是 0
- `solution/`：完整实现

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 ANTHROPIC_API_KEY；没有 key 先用 MOCK=1
MOCK=1 pnpm start     # 离线模拟，看清整条流水线
pnpm start            # 真模型，判断质量以这一次为准
```

`starter/` 原样跑起来，两个版本的通过率都会是 0%，正例全是 ❌——这是正常的，五个练习点还没做。做完之后 `solution/` 的结果长这样：

```text
v1  训练集 63%  验证集 50%
v2  训练集 100% 验证集 100%
最终应当选用：v2
```

> **`MOCK=1` 下的判定不是真模型给的。** 它按每条查询预先标注的意图信号跟描述做匹配，
> 目的是让整条流水线在没有密钥时也能跑通、也能看出「改了描述结果就变」。
> **描述写得好不好，最终必须去掉 `MOCK=1` 用真模型验证一遍。**

## 验收标准

1. `MOCK=1` 下能跑通全流程，输出一张逐条表格：查询、期望、触发率、通过与否，最后给出训练集与验证集两个通过率。
2. 查询集至少 12 条，正负比例接近，其中至少 3 条是与目标 skill 共享关键词的近似负例。
3. 每条查询跑 3 次并取触发率，而不是跑一次直接判定。
4. 训练集与验证集按大约六比四拆开，两个集合的正负比例接近，并且汇总时分别统计。
5. 按训练集的失败项改一版描述后重跑，能在输出里看到两版描述的验证集通过率对比。

## 常见坑

1. **跑一次就下结论。** 模型的判断是不确定的，同一条查询这次触发下次可能不触发。跑一次拿到的只有 0 或 1，看不出「勉强命中」和「稳稳命中」的区别，而这两者在真实使用里的体验天差地别。练习 3 挖的就是这个。
2. **负例挑得太远。** 「解释一下 git rebase 和 merge 的区别」这种句子当然不会触发，但它什么也没测出来。真正有区分度的是「这次改动该不该现在提交」——共享「改动」「提交」两个词，目标动词却是决策。练习 5 要你补的就是这一类。
3. **训练集和验证集混在一起算。** 混算之后你其实是在拿全部数据调描述，调出来的那一版只对这批查询有效。练习 4 挖的就是这一步，做完你会看到两个数字经常不一样，而**该信的是验证集那个**。
4. **改描述时把失败查询的原话抄进去。** 那一条会立刻通过，换一句同义的又不过。正确做法是归纳出它代表的那一类说法——`solution` 里 v2 补的是「用日常说法表示这批文件准备提交」这一类，不是训练集里那句原话。
5. **忘了给陪跑 skill。** 只有一个 skill 时，负例没有「被别人接走」的可能，模型只能在触发与不触发之间二选一，近似负例就测不出边界了。`catalog.ts` 里那两个陪跑不是装饰。
