# D18 实验：一套生命周期钩子与后台任务机制，编辑后自动检查、长命令不阻塞对话

> 目标：给 `mca` 装上**确定性的那一半**。前十七天加的东西都是「让模型做得更好」，
> 今天加的是「不让它有机会做错」：四个生命周期触发点、一套能否决也能回灌的钩子协议，
> 外加一套后台任务机制，让跑得久的命令不再把对话卡住。**零运行时依赖**——
> 不引 prettier、不引任何任务队列，格式化自己写、进程自己管、进度接收端自己起。
>
> 现象最好看的两条：模型第一手想**凭记忆直接改文件**，被 `read-before-write`
> 当场拦下、工具根本没执行，于是它补读一次再改；改完钩子自动跑了 `node --test`
> 并把「四个用例全绿」回灌给它，**它就没再自己跑一遍测试**。
> 另一条是后台任务跑完时那行通知——它**不是当场打印的**，而是攒到一个终端状态
> 允许插话的时刻才出现。

## 你会学到

- 钩子的四个触发点，以及**为什么只有 pre_tool 能否决**（post_tool 的「阻断」是另一件事）
- 否决怎么实现才不破坏协议：返回一条 ok 为 false 的 `ToolResult`，和第五天的审批门同一条路
- 钩子的输出**要不要回灌给模型**：判据是「它接下来的决策会不会因此不同」
- 钩子失败时阻断还是只警告，取决于它守的是什么；以及为什么默认该是只警告
- 钩子的超时与异常必须兜住：**一个写坏的钩子最坏的后果应该是它自己失败**
- 确定性约束与概率性约束的分工：**能用一个 if 判断出来的规矩，就不该交给模型去记**
- 钩子与第五天权限规则的分界：权限管「谁有权做」，钩子管「此刻做得对不对」
- 挂钩子的三种做法，以及为什么选了「装饰 ToolDef」而不是改循环、不是扩协议
- 后台任务三件套：进程、日志、状态查询，少一件它就是个找不回来的东西
- `run_background` 返回的是**受理回执不是结果**，以及这件事为什么必须写进工具描述
- 终端的三种状态，以及通知为什么只能在其中一种里插话
- **钩子会拖慢每一次编辑**，而且这笔账是乘以编辑次数的

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：凭记忆改文件被拦下 → 补读一次再改 → 钩子替它跑完测试
rm -rf work
printf '这个失败的用例，最快的办法是什么（钩子演示）\ny\ny\n/exit\n' | MOCK=1 pnpm start

# 主现象二：改错了，阻断型钩子把这次调用判成失败，模型自己改对
rm -rf work
printf '先看一眼再加个守卫，我可能会改错\ny\ny\ny\n/exit\n' | MOCK=1 pnpm start

# 主现象三：后台任务——受理回执、进度、完成通知排在对话之后
rm -rf work
printf '这条要跑很久，放后台\ny\n/tasks\n再说说别的\n/tasks t1\n/exit\n' | MOCK=1 pnpm start

# 钩子的开销与总开关
rm -rf work
printf '/hooks\n/hooks off\n/exit\n' | MOCK=1 pnpm start
```

> **哪些数字可复现：** 自检里除毫秒数之外的每一项都可复现（连跑两次 diff 只差耗时）：
> 选中了几个钩子、拦没拦下、文件内容、任务状态与进度步数、通知攒了几条、
> 端到端那一轮调了哪几个工具。**不可复现的是毫秒数**——`test-after-write` 是真的在跑
> `node --test`，每台机器、每次都不一样，正文里只写量级不写具体值。
>
> 端口 **3118** 是后台任务报进度的接收端，只绑 `127.0.0.1`。被占用时 `mca` 照常启动，
> 只是报不上进度（换端口用 `MCA_TASK_PORT`）。跑完记得 `/exit` 正常退出，
> 那一步会杀掉还在跑的任务并关掉端口。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `14/14 通过`
- [ ] 否决那一项：没 `read_file` 过就 `edit_file` 被拦下，`blockedBy=hook`，**文件一个字节都没变**
- [ ] 放行那一项：补一次 `read_file` 之后同一个调用就过了（判据依赖会话状态，权限规则表达不了）
- [ ] 阻断那一项：改坏源码之后 `test-after-write` 把这次 `edit_file` 判成失败，测试输出原样回灌
- [ ] 超时与异常那两项：钩子卡住 / 抛错都只是「这个钩子失败了」，自检没有崩
- [ ] 后台那四项：受理回执立刻返回、进度经 3118 报到 3/3、日志落盘可回看、通知攒住了没当场插话
- [ ] 端到端那一项：三次工具调用是 `edit_file`（被拦）→ `read_file` → `edit_file`，而且**没有 run_command**
- [ ] `pnpm typecheck` 无输出

## 常见坑

- **钩子一定要有超时，而且超时要算失败。** 没有超时的钩子就是一个新的挂死点：它挂住的不是它自己，是整个 Agent 的这一次工具调用。而把超时算成「通过」更糟——那等于在最需要检查的时候（工作区大到检查跑不完）悄悄把检查关掉了。另外要知道 `Promise.race` **停不住任何东西**：JavaScript 没法从外面掐断一个正在 await 的函数，真正能停住的是钩子自己传给子进程的那个超时。
- **钩子抛的异常必须兜在钩子这一层。** 一个写坏的钩子最坏的后果应该是「少一个检查」，不是「mca 起不来」。这和第十五天对掉线 MCP server、第十六天对写坏的技能包是同一条纪律。
- **否决要走「返回一条失败结果」，不要抛异常。** 抛异常会被注册表兜成一句「执行失败」，模型看不出发生了什么，多半原样重试。返回一条写清原因与下一步的 `ToolResult`，第六天那套自纠就自动接手了。
- **否决的失败信息里必须写「重试没用」。** 模型第六天学到的是「失败就再试一次」，而确定性规则重试一万次结果都一样。少这一句，你会看到它对着同一堵墙撞三次然后被打转检测拦下。
- **`post_tool` 的 blocking 不是「撤销」。** 工具跑完文件已经改了，那时候说「不行」是自欺。它的真实含义只有一个：把这次调用判成失败，好让模型知道自己那一手没成。想真的阻止，只能在 `pre_tool`。
- **别把所有钩子都写成阻断。** 一个动不动就阻断的钩子会让 Agent 变成走不动路的东西，而那种故障最难查——用户看到的只是「它今天什么都不肯做」。默认应该是只警告。
- **钩子的输出不是都该回灌。** 判据只有一条：模型接下来的决策会不会因为知道它而不同。格式化改了几个空格，说了也是废话（但改动了文件内容就得说，否则它下一次精确替换会拿旧原文去匹配）；测试红了它必须知道。
- **别拿钩子去做权限该做的事。** 第五天的权限规则按工具名与路径静态匹配，钩子的判据可以依赖会话状态与写入内容。本实验里 `test/**` 不许改那条已经是一条权限规则了，再写一个同样的钩子只是让它永远跑不到。
- **`run_background` 的描述里必须写清「返回的是回执不是结果」。** 模型见过的工具几乎都是调用完就拿到答案，不明说的话它会拿着回执告诉用户「测试跑完了」。
- **后台任务的日志用 `flags: 'w'` 不是 `'a'`。** 任务号在每个进程里都从 `t1` 重新开始，追加会把上一次运行的日志接在这一次前面——这个坑只在第二次跑的时候才出现，第一次怎么测都测不到。
- **通知不能想打就打。** 终端在任何时刻只可能是三种状态之一，只有「正在等用户输入**而且他一个字都还没敲**」那一种才允许插话。正在流式输出时插一行会把打字机撕成两半；用户敲了半行字时插一行会把他敲的东西冲掉。其余时候攒着，等一轮结束再倒。
- **给人看的通知和给模型看的通知要分开攒。** 屏幕上的字不在消息数组里。少了这一条，用户会遇到一个很别扭的现象：他明明看到「任务完成」，一问模型却说「还在跑」。
- **退出时要把后台任务杀掉，而且先杀进程再关端口。** 反过来的话，正在报进度的任务会在一个刚关掉的端口上收到连接拒绝，日志里多出一堆吓人的报错——而那只是我们自己收摊的顺序没排对。
- **钩子会拖慢每一次编辑，这笔账要乘以编辑次数。** 沙盒仓库跑一次 `node --test` 是一百来毫秒，看起来不值一提；真实仓库跑全量测试要几分钟，一个任务改二十次文件就彻底没法用了。到那一步就得换成「只跑受影响的那几个文件」，或者把这个钩子挪到提交前那个触发点上。
