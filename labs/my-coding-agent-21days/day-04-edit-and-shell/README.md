## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 看它自己把红测试修绿（这是全课的基准任务）
printf '帮我修一下失败的测试\n/exit\n' | MOCK=1 pnpm start

# 看原文对不上时它怎么改道
printf '直接改，不读就改\n/exit\n' | MOCK=1 pnpm start

# 看卡死的命令被杀掉（solution 约 2 秒；杀不掉的实现会一直挂着）
printf '帮我修一下失败的测试\n/exit\n' | MOCK=1 INJECT=timeout pnpm start
```

> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

> 沙盒仓库零依赖：测试用 Node 自带的 `node --test`，所以 `work/repo` 里不需要 `pnpm install`。
> 每次自检都会重新 `seed` 一遍，保证起点一致。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `7/7 通过`
- [ ] 说一句「帮我修一下失败的测试」，终端上依次出现 run_command、read_file、edit_file、run_command 四张卡片，第二次退出码是 0
- [ ] `old_string` 与文件内容不一致时返回「找不到」，出现多次时返回「出现了 N 次」，两种情况下文件一个字节都没动
- [ ] 一条打出二十万字符的命令，标准输出只留 4000 字符、整条结果回灌 4085 字符
- [ ] `INJECT=timeout` 时终端出现「命令超时被杀掉」，进程真的没了，循环继续往下走

## 常见坑

- **不要用 replace 直接改第一处。** 这是本天最危险的一个 bug，因为改动看起来成功了：`old_string` 在文件里出现多次时，你会静默改错地方，而返回给模型的是「已改」。必须先数出现次数，0 次与多次都失败。
- **「原文必须唯一且完全匹配」这条规则同时兼任冲突检测。** 模型读到的那段内容如果已经不在了（被外部编辑器改过、被上一次替换动过），匹配就会失败，这次写入必须放弃。不许模糊匹配、不许「猜它想改哪一处」。
- **新建与删除不要塞进替换工具。** 新建没有「旧内容」可匹配，所以单独一个工具，并且目标已存在时必须失败（覆盖已有文件应当走 `edit_file`）。删除是不可逆操作，本课交给命令工具，并在第五天被审批门拦住。
- **杀不掉的子进程是最容易踩的坑。** `spawn` 时要 `detached: true` 让子进程自成进程组，杀的时候杀进程组（负的 pid），并且 SIGTERM 之后留一小段宽限期再 SIGKILL。只杀 shell 的话，它拉起的孙子进程会变成孤儿继续跑，而且还持着管道，于是 `close` 事件永远不来、这次工具调用永远不返回——现象是「杀了却没停」。starter 里就是这个错误实现，你会看到自检第 7 项卡到超时。
- **输出要边收边截，不要先攒完再截。** 先攒完的话内存里仍然放着那几十万字符。另外标准输出与错误输出要分开算上限，否则一条刷屏的警告会把真正的报错挤掉。
- **子进程的标准输入要给 `ignore`。** 否则等输入的交互命令会一直挂着，直到超时才被杀——给 `ignore` 它会立刻读到 EOF 而自行退出。
