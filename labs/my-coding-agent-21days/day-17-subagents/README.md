# D17 实验：子 Agent 派发、工作树隔离与结果汇总

> 目标：把一件能拆开的活儿分头干。每个子 Agent 有**自己的消息数组、自己的工具白名单、
> 自己的预算、自己的一间工位**，做完只交回一份结构化回执；主会话看不到它中间说过的任何一句话。
>
> 现象最好看的两条：两个子 Agent 的时间区间**真的重叠**（墙上时间明显小于两者耗时相加），
> 而主工作区在合并之前**一个字节都没变**；以及两个人改同一个文件改成了不同版本时，
> **一份都不落盘**并报出冲突——直觉写法在这里会静默地让后写的那个赢。

## 你会学到

- 子 Agent 就是**再跑一遍 `kernel/loop.ts` 的 `run()`**：换消息数组、换工具表、换预算、换工作目录，循环一行没改
- 三条「独立」各挡住一种失控：独立上下文挡污染、独立白名单挡跑偏、独立预算挡连坐
- **审批为什么只发生在派发那一刻**：用户批得懂「派两个人去干这两件事」，批不懂子 Agent 的第七次 `edit_file`
- 为什么 `dispatch_agents` 自己**永远不许进子 Agent 的白名单**（派发树一旦能递归，预算与取消都失控）
- 工作树隔离的语义：派单时拍基线、干活只在自己那间屋、回收时拿「基线 → 现在」的差异
- 真实 `git worktree` 与本实验那份复制版的差别，以及真实实现的四条命令
- 合并必须做**三方比较**：不然就是「后写的赢」，而且屏幕上不会有任何提示
- 主工作区**自己也会漂移**：子 Agent 干活那几秒里用户存了一次盘，落盘就会无声覆盖
- 结构化回执该带哪些字段，以及为什么冲突要写在最前面
- 并行的成本：token 是实打实翻倍的，而主会话**一个都看不到**

## 关于「工作树」：这里是简化版，不是真的 git worktree

本课的沙盒仓库 `work/repo` **不在 git 里**（`seed.ts` 是冻结文件，全课不改），
所以这个实验用的是「复制一份目录 + 记下派单那一刻的内容」来模拟工作树隔离。
真实实现该跑的是这四条命令：

```bash
git worktree add --detach ../.mca/agents/<id> HEAD   # 开一间工位
# ...子 Agent 在那个目录里干活...
git -C ../.mca/agents/<id> diff HEAD                 # 收它的产物
git worktree remove --force ../.mca/agents/<id>      # 收摊
```

真实 worktree 比复制强在三点：**共享同一个对象库**（开一间工位是常数级开销，不随仓库大小线性增长）、
每间工位有自己的 HEAD 与索引（子 Agent 可以正常 commit 与切分支）、
以及**合并与冲突判定可以直接交给 git 的三方合并**，不用像 `merge.ts` 那样自己写。

简化版做不到的三件事也要知道：不认识重命名、不处理二进制文件、不保留文件权限位。
但两者**共享同一套语义**（派单时拍基线、只在自己屋里干活、回收时拿差异），
所以本实验讲的那套冲突规则换成真 git 一样成立。

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：一句话拆成两张派单，两个子 Agent 各改各的文件，合并回来
rm -rf work
printf '把 divide 的除零保护和 README 的说明分头做了\ny\n/agents\n/exit\n' | MCP=off MOCK=1 pnpm start

# 主现象二：两个子 Agent 改同一个文件改成了不同版本 → 报冲突，一份都不落盘
rm -rf work
printf '两种做法你都试一下：抛错和返回 null\ny\n/exit\n' | MCP=off MOCK=1 pnpm start

# 主现象三：跑完主现象一之后看账。子 Agent 花掉的 token 主会话一个都看不到
rm -rf work
printf '把 divide 的除零保护和 README 的说明分头做了\ny\n/agents\n/exit\n' | MCP=off MOCK=1 pnpm start | tail -12
```

> **哪些数字可复现：** 工具清单、文件内容、合并裁决、冲突条数，以及**全部 token 数**
> （离线估算器，同一台机器上连跑两次完全一样：`calc-guard` 约 398、`doc-writer` 约 363、
> 回灌给主会话的回执 517 字符）。
> **耗时不可复现**：自检第四项断言的是时间区间的**关系**——两段区间重叠、
> 并行墙上时间小于两者相加——不是具体毫秒数，所以慢机器上一样成立；
> 屏幕上打出来的那几个毫秒数只能看相对关系，不要当基准。
> 今天**不需要网络、不占任何端口**（加 `MCP=off` 是为了不去起 D15 那个演示 server）。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 常见坑

- **不要让子 Agent 继承主会话的消息数组。** 它一进去就带上了一堆与这张派单无关的历史，窗口被占掉不说，它还会去追问「你刚才说的那个文件」——而那个上下文对它并不存在。子 Agent 的消息数组只该有两条：一份**为它单独写的**系统提示，和一张派单。
- **系统提示也不要继承。** 主会话那份里写满了只对主会话成立的事：对话可能被压缩过、用户会用 `@` 贴资料、有技能会自动出现、可以用 `ask_user` 提问。子 Agent 一条都不适用，继承过去的后果是它会去等一件永远不会发生的事。
- **白名单里必须硬挡掉派发工具自己。** 允许子 Agent 再派子 Agent，派发树就没有边界了：预算算不出来、取消信号传不下去、出了事你也说不清是第几层那个在改文件。要多层就显式做成多层，不要靠递归默认发生。
- **白名单里写错的工具名要报出来，不要静默忽略。** 静默的表现是「这个子 Agent 什么也没干成」，而原因藏在一个拼错的工具名里，从回执上完全看不出来。
- **不要在子 Agent 内部逐次审批。** 用户批得懂「派两个人去干这两件事，它们只能读和改文件」，批不懂第七次 `edit_file`——他**看不到子 Agent 的上下文**，那种审批只是走过场。授权在派发那一刻一次性给过，边界由白名单承担。
- **不要让子 Agent 共用预算。** 一个打转的子 Agent 会把整次任务的额度烧光，而派它出去的那个会话毫不知情，表现是「另一件事莫名其妙没做完」。
- **不要按顺序把每个人的改动写回去。** 那等于**后写的赢**：两份回执都写着「已完成」，主工作区里却只剩一份改动，而且屏幕上没有任何提示。这是并行 Agent 最典型的一种静默数据丢失。合并必须做三方比较。
- **两个人改成了相同内容不算冲突。** 同一件事做了两遍，落盘一次就行。把它也报成冲突会让冲突这条信号变得廉价，人很快就不看了。
- **基线要在派单那一刻取，不能等回收时拿主工作区去比。** 子 Agent 干活的这几秒里主工作区可能已经被别人动过，拿一个变了的现场当基线，算出来的差异里会混进不是它改的东西。
- **别忘了主工作区自己也会漂移。** 用户在编辑器里存了一次盘，基线就不再等于现状，这时候落盘会无声覆盖掉他刚写的东西。落盘前必须再比一次。
- **回执不是转录。** 回灌给主会话的必须是「干了什么、结果如何、花了多少」，不是「它一路上说了些什么」。把子 Agent 的对话原样搬回主会话，等于把你刚刚省下来的窗口又还回去。
- **`rm -rf` 一个由参数拼出来的路径之前，先确认它落在自己的目录里。** `removeWorktree` 里那行前置判断只有一行，漏掉的代价是删掉别人的仓库。
- **不是所有活儿都该并行。** 有先后依赖的（先改接口再改调用方）、要改同一批文件的（必冲突）、以及一步就能做完的（派一次的固定成本比自己顺手做完还高），这三类派出去只会更慢更贵。判据写进系统提示里，别指望模型自己悟。
