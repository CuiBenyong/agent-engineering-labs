# D5 实验：一道能配置、能记住选择、拒绝后模型会改道的审批门

> 目标：给昨天那些会改东西的工具装一道门。三态规则（allow / ask / deny）按工具名与路径模式匹配，
> 只读工具直接放行，写工具停下来问一句，被拒绝的调用变成一条工具结果回灌给模型让它改道。
> 现象最好看的一条：模型想「改测试让它变绿」，被 deny 挡住，于是转头去改被测代码。

## 你会学到

- 实现规则表与匹配函数，支持工具名与路径模式两类条件
- 把审批插进工具执行链路，只读工具跳过、写工具与命令暂停等输入
- 实现三种记忆范围的选择，并在终端里显示这次为什么需要审批
- 让被拒绝的调用变成一条工具结果回灌，观察模型改走只读路径
- 自检里覆盖放行、询问后同意、询问后拒绝三条分支

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 交互着看：第二行的 y 是回答审批提示（a 本会话都可以 / w 写进配置 / n 不行）
printf '帮我修一下失败的测试\ny\n/permissions\n/exit\n' | MOCK=1 pnpm start

# 同一句话，这次拒绝：文件不会被改，模型会收到拒绝原因
printf '帮我修一下失败的测试\nn\n/exit\n' | MOCK=1 pnpm start

# 看被 deny 之后它改走只读路径
printf '把锁文件改一下\n/exit\n' | MOCK=1 pnpm start
```

> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `9/9 通过`
- [ ] 三个只读工具一次都不触发审批；写工具与命令工具按规则走 allow / ask / deny 三条分支
- [ ] 模型改测试文件被 deny 挡住，回灌里带着「测试是验收标准」，随后它自己改去改被测代码
- [ ] 审批提示里写着「为什么问你」，回答 `y` 后改动生效、测试变绿；回答 `n` 后文件一个字节都没动
- [ ] `y` 只在本轮有效、`a` 在本会话内不再问、`w` 会把规则写进 `work/permissions.json`

## 常见坑

- **写操作没有规则命中时，默认必须是 ask，不是 allow。** 默认放行的门等于没有门，而且这个错误只会在出事那天暴露。
- **没有提问渠道时也要按拒绝处理。** 在 CI、管道、别的 Agent 的 shell 里没人能回答，此时自动同意等于把最危险的场景变成全自动。
- **看不懂的回答按拒绝处理。** 用户敲了个回车、敲了句「好的」、或者输入直接 EOF，都不能算同意。
- **审批是暂停不是异常。** 门只有两种返回：放行，或者一条工具结果。被拒的调用在消息数组里和「工具执行失败」长得一样，模型会像处理任何失败那样改道。实现成抛异常，你就得在循环外面接住它、决定要不要继续这一轮、还要补一条工具结果消息（否则下一轮请求不合法）——复杂度全堆在错误路径上。
- **规则冲突不要靠顺序，靠具体度。** 「更具体的赢，同具体度更严格的赢」这条口径让规则表可以随便追加；靠顺序的话，你加一条更具体的规则却被上面某条吃掉，排查起来很痛苦。
- **嵌套提问会和 readline 的异步迭代器抢输入。** 一轮跑到一半要停下来问一句，如果在 `for await (const line of rl)` 里再读一行，两个消费者会抢同一批 `line` 事件。本天把输入换成一个行队列：主循环与审批提示轮流从队列里取行，谁在等谁拿到。
- **拒绝原因要写成模型能改道的样子。** 「permission denied」只会让它原地重试同一个调用；「测试是验收标准，请改被测代码」才会让它换一条路。
