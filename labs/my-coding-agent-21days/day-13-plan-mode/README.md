# D13 实验：一个提问工具、一个只读探索模式与一套计划审批后执行的流程

> 目标：让 Agent 在动手之前把话说清楚。今天做三件事：一个让模型**结构化反问**的工具
> （带选项、默认值、多选，终端渲染成可选列表）；一个**只读探索模式**——它不是新的权限
> 系统，只是第五天那张规则表的一个预设；一套**计划审批**流程——模型交一份写明「改哪些
> 文件、怎么验证、有什么风险」的计划，用户批准之后才切回可写模式，而批准的授权范围
> 只有计划里列出的那几个文件。
> 现象最好看的一条：同一份计划走两条支线，批准那条核对表全是勾；不批准那条，
> 接下来每一次写入都被同一句话挡回来，`src/calc.js` 一个字节都没动。

## 你会学到

- 为什么反问要做成一个**工具**，而不是让模型在正文里问一句（三条理由，第三条最实在）
- 结构化提问的参数表怎么写：选项、默认值、多选，以及回答的五种形状怎么收
- 只读探索模式怎么用「换一张规则表」实现，而不是在三个地方各判一次「现在是不是计划模式」
- 为什么计划模式连 `node --test` 也不开口子：边界简单才是它的全部价值
- 计划要有哪四个字段才**可核对**，以及为什么不合格的计划要整份退回、不要就地补全
- 计划审批为什么不需要任何新机制：一个非只读工具 + 一条 `ask` 规则，门就自动接住了
- 「批准的是这份计划，不是无限授权」怎么落地：按 `files` 逐个放行，而且**不许越过 deny**
- 执行阶段怎么核对计划与实际改动，以及为什么「没跑验证就宣布成功」也算一种偏离

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象：进探索模式 → 它先问一句（回 1 选「抛错」）→ 命令被挡 → 出计划 → 批准（y）→ 执行 → 核对
printf '/plan\n让 divide 在除数为 0 的时候更安全一点\n1\ny\n/check\n/exit\n' | MOCK=1 pnpm start

# 反过来试一次：同一份计划不批准（n），接下来每次写入都被挡回来，文件一个字节没动
printf '/plan\n让 divide 在除数为 0 的时候更安全一点\n1\nn\n/plan show\n/exit\n' | MOCK=1 pnpm start

# 偏离计划的对照：改完计划里那个文件，又顺手多改一个，而且没跑验证命令
printf '先出个计划，然后顺手把说明也写一下\ny\ny\n/check\n/exit\n' | MOCK=1 pnpm start
```

> **哪些数字可复现：** `MOCK=1 SELFTEST=1 pnpm start` 打印的每一项都可复现（连跑两次
> diff 为空）：回答解析的结果、规则表条数、判定结果、计划解析出的原因条数、六次工具
> 调用的名字与顺序、核对表的三列。**REPL 里那几条管道命令不完全可复现**——
> `run_command` 跑 `node --test` 的输出带毫秒数，token 数会有几十的浮动，看现象不要抄数字。

> 工具调用的**顺序**是离线剧本钉住的。接真模型时顺序会变（它可能不问就直接读代码，
> 也可能读两个文件再出计划），但**每一步该被挡还是该放行不变**——那是规则表决定的，
> 与模型无关。这条区别在读自检输出时要一直记着。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `12/12 通过`
- [ ] 进探索模式那一项打出「规则表从 4 条整体换成 2 条预设」，且 `edit_file` 与 `node --test` 都判 `deny`
- [ ] 端到端那一项打出 `ask_user → run_command → read_file → submit_plan → edit_file → run_command`，其中第二次的 `run_command` 带 `blockedBy=approval`
- [ ] 批准那一项打出「只放行 src/calc.js；test/calc.test.js 本来就 deny，批准不解除它」
- [ ] 核对表两条支线都对：对齐那条三列全绿，偏离那条抓到 `src/notes.md` 不在计划里、验证没跑过
- [ ] 拒绝那条支线：`/plan show` 仍显示「只读探索模式」，`src/calc.js` 里没有 `divide by zero`

## 常见坑

- **别让模型在正文里问问题。** 它说完一句问句之后，循环拿到的 `finish_reason` 是 `stop`，和「我答完了」长得一模一样——程序分不出「这一轮在等人」，用户会以为它卡住了。做成工具之后，答案是一条 `toolCallId` 指回那次提问的消息，绑定是结构上的。
- **提问工具必须给 `options`。** 自由文本的问题永远长成「你想怎么做？」这种没法回答的形状。参数表里放上选项，模型就必须先把「有哪几种做法」想清楚才问得出来——**schema 就是提问的质量下限。**
- **提问渠道靠闭包注入，不要往 `ToolContext` 加字段。** 协议层是冻结的，为一个工具改它意味着二十一天每份 `types.ts` 都得跟着改。工具由工厂函数造出来、渠道在造它的时候闭进去：REPL 那个从行队列读，自检那个按剧本答。D15 的 MCP 工具、D18 的钩子都照这个形状。
- **空回答不等于没答案。** 用户在终端里最常做的动作是直接回车，他心里想的是「按你说的默认那个来」。有 `default` 就取 `default`，没有才算跳过——而跳过也要明确回灌「用户没有回答」，不能装作他选了第一个。
- **序号和选项名都要收。** 人最自然的输入是「2」，而模型认的是它自己给的 `value`。另外不认识的输入要**原样当答案**回灌回去：选项是模型列的，它常常列不全，把「都不是，我要第三种」传回去比逼用户在三个错选项里挑一个有用得多。
- **只读探索模式不是新权限系统。** 它只是把规则表整体换成两条预设。反过来做——加一个 `mode` 字段，然后在循环里、门里、每个写工具里各判一次——你会得到三处可能不一致的判断，而它们不一致的那天表现是「计划模式下它偷偷改了文件」。**权限的判定入口全课只能有一个。**
- **换规则表要整体替换，不能追加。** 第五天的匹配规则是「更具体的赢」，而原表里 `run_command command=node --test*` 那条比无条件的 `deny` 具体得多。追加一条「一律 deny」上去，探索模式下测试照跑，而且没有任何提示。
- **计划模式不给任何命令开口子。** 探索阶段跑测试确实无害，但「哪条命令算只读」是个无法穷举的判断（跑测试会不会写快照？会不会碰缓存目录？）。这个模式的全部价值就在于边界一句话说得清：**只读工具全过，其余全挡。**
- **计划必须可核对，所以四个字段一个都不能省。** 最容易被省的是 `verify`——没有它，Agent 改完就宣布成功，你只能靠人看。最容易被糊弄的是 `files`——「优化一下边界处理」这句话，改一个文件和改五个文件都算符合。
- **计划不合格要整份退回，不要就地补全。** 我们替它补的 `verify` 是我们编的，而审批的意义在于用户批的是**模型自己的**计划。补一条验证方式，等于让用户批准了一份没人负责的计划。
- **格式不合格的计划连问都不要问出去。** 门排在工具执行之前，所以用户看到计划的时候我们还没校验过它。校验要提前到提问那一步（预检），解析不过就当「拒绝」，把问题清单当拒绝理由回灌给模型让它重发。
- **计划审批只给 y / n 两个选项。** 第五天那个 `a`（本会话都可以）与 `w`（写进配置）的含义是「以后同样的操作别问了」，而「以后所有计划都自动批准」正好把计划模式的意义抹掉。
- **批准的是这份计划，不是无限授权。** 批准后按 `files` 逐个文件放行，一个不多。全开等于批准「随便改」；什么都不放行，则用户刚批准了一份写明文件的计划，执行时每个文件还要再问一遍——纯粹的骚扰。
- **按计划放行不能越过 `deny`。** 放行之前先用原规则表判一次，本来就 `deny` 的（比如测试目录）保持 `deny` 并明确告诉模型。否则它只要把 `test/` 写进计划，就能借一次审批绕开一条硬规则——这是本天最值得警惕的一条。
- **偏离要主动核对出来，不能靠肉眼。** 多改一个文件、没跑验证，这两种偏离都不是错误：工具全部成功、循环正常结束、终端一片对勾。静默的失败只能靠主动检查暴露——和第十二天那条压缩探针是同一个道理。
- **只记 `ok` 为真的写入。** 被门挡下的、执行失败的都不算「实际改动」，混进来会让核对表里出现根本没被改过的文件。
- **核对只看这一次执行做了什么，不看代码写得对不对。** 「改动是否正确」由计划里的 `verify` 负责（跑测试），不是核对的活儿。
- **没动过东西的那几轮不要打核对表。** 否则每一轮都会刷一屏「计划里的文件没被改动」，而那句警告在真正需要它的时候就没人看了。
