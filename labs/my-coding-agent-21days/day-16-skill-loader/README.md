# D16 实验：一个带渐进披露与触发判定的技能加载器

> 目标：把可复用的经验做成**技能包**，让它在需要的时候才上桌。今天**不引 js-yaml、
> 不引 gray-matter**，frontmatter 自己按一个明确的子集解析；扫描时只拿名字与用途，
> 命中触发条件时才读全文，附带的脚本**永远不读、只给一条能直接跑的命令行**。
>
> 现象最好看的两条：同一批技能，**没命中的那一轮只花 177 token，而全量加载要 1399**
> （省 87.3%）；以及一句话同时命中三条技能时，两份互相矛盾的 calc 约定
> **只有分数高的那一份上桌**，另一份被挡下并说清是被谁挡的。

## 你会学到

- 技能与工具的分工：为什么技能**不占工具清单的位置**，`createRegistry` 今天一行都没改
- 手写 YAML frontmatter 子集的红线：**看不懂的行要报错，绝不猜**；以及为什么不引完整 YAML
- 为什么 `text.split('---')` 一定会出事——Markdown 正文里 `---` 是合法分隔线
- 渐进披露三个阶段各自的**判据**不同：装了什么 / 这句话命中了什么 / 模型决定要用
- 渐进披露省的是**上下文不是磁盘 IO**：扫描时其实整份文件都读了
- 触发判定的两类误判代价**完全不对称**：过度触发看得见，漏触发没有任何提示
- 英文触发词要按**词边界**匹配，中文只能按子串——为什么这条不能交给技能作者自己选
- 技能冲突的本质是**互相矛盾**而不是重复，以及为什么让作者显式声明领域比指望模型调和靠谱
- 预算这道闸为什么必须**把没装的原因说出来**
- 阶段三的定义：脚本是拿来跑的，不是拿来读给模型听的

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：三个阶段各花多少，以及全量加载作为对照要花多少
rm -rf work
printf '/skills\n/exit\n' | MOCK=1 pnpm start

# 主现象二：一句话同时命中三条技能，两份矛盾的 calc 约定只上桌一份
rm -rf work
printf '按团队约定修一下 src/calc.js 里 divide 的除零问题，再跑一遍测试\ny\ny\n/exit\n' | MOCK=1 pnpm start

# 主现象三：没命中的一轮只花常驻摘要那点 token（省下的大头在这里）
rm -rf work
printf '今天先不干活了，随便聊聊\n/exit\n' | MOCK=1 pnpm start

# 主现象四：显式点名，一句完全不相干的话里也能强制展开
rm -rf work
printf '/skill release-notes\n随便说点什么\n/exit\n' | MOCK=1 pnpm start
```

> **哪些数字可复现：** `MOCK=1 SELFTEST=1 pnpm start` 打印的每一项都可复现（连跑两次
> diff 为空）：字符数、估算 token、命中分数与原因、装了哪条没装哪条、版本号。
> 今天**不需要网络、不占任何端口**（D15 那个演示 server 自检里用不着，所以不起它）。
> 一个口径要先说清：**token 是估算不是真值**——这一天全程离线，没有任何真实 usage
> 可以校准，用的是第十二天那对默认系数。同一台机器上算出来的数是确定的，
> 但它不等于任何一家模型的真实分词结果。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 常见坑

- **不要用 `text.split('---')` 切 frontmatter。** Markdown 正文里 `---` 是合法的分隔线，稍长一点的文档就会有一条，按分隔符切会把正文切碎，表现是「技能全文莫名其妙少了一半」。按行扫描，只认第一行与其后第一条单独成行的 `---`。
- **不要引完整 YAML 解析器来省事。** 完整 YAML 的表达力远超技能元信息需要的那一点点，多出来的全是风险面：锚点、合并键、隐式类型转换（著名的 `no` 会被解析成布尔假）。实现一个明确的子集，**看不懂的行报错而不是猜**——猜的代价是作者写错了却没人告诉他。
- **缺必需字段要跳过并说清原因，不要静默跳过、也不要抛到最外面。** 静默跳过的后果是作者以为自己写好了；抛到最外面的后果是一个技能包写坏了整个 mca 起不来。这和第十五天对掉线 server 的处理是同一条。
- **别把「省 token」和「省 IO」搞混。** 扫描阶段其实整份 SKILL.md 都从磁盘读出来了，因为要拿 frontmatter 就得读文件头。渐进披露省的是**上下文**：读一份本地文件是微秒级的，而把同样这段文字塞进每一次请求，要按 token 一次次付钱、还要占掉窗口。
- **阶段二注入的消息角色写 `user` 不写 `system`。** 它是本轮的**资料**不是长期规则，写成 `system` 的话后面每一轮都会被当成同等权重的指令，而它明明只对这一句话有效。
- **别把 `priority` 用来决定「有没有命中」。** 它只该用来打破平局。让它参与命中判断的话，一个 `priority` 很高的技能会在一句完全不相干的话里上桌。
- **英文触发词必须按词边界匹配。** 不加词边界的话，一个 `test` 会被 `latest`、`contest` 命中，这是误报最主要的来源。中文只能按子串——没有空格分词，词边界无从谈起。这条分界**不能交给技能作者自己选**：他写触发词时想的是「我这个技能是干嘛的」，不是「这个词会不会出现在别的句子里」。
- **过度触发与漏触发的代价不对称，判定的默认姿态应该是宁可多上一张。** 过度触发花掉一点上下文，而且注入报账里看得见；漏触发时模型按通用知识回答，答得像模像样，**而没有任何东西提示你有一份约定没被读到**。真正的刹车放在预算那一层，不是放在判定那一层。
- **同时命中的两条如果互相矛盾，不要都装。** 技能冲突的本质不是重复而是矛盾：一份说除零抛错、一份说返回 Infinity，同时上桌的结果不是模型知道得更多，而是**它随机挑一份，而且你看不出它挑了哪份**。让作者用领域字段显式声明互斥，比指望模型自己调和靠谱得多。
- **预算挡下来的那一条必须把原因说出来。** 静默丢弃会让人以为技能写错了，实际是预算没给够——这两件事的修法完全相反。
- **附件脚本只给命令行，不给路径、更不给内容。** 只给路径的话模型多半会先 `read_file` 把脚本读一遍，那就等于把阶段三又退化回阶段二；给了内容它还可能「读懂之后自己照着写一遍」，那比直接跑它糟得多。
- **扫描要在建会话之前。** 阶段一摘要是拼进系统提示的，而系统提示在 `newSession` 里一次性写进消息数组——扫晚了摘要就进不去，模型从头到尾不知道有技能可用，**而且不会有任何东西报错**。这和第十五天「挂载要在建会话之前」是同一个形状的坑。
- **显式点名只对下一轮有效。** 常驻的东西已经由阶段一负责了，点名如果不清就变成了「悄悄多出来的常驻成本」。
