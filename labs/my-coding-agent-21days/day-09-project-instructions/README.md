# D9 实验：三层指令文件的加载与合并链路，以及一条能打印来源与优先级的命令

> 目标：让 `mca` 一进仓库就知道规矩。实现用户级 / 项目级 / 目录级三层 `AGENTS.md` 的发现与加载，
> 支持文件之间的 `@import`（带循环检测、深度上限与根边界），按「越具体越靠后、冲突时后者赢」
> 合并成 system prompt，并用一条 `/context` 命令把每一段来自哪个文件、多大、谁覆盖了谁打出来。
> 现象最好看的一条：三层都写了「测试命令」，而模型真的执行了**最具体那一层**的那条——
> 判据不是它嘴上说什么，是 `run_command` 的参数值。

## 你会学到

- 实现三层指令文件的发现：用户主目录、仓库根（靠标记文件往上找）、当前目录往上溯
- 按 `realpath` 去重，让软链接指向同一个文件时只加载一次
- 实现 `@import` 展开，并想清楚循环检测（看导入链）与重复导入（看导入过没有）的区别
- 定义可解释的合并顺序：基座在最前、越具体越靠后，冲突时后者赢且被覆盖的行真的删掉
- 用一条命令让常驻上下文变得可查：段数、来源、字符数、估算 token、占预算比例、冲突表

## 三层指令文件在哪

本实验把两个「边界」都做成环境变量，默认值都落在 `work/` 里面——**一个字节都不会写到真实的用户主目录**：

| 变量        | 默认值          | 是什么                                                               |
| ----------- | --------------- | -------------------------------------------------------------------- |
| `MCA_HOME`  | `work/home`     | 模拟用户主目录。生产实现里换成 `os.homedir()`，发现逻辑一行都不用改  |
| `MCA_START` | `work/repo/src` | 模拟「在哪个目录启动 mca」。默认在子目录里，这样目录级那一层才看得见 |

加载出来是这四段（`/context` 会原样打出来）：

```text

  1  基座    内置基座  426 字符 · 约 341 token
  2  用户级  work/home/AGENTS.md  37 字符 · 约 30 token
  3  项目级  work/repo/AGENTS.md  119 字符 · 约 79 token（含导入 2 个文件：work/repo/.mca/assert.md、work/repo/.mca/testing.md）
  4  目录级  work/repo/src/AGENTS.md  117 字符 · 约 68 token
```

上面这些数字在 `MOCK=1` 下是可复现的（字符数、token 估算、段数、冲突条数都只取决于文件内容）；
会话 id 与耗时不可复现。

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象：三层冲突之后，它执行的是最具体那一层的测试命令（y 是给审批门的回答）
printf '跑一下测试\ny\n/exit\n' | MOCK=1 pnpm start

# 只想看 system prompt 是怎么拼出来的
printf '/context\n/exit\n' | MOCK=1 pnpm start

# 改一条目录级指令，再 --resume 接上老会话：生效的是新规矩
printf '跑一下测试\nn\n/exit\n' | MOCK=1 pnpm start
echo '- 提交前：先跑一次 node --test' >> work/repo/src/AGENTS.md
printf '/context\n/exit\n' | MOCK=1 pnpm start -- --resume
```

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 常见坑

- **不要读写真实的用户主目录。** lab 里用 `MCA_HOME` 模拟，生产实现换成 `os.homedir()`。真实主目录里可能已经有别的工具的同名文件，往里写东西更是不可接受。
- **仓库根靠标记文件往上找，不要猜层数。** 标记是 `.git` 或 `package.json`，找到第一个就停；一路上溯到文件系统根的话，用户在 `/tmp` 里跑一次你就会去读 `/AGENTS.md`。
- **按 `realpath` 去重。** 把项目级指令软链到子目录是很常见的做法，不去重它会在 prompt 里出现两遍，既花钱又让模型在两份「同样权威」的副本之间无所适从。
- **循环检测看的是「导入链」，不是「导入过没有」。** 只用一个 `seen` 集合，菱形导入（A 同时导入 B 与 C，两者都导入 D）会被误报成循环。链要在退出一层时弹出，`seen` 永不弹出——两个集合各管一件事。
- **深度上限要有，而且不要太大。** 三层足够；再深说明作者该重构文件，而不是你该支持它。
- **导入路径必须落在允许的根里面**，判据是解析成绝对路径之后再比前缀。而且用户级文件只能导入主目录里的东西：一个仓库的指令文件不该能把用户主目录里的文件拉进来。
- **坏一行不许让整份指令失效。** 出问题的那一行换成一句括号说明留在原地，其余内容照常生效；但问题必须显式报出来——它的表现是「模型莫名其妙不听话」，用户手里没有任何东西可查。
- **基座放在最前面，别为了「让模型先看到」把项目指令提到最上面。** 两个代价：规则（越靠后越具体）和实现自相矛盾；prompt 的前缀每一轮都在变，缓存无从命中。
- **冲突要真的消解，不能只记录。** 两条矛盾的规矩同时留在 prompt 里，你不知道模型挑了哪一条，而 `/context` 打的却是「后者赢」——报告和实际发出去的东西不一致，比没有报告更糟。
- **规矩不属于历史。** `--resume` 恢复的是「说过的话」，指令文件是「现在的规矩」：恢复时要用当下重新加载的那一段 system prompt，否则同一个仓库里两条会话会按两套规矩干活。
- **指令预算不含基座。** 基座是我们自己写死的固定成本，把它算进「用户还能不能多写两行规矩」这笔账里，那个百分比就看不懂了。超预算时从**最不具体**的那一层开始截断，一层都不许整条丢。
- **指令别当文档写。** 引用是一次性的，指令是常驻的：一段两千字符的项目指令，二十轮对话就重发了二十遍。单个指令文件在本实验有 32 KB 的硬上限，超了直接不加载并说明原因。
- **文件到了上限就拆。** `repl.ts` 加完今天的东西刚好贴到 350 行（本课的单文件上限），所以行队列、取消按键判定与审批提问被搬到了 `input.ts`——它们是纯函数与一个小数据结构，可以被自检直接断言；输入循环是控制流，只能靠管道跑。两层混在一个文件里，不会因为「都是输入相关的东西」而变得好读。
- **总预算怎么在各路之间分配不是今天的题目**（那是第十二天）。今天沿用第八天那条纪律：每一路注入都要自己报账。
