# D12 实验：一套带估算校准、可触发、可验证的上下文压缩机制与手动压缩命令

> 目标：上下文总会满，而满了之后的现象很难看——报错超限、答得越来越离谱、或者干脆
> 把最要紧的那条事实挤了出去。今天先用网关回传的真实用量校准一个本地 token 估算器，
> 再实现分段摘要式压缩，明确哪几类消息必须原样保留，最后用一组回答早期事实的探针
> 验证压缩没有丢掉关键信息。
> 现象最好看的一条：同一段长会话，摘要式压缩之后早期那条事实还在，
> 换成「只留最近几组」的截断式压缩，它就没了——**而两者省下的 token 差不多**。

## 你会学到

- 实现一个两系数的 token 估算器，并用 usage 回传的真实用量做一次最小二乘回归校准它
- 说清估算与精确计数各自的适用场景，以及样本比例单一时为什么必须承认「解不出来」
- 按比例而不是按轮数判定触发，并知道为什么七成就要压、不能等到九成
- 写出一份明确的保留清单（系统指令、钉住的清单、未完成的工具调用、最近几组）
- 让模型写**结构化**摘要，以及摘要不合格时整次放弃、上下文一个字都不动
- 用探针验证压缩没丢关键信息，并知道探针的判据是「上下文里还有没有」而不是「模型答得对不对」
- 把七路占用汇总成一张总预算表：这是全课唯一讨论「总预算怎么分」的地方

```bash
# 反过来试一次：不说那条事实就直接压，第一条探针会变成 ✘
printf '解释一下 @src/calc.js 里的 divide 哪里有问题\n跑一下测试看哪个用例失败\n/compact\n/exit\n' | MOCK=1 pnpm start

printf '解释一下 @src/calc.js 里的 divide 哪里有问题\n/budget\n/tokens\n/exit\n' | MOCK=1 pnpm start
```

> **哪些数字可复现：** `MOCK=1 SELFTEST=1 pnpm start` 打印的每一个数字都可复现
> （连跑两次 diff 为空）：估算值、校准系数与误差、压缩前后的消息数与 token 数、
> 分段数、探针结果。**REPL 里跑真实命令的那几轮不完全可复现**——`run_command`
> 执行 `node --test` 的输出里带毫秒数，token 数会有几十的浮动，看趋势不要抄数字。

> **离线下的「真实用量」来自剧本**（按字符数折算），所以自检里校准后的误差会掉到很小。
> 接真网关时这段代码一行都不用改，但回归出来的是另一对系数，误差也不会归零——
> 真实分词不是字符数的线性函数，估算永远只是估算。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `15/15 通过`
- [ ] 校准那一项打出「系数 中日韩 0.50 / 其余 0.51，误差 55.6% → 2.6%」这种一行，且全是纯 ASCII 的样本被判为「两个系数分不开」
- [ ] 触发判定按比例：同样 14 条消息、同样的轮数，长的（1368 token）触发、短的（176 token）不触发
- [ ] 压缩之后 14 条消息变 7 条、估算 1368 → 571 token，两段摘要都带齐四个小标题，且没有对不上调用的工具结果
- [ ] 两条探针在压缩后的上下文里都还找得到；换成 `dropOldest` 的截断式压缩，`pnpm build:calc` 那条事实就丢了
- [ ] 摘要没按四个小标题写时整次放弃，上下文一个字节都没动

## 常见坑

- **不要引 tokenizer 包。** 精确计数只能靠模型自己那套分词表，而这门课要连的是任意一个 OpenAI 兼容网关，后面可能是任何一家的任何一个模型——分词表根本不唯一。引一个包只会给你一种精确的错觉：算得很准，但算的是别人的分词。要精确就用你所用网关/模型官方的分词器或计数接口，不要在这里猜。
- **系数要回归，不要拍。** usage 里的 `prompt_tokens` 就是「这段文本真实是多少 token」，把若干条（文本, 真实值）当样本解一次最小二乘就有了。样本从每一轮请求顺路收，**不要为了校准额外发请求**——那要花钱，而且测的是另一段文本。
- **行列式接近 0 必须承认解不出来。** 样本全是纯英文时，两个系数分不开，硬解常常给出一正一负的荒唐系数，比不校准更糟。判「接近 0」要用相对判据，样本一多绝对值本身就很大。
- **一轮里只能取第一条 usage 当样本。** 文本快照是发起这一轮之前取的，而第二轮的输入已经多了助手消息与工具结果，配不上同一段文本。
- **按比例触发，不要按轮数。** 一次 grep 命中两千行，一轮就能吃掉半个窗口；而十轮「改一行、跑一次测试」可能还不到一成。按轮数压，短对话被压得太早、长结果被压得太晚。
- **触发线不要留到九成。** 压缩自己也要占地方：摘要请求要把旧上下文再发一遍，摘要写出来也要占位置。九成才压，很可能压缩这一次请求自己就超了。
- **保留清单是白名单，不是黑名单。** 先说清「哪几类必须原样留下」，剩下的才可以压。反过来列举「哪些可以压」，迟早会漏掉一类新出现的消息，而漏掉的后果是静默丢信息。
- **带工具调用的助手消息与它的工具结果是一个不可分割的整体。** 拆开会得到「请求了工具却没有结果」的消息数组，下一轮请求直接不合法。这条和第七天的分叉规则是同一条。
- **工具结果少于工具调用的那一组必须原样保留。** 那是上一轮被打断或出错留下的，模型需要的是补上那条结果，而不是从摘要里知道它发生过。
- **最近几组不能压。** 摘要是结论，而模型此刻需要的是原文——刚才那条报错的完整堆栈、刚才读到的那几行代码。压掉最近几组最典型的现象是它开始重复刚做过的事。
- **要结构化摘要，不要自由发挥。** 自由发挥的摘要读起来很顺，但它会把「已经改过 src/calc.js」写成「讨论了如何修复除零问题」——动作变成了话题，下一轮它就不知道自己已经动过手了。
- **摘要不合格就整次放弃。** 压坏的上下文比没压的上下文糟得多，而且不可逆：原文已经不在数组里了。所以先把全部段落的摘要都拿到手，再一次性重建数组。
- **压的是旧上下文，不是这一句。** 顺序反了，用户刚用 `@` 贴进来的资料会被立刻压成摘要，那是最没道理的一种压缩。
- **探针的判据是「事实还在不在上下文里」，不是「模型答得对不对」。** 模型答对可能是猜对的，答错也可能是这一轮的运气；而上下文里有没有那句话是确定的、可复现的，也是压缩这一步唯一能负责的事。
- **系统提示里要说明「历史可能被压缩过」。** 少了这句，模型会把摘要当成用户刚说的话，或者反复问「你刚才说的那个文件是哪个」。
- **估算器全课只能有一个。** 第八天那个粗估算搬进了 `context/tokens.ts`，校准结果是进程级的一份表——否则同一段文本会在引用报账那行报一个数、在压缩判定那里报另一个数，用户没法对账。
