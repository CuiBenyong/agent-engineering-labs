# D11 实验：一个文件式的记忆目录，两条写入路径、三个检索判据、三类拦截

> 目标：让 `mca` 记住这个仓库的坑。一条记忆一个文件，带写下时间、来源、关键词、路径与一个
> 可核对的锚点；用户用 `/remember` 显式写，模型用 `remember` 工具自动沉淀；每一轮按当前这句话
> 检索，**只把最相关的几条放进一个可替换的槽位**，并把命中原因打在终端上；密钥、临时结论、
> 代码里已经写着的事三类内容在写入那一层就被挡住。
> 现象最好看的两条：**两条互不相干的会话，第一条记下的事实自己回到了第二条的请求里**；
> 模型想把一个 key 记进记忆，被拒绝、读到理由，下一轮自己改成记住那个环境变量名。

## 你会学到

- 记忆、会话日志、指令文件的分工：一个记事实、一个记过程、一个是规定，混在一起会怎样
- 一条记忆一个文件的四条工程理由，以及它的代价（几百条之后要靠什么活下去）
- 两条写入路径为什么必须汇到同一个函数——少写一处，那一处漏掉的就是密钥
- 检索的三个判据（路径 / 关键词 / 来源加权）与两个上限，以及「0 分不注入」这一行的分量
- 常驻注入与一次性注入的结构差别：**记忆是一个原地替换的槽位，不是每轮追加一条**
- 记忆会过期：用锚点做「用之前先核对」，失效的拿下来等人处理而不是自动删

## 记忆文件长什么样

`work/memory/m1.md`，「几行元信息 + 一个空行 + 正文」，故意不引 YAML 库：

```text
id: m1
source: model
at: 2026-09-07T00:00:00.000Z
keys: 测试, 验证, node, --test
paths: package.json, test
anchor-path: package.json
anchor-contains: node --test

这个仓库的测试只能用 node --test 跑，脚本里那条是给 CI 用的，本地直接跑会少载一个用例
```

`source` 与 `at` 是今天最便宜也最值钱的两个字段：出问题时你要能回答「这条错的事实是谁写进来的、
什么时候写的」。`anchor-*` 是这条记忆将来能被**自动核对**的唯一依据。

终端上的注入报账（`MOCK=1` 下条数、分数、字符数都可复现，只取决于剧本与阈值；写下时间与会话 id 不可复现）：

```text
记忆注入 1/1 条（共 146 字符、约 124 token，占记忆预算 12%；一次最多 3 条）
  ✔ [m1] 这个仓库的测试只能用 node --test 跑，脚本里那条是给 C
      命中 3 分：关键词 测试、用户写下
```

一条都不相关的时候它只说一句 `记忆 1 条，这句话一条都没命中，没有注入。`——
**这一行比注入本身重要**：它证明「没注入」是判断的结果，不是功能坏了。

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：显式写一条，紧接着问一个相关的问题，它自己回到上下文里（y 是给审批门的回答）
printf '/remember 这个仓库的测试只能用 node --test 跑，脚本里那条是给 CI 用的\n测试要怎么跑\ny\n/memory\n/exit\n' | MOCK=1 pnpm start

# 主现象二：模型自己沉淀一条（带关键词与锚点），然后 /memory 看核对状态
printf '记一下：这个仓库的测试怪在哪\ny\n/memory\n/exit\n' | MOCK=1 pnpm start

# 主现象三：密钥被拦，模型读到理由后改成记住环境变量名
printf '把我的 key 记下来\ny\ny\n/memory\n/exit\n' | MOCK=1 pnpm start

# 检索判据自己试：/memory 加一句话只算不改，不动当前会话的上下文
printf '/remember 这个仓库的 divide 用例一直没人修\n/memory divide 那个用例\n/memory 帮我看看排版\n/exit\n' | MOCK=1 pnpm start
```

> 跨会话那一幕在管道里不好演（一条管道就是一个进程一条会话），所以它由自检负责：
> 第 15 项在会话一里让模型记下一条，第 16 项**开一条历史只有一条 system 消息的新会话**，
> 问一句相关的话，断言那条事实进了这一轮的请求。想手动看，跑两次 `MOCK=1 pnpm start`
> 就行——`work/memory/` 在进程之间是共享的，第二次启动时那些文件还在。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `17/17 通过`
- [ ] 显式 `/remember` 与模型的 `remember` 工具各能写一条，`/memory` 里看得出来源不同
- [ ] 相关的一句话命中并打印命中原因与分数；无关的一句话一条都不注入，且明确说「没命中」
- [ ] 连着说几轮，消息数组里**始终只有一条**记忆消息，位置紧跟 system
- [ ] 密钥被拒绝，拒绝话术里没有原文，`work/memory/` 里搜不到它；模型下一轮自己改成记变量名
- [ ] 锚点失效的记忆不注入、只列在「待核对」里；没有锚点又很旧的照样注入但带一句「先核对」

## 常见坑

- **两条写入路径必须汇到同一个 `write`。** 拦截、去重、写盘都只写一遍。少写一处，那一处就是漏洞——而这里漏掉的是密钥。这和第十天「校验放数据模型不放工具」是同一条纪律。
- **拒绝话术里绝不回显被拦下的密钥。** 把它抄进错误信息，等于把它写进了另一份日志（终端 scrollback、会话日志、CI 输出）。而且只说「不能记」是没尽到责任的：**那个凭据已经出现在这次输入里了，要提醒用户去轮换。**
- **本实验的脱敏只覆盖记忆这一路。** 模型请求的那张工具卡片（D4）与审批提示还是会把它要记的东西原样回显在终端上，所以密钥仍然会在屏幕上闪一次。真要连回显都不显示，得在渲染层再做一次脱敏——那是另一件事，但你应该知道这条边界在哪，而不是以为拦住写入就万事大吉。
- **「代码里已经写着」这条闸的长度下限必须给得比直觉大。** 给 4 的时候「测试只能用 node --test」会被 `test` 命中 `package.json` 而误杀，因为 `test` 在任何一个 `package.json` 里都出现。给 8 之后命中的只能是标识符、命令、路径这类一眼就是代码的东西。**而且只在这句话点了某个文件名的时候才去读那个文件**——全仓库搜索的命中率高得离谱，那条闸会变成「什么都不许记」。
- **「临时结论」这条闸一定会误杀，所以拒绝话术必须给出改法。** 「这个仓库现在还在用 CommonJS」其实是条不错的记忆。让用户知道「去掉时间词重写一遍就能记」，他就会改；只说「不许记」，他会直接放弃这个功能。
- **0 分不注入。** 默认是「不注入」而不是「全注入」：一个记了三百条的目录全量注入等于把记忆变成第二份系统提示，而其中两百九十条和这句话毫无关系——它们不只是浪费额度，还会把模型带偏。**宁可漏也不要糊。**
- **关键词计分要有上限。** 少了它，一条 `keys` 写得多的记忆只要撞上七八个词就能压过一条路径精确命中的记忆。那不叫相关，那叫关键词堆砌，而堆砌它的既可能是兜底的抽词器（中文两字组合切出一堆），也可能是模型自己——它会很热心地给十二个关键词。
- **中文关键词要切成相邻两字的组合，并把含虚词的组合丢掉。** 整段留着，用户下次问「怎么跑测试」一个字都对不上；不过滤虚词，`/memory` 里会列出「库的」「只能」这种废词，看起来像个 bug。这是不引分词表能做到的最省的做法，也是它的天花板。
- **记忆是常驻注入，所以它是一个原地替换的槽位，不是每轮追加一条。** 追加式写法看着能跑，十轮之后上下文里有十份记忆，而且前九份还是过时的检索结果。槽位放在开头那几条 system 消息之后：常驻的东西靠前，网关那边才有机会命中缓存（和第九天把内置基座放最前面是同一条理由）。
- **必须用 `splice` 原地改消息数组。** 循环、自检、会话日志持有的是同一个数组引用——第七天的 `replaceHistory` 踩过同一个坑。
- **命中原因要打给用户、不要发给模型。** 记忆是唯一一种「用户没提、却影响了这一轮回答」的上下文；它错了的表现是「模型莫名其妙地坚持一件不成立的事」，而用户手里没有任何东西可查。至于模型，它不需要知道分数——那是给人做决策用的，塞给它只是浪费额度。
- **被拿下来的记忆也要报出来。** 一条锚点失效的记忆悄悄不注入，用户会以为它还在生效，于是下次模型答错时他去查记忆目录——那条记忆明明还在文件里。**静默失效比失效更难查。** 同理，`/forget` 删了个不存在的 id 要说出来。
- **锚点失效不等于这条记忆错了。** 也可能只是文件改了名。所以处理方式是「拿下来等人看」，而不是自动删：**自动删记忆是不可逆的，而判据只是一个 `includes`。**
- **`remember` 不是只读工具**，和第十天的清单工具正好相反。清单是易失的工作面，记忆会留在磁盘上并影响以后每一次会话——一个会改变将来所有会话行为的写操作，正是第五天那道门该管的。判据从来不是「它改的是不是用户的源码」，而是「它会不会造成不可逆的外部影响」。
- **审批提示得说清「将要发生什么」。** `remember` 既不动路径也不跑命令，于是提示只剩一句「需要确认：remember」，用户只能一路按 y。今天给 `input.ts` 加了一层退路：没有 `path` / `command` 就拿参数里第一个字符串字段当摘要。**门的价值不只取决于它多久响一次，还取决于它响的时候说了什么。**
- **记忆目录不进 git。** 它是这台机器上学到的经验，而且可能含有不该共享的东西。要共享的经验应该写进第九天那三层指令文件里，走一次 code review。
- **解析不出来就返回 null，不要「尽量修补」。** 修补出来的记忆是一条你不知道内容的事实，而它会被注入进上下文——比丢掉它糟得多。这和第七天「日志坏行停在坏行之前」是同一条纪律。
- **注入的总预算怎么在各路之间分配不是今天的事**（是第十二天的）。今天只报自己这一路的账：注入了几条、多少字符、约多少 token、占记忆预算百分之几。估算器直接复用第八天 `refs/budget.ts` 里那个，**不要另算一份**——同一段文本在两处报出两个数，用户就没法对账了。
