# D10 实验：一个模型自维护的任务清单工具与实时进度渲染，附停滞检测

> 目标：给长任务装一块看板。实现 `update_todos` 工具（整表替换 + 单项更新两种写法），
> 把清单画在终端底部的固定区域里并且**不和流式文本打架**，用「同时只能有一个进行中」
> 这条硬不变量约束模型一次只做一件事，再借清单的变化在它开始打转时第一时间发现。
> 现象最好看的两条：一轮对话里清单从 `0/3 已完成` 一路走到 `3/3`；
> `INJECT=loop` 时打转检测挡住重复调用，而清单原地不动，把「整件事没进展」摊在你眼前。

## 你会学到

- 设计一个让模型自己维护状态的工具：为什么只留三种状态、为什么要两种写法
- 用一条硬不变量（同时只有一个进行中）代替一句「请专注」的提示词，违规就回灌纠正
- 在终端底部维护一块固定区域：保存 / 恢复光标 + 清到屏幕末尾，正文夹在中间写
- 区分「打转」（有没有重复调用，D6）与「停滞」（有没有进展，今天），以及两级干预
- 想清楚什么任务不该用清单：三步以内的活儿加清单是负担，假警报比不检测更糟

## 清单长什么样

终端底部那块面板（`MOCK=1` 下这些内容是可复现的，只取决于剧本）：

```text
─ 任务清单 2/3 已完成 ─
☑ 跑一次测试，确认哪个用例是红的
☑ 给 divide 补上除零保护
▶ 再跑一次测试，确认全绿  ← 进行中
```

`INJECT=loop` 时看到的是另一幅画面：清单停在 `0/3 已完成`，进行中那一条从头到尾没换过，
而终端上先出现一条打转检测的回灌、再出现一条 `（系统提醒）任务清单已经 3 轮没有变化了…`，
再一轮就停下。**两个机制的分工在这一幕里最清楚：打转检测挡住的是单次调用，
清单说得出的是「你已经三轮没往前走了」。**

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象：三步任务从 0/3 走到 3/3（y 与 a 是给审批门的回答）
printf '帮我修一下失败的测试\ny\na\n/todos\n/exit\n' | MOCK=1 pnpm start

# 违规纠正：一次给两个进行中，被拒之后它自己改对
printf '能不能同时推进前两步\n/todos\n/exit\n' | MOCK=1 pnpm start

# 打转：清单原地不动，两个机制先后响
printf '再看看 calc.js\n/todos\n/exit\n' | INJECT=loop MOCK=1 pnpm start
```

> 面板的固定区域只在**真终端**里成立。管道（上面这几条命令、CI、别的 Agent 的 shell）
> 没有光标可用，会退化成「清单每次变化整块打一遍」——这条退化和第二天的打字机是同一个口径：
> **没有光标就不发光标控制符**，而不是发出去让它变成一串乱码。想看固定区域的效果，
> 直接 `MOCK=1 pnpm start` 然后手打那句话。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `15/15 通过`
- [ ] 一轮对话里清单从 `0/3 已完成` 走到 `3/3`，中途每一次整表替换里 `in_progress` 都不超过一个
- [ ] 一次给两个进行中会被拒绝，回灌里点名是哪两条，而且清单一个字都没改；下一轮模型自己改对
- [ ] 非法状态、不存在的 id 各有一句能照着改的纠正；`update_todos` 是只读工具，不触发审批门
- [ ] `INJECT=loop` 时打转检测挡住重复调用、清单版本号停在 1，停滞提醒出现之后再一轮被停下

## 常见坑

- **状态只留三种。** 多了模型就开始纠结「阻塞」和「待做」的区别——那个纠结要花 token，还会让它把一条卡住的任务标成阻塞然后就此绕过去。三种状态里没有「放弃」的位置，这是故意的：做不了的事要说出来，不是悄悄改个状态。
- **两种写法都要有。** 只给整表替换，模型每改一个状态都要重发整张表（一张十条的清单每次几百个 token），而且它有不小的概率在重发时改错别的条目的文字；只给单项更新，它又没法在中途重新规划。**两种写法覆盖的是两种不同的动作。**
- **「同时只能有一个进行中」要做成硬不变量，不是提示词。** 违规时**整张表都不改**，把「你给了几个、分别是哪几条、请怎么改」回灌回去。纠正话术必须点名是哪几条：只说「不能有多个」，它不知道该改哪一条。
- **校验放在数据模型里，不放在工具里。** 第十三天的计划模式也会写这份清单，它不该再抄一遍校验。
- **清单工具是只读的。** 它不动用户的任何文件，所以不该触发第五天的审批门。每改一条状态都要用户按一次 y，门就成了噪音——用户会一路按同意，于是真正需要审批的写操作也被放过去了。**门的价值取决于它多久响一次。**
- **「写成它已经是的状态」不能算改动。** 否则模型只要反复把同一条写成进行中，版本号就一直在涨，而版本号是停滞检测唯一的进展度量——这等于给了它一个作弊入口。
- **清单是易失的，不落盘。** 它是这一次任务的工作面，不是事实（那是第十一天的记忆）也不是过程（那是第七天的会话日志）。任务结束清单就没有意义了，存下来只会让下一次对话看到一份过期的待办。
- **面板放底部，不要放顶部。** 顶部要算「正文已经滚了多少行」，而正文会自动换行，行数由终端宽度决定——你得知道用户窗口有多宽，还得处理他中途拉窗口。底部只需要知道清单自己有几行，这是唯一一个你真的知道的数字。
- **正文输出必须夹在 hide 与 show 之间。** 做对之后你会发现渲染层一行都不用改：它拿到的仍然只是一个「写字符串」的函数，完全不知道屏幕下方有块面板。这是第二天那层分界的第二次红利。
- **打转与停滞是两件事。** 打转检测（`kernel/repeat.ts`，D6）看「有没有一字不差地重复调用」；停滞检测看「有没有进展」。前者漏掉的正是后者要抓的东西：**每一轮都在做不一样的事，但一件都没做完**——读了 A 又读了 B 又读了 C，参数每次都不同，打转检测一次都不会响，而清单从头到尾一个字没变。这是长任务里最常见的失控形态，因为它看起来一直很忙。
- **停滞检测要有豁免：清单一次都没被写过就不判停滞。** 少了这一条，任何一次不用清单的短对话转到第三轮都会被提醒，而这个假警报比不做检测更糟——用户很快就学会无视它了。
- **干预分两级，先给机会再抬头。** 第一次命中回灌一条提醒让它自己更新清单或说明卡在哪，第二次才停下这一轮。和第六天的打转打断同一条思路。
- **提醒用 user 角色回灌，不要用 assistant。** assistant 消息会被它当成自己说过的话，于是它很可能顺着原来那条思路继续写下去；user 消息才是「有人在催」。**给模型的纠正，角色选错了效果会反过来。**
- **提醒事件复用 `error` 加 `retryable: true`，没有给 `AgentEvent` 加新类型。** 渲染层要知道的只是「循环接下来还会转一圈」，而这正是那一位的语义。为了在屏幕上多打一种前缀去改协议层，不划算——这是第五天「审批不进协议」那条裁定的延续。
- **文件到了上限就拆。** `commands.ts` 加完 `/todos` 是 384 行，超过本课的 350，所以会话构造搬到了 `session-init.ts`：命令表是数据，会话构造是装配，本来就是两层。
