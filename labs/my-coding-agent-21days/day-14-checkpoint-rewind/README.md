# D14 实验：一套快照与回退机制，支持文件与对话分别或一起恢复

> 目标：改坏了要能退回来。今天实现**内容寻址**的文件快照（按内容哈希去重，只存被工具
> 改过的文件，写工具执行前后各拍一张），把它与第七天那条会话事件日志组成**两条独立的
> 时间线**，于是「只回文件 / 只回对话 / 都回 / 都不回」四种组合都能选；最后处理三类
> 真实问题：工作区里有 mca 没记录过的改动、快照之后被外部动过、快照本身的体积。
> 现象最好看的两条：一次任务里连改同一个文件两次会留下四条记录，但对象库里只有三份
> 内容——**第一次的「改之后」就是第二次的「改之前」**；以及 `INJECT=dirty` 时回滚
> 会**先拒绝再提示**，你手写那一段一个字节都不会丢。

## 你会学到

- 内容寻址是什么、为什么它让去重变成白拿的（而且不需要任何一张「谁和谁一样」的表）
- 为什么快照存全文而不存 diff：出事要恢复的时候，最不该有链式依赖
- 为什么写工具执行**前后各拍一张**，以及「改之前」为什么必须挂在 `tool_start` 上
- 基线快照的用处：让「回到什么都还没发生的时候」变成一个真实可达的状态
- 文件时间线与对话时间线为什么必须独立，以及四种回滚组合各自的真实用途
- 回滚为什么是唯一需要「先检查工作区」的动作，以及内容漂移与时间漂移为什么一个拒绝一个警告
- 快照与 git 提交的分工：为什么不能替用户提交，以及真实实现该同时查 `git status` 与快照哈希
- 「都不回」这一支为什么不是空操作——它是预演

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：一次任务连改同一个文件两次 → 四条记录、三份内容（去重肉眼可见）
rm -rf work
printf '修一下失败的测试，再给 divide 补一条注释\ny\n/checkpoints\n/exit\n' | MOCK=1 pnpm start

# 主现象二：先预演再只回文件。回完 divide 的除零保护又没了，而对话一条没少
rm -rf work
printf '修一下失败的测试，再给 divide 补一条注释\ny\n/rewind none 4\n/rewind files 4\n/exit\n' | MOCK=1 pnpm start

# 只回对话：文件改动留着，话头拉回第 2 条（新会话，母会话一个字节没动）
rm -rf work
printf '修一下失败的测试，再给 divide 补一条注释\ny\n/rewind chat 2\n/exit\n' | MOCK=1 pnpm start

# 未记录的改动：INJECT=dirty 在基线之后往 README.md 塞一段你手写的内容 → 回滚先拒绝
rm -rf work
printf '修一下失败的测试，再给 divide 补一条注释\ny\n/rewind files 4\n/exit\n' | MOCK=1 INJECT=dirty pnpm start

# 两条时间线并排看一眼
rm -rf work
printf '修一下失败的测试，再给 divide 补一条注释\ny\n/rewind\n/exit\n' | MOCK=1 pnpm start
```

> **每条命令前面那句 `rm -rf work` 不是可选的。** 快照日志是只追加的，跨进程累积；
> 不清掉的话第二次跑会再拍一批基线，编号全都往后挪，上面那些 `4` 就指不到基线末尾了。
> 真实使用中这种累积是对的（对象库就该跨会话共享），但看现象时它只会让编号变乱。

> **哪些数字可复现：** `MOCK=1 SELFTEST=1 pnpm start` 打印的每一项都可复现（连跑两次
> diff 为空）：对象数、记录条数与 phase 序列、去重后的内容份数、哈希值、四种组合前后的
> 文件内容与消息条数、漂移检出的种类。**记录里的 `ts` 与 `mtimeMs` 不可复现**，
> 所以今天没有任何一项断言去比它们的绝对值——只比「谁比谁新」。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `12/12 通过`
- [ ] 去重那一项：两次 `edit_file` 记了 4 条（`before,after,before,after`），但只有 3 份不同内容
- [ ] 只记被工具改过的文件：一轮任务之后只有 `src/calc.js` 有新快照（读过的、跑过测试的文件都没有）
- [ ] 四种组合各自成立：只回文件时消息条数不变、只回对话时文件内容不变、都回时两边都变、都不回时两边都不变但预演算得出要动什么
- [ ] `INJECT=dirty` 那一项（跑在子进程里）：`README.md` 上检出 1 处 `content` 级漂移、回滚被拒绝、手写内容还在
- [ ] 改了又改回来时只报 `mtime` 级警告，不拦住回滚

## 常见坑

- **不要按顺序编号存快照。** 「一次快照存一份文件，名字是 1、2、3」是最直白的实现，代价是同一段内容被存很多遍：一次 `edit_file` 的「改之后」就是下一次的「改之前」，模型试一条路不成再改回来，第三份还是同一段。内容寻址让去重变成白拿的，**而且不需要任何一张「谁和谁一样」的表——哈希本身就是那张表。**
- **不要存 diff。** 增量最省空间，但它要有基准、基准要有链，链断了整串都恢复不了。而快照的用途恰恰是「出事了要能恢复」，那是最不该有链式依赖的时候。源码文件只有几 KB，这门课的场景里磁盘从来不是瓶颈。
- **哈希只认内容，不认文件名。** 所以对象库自己不知道哪个哈希属于哪个文件，那件事记在快照索引里。这条分工是内容寻址的全部好处所在：存储层去重，索引层记语义。
- **写入对象库要「先写临时文件再改名」。** 写到一半崩掉时，对象库里不能留下一个哈希对不上内容的文件——那种文件比没有更糟，因为回滚会拿它去覆盖。
- **前后各拍一张，不能只拍一张。** 只拍「改之后」，你回不到第一次改之前，而那恰恰是「撤销这次任务」最常要的状态；只拍「改之前」，最后一次改完的样子没人记，回滚会莫名其妙丢掉最新一次改动。
- **「改之前」必须挂在 `tool_start` 上。** 在 `tool_end` 里补拍的话文件已经被改了，读到的「改之前」是假的。生成器在 `yield` 处挂住，所以透明包装拿到 `tool_start` 这一刻循环还没恢复执行，工具也就还没动手——这是那一层能拍到真实「改之前」的全部原因。
- **只给成功的调用拍「改之后」。** 被审批门挡下的、执行失败的调用没有改动任何东西，给它们拍一张会在时间线上留下一个看起来发生过、其实没发生的节点。
- **基线只拍一次，不要每轮重拍。** 重拍会把 Agent 自己的改动记成新基线，于是「工作区里有未记录的改动」这条检查永远查不出东西。
- **两条时间线不要互相引用。** 只要在快照记录里塞一个会话 seq 把两者绑起来，「只回文件不动对话」和「只回对话不动文件」这两种组合就做不出来了。所以 `both` 要两个参数——它们是两条线上的两个位置，一轮对话里可能改了五个文件，也可能一个都没改。**不好用胜过不确定。**
- **回滚要能删文件。** 任务里新建的文件，回到新建之前就该消失。只做「还原内容」的回滚会留下一堆凭空多出来的文件，而那种残留最难查——它看起来像是你自己建的。
- **回滚前必须检查工作区。** 回滚是**唯一一个会主动覆盖用户文件的动作**：`edit_file` 有 `old_string` 必须逐字匹配这条护栏，改不动就失败；而回滚是整文件覆写，它不会失败——它会成功地把你手写那一段冲掉。
- **内容漂移拒绝，时间漂移只警告。** 内容不一致意味着有人在 mca 之外改过它，而那份内容从没进过任何一次快照，回滚会让它永久消失，所以**先拒绝、再告诉用户是哪几个文件、他可以怎么办**。而内容一致只是 mtime 更新（最常见的是改了又改回来），回滚是无害的，拦住用户没有道理。
- **只检查记录过的文件。** 把整个仓库都纳进来，读者第一次跑就会被一堆无关警告淹没，然后学会忽略警告——而那正是要避免的结果。
- **哈希与 mtime 两个都要记。** 哈希回答「内容是什么」，mtime 回答「谁最后碰过它」。内容改了又改回来时哈希一样，只有 mtime 会告诉你这个文件被动过。
- **不要替用户提交 git。** 快照是 mca 自己的账本，放在 `work/snapshots/` 下，跟用户的提交历史没有关系。替他 commit 一次「Agent 改动前的状态」会污染他的历史，而那种污染是他要花时间去 rebase 掉的。本课的沙盒仓库不在 git 里，所以「未提交改动」落成了一条更普适的判据（工作区里有 mca 没记录过的改动）；**真实实现应该两条都查**：`git status --porcelain` 抓编辑器里的改动，快照哈希抓 git 也不知道的（未跟踪文件、被忽略的文件）。
- **「都不回」不是空操作。** 它是预演：打印会被还原的文件与会被截断的对话，什么都不动。回滚既然是唯一会主动覆盖用户文件的动作，就值得给它一个「先看看再决定」的入口。
- **快照日志的坏行处理与第七天一样：停在坏行之前，不跳过、不修补。** 追加写只有一种失败模式——最后一行可能不完整。前面那些行完整可信，坏行之后不存在。
