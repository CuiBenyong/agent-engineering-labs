# 发版流程

## 三件事，顺序固定

1. 先确认 `node --test` 全绿。测试红着发版，等于把已知问题一起发出去。
2. 再升补丁版本号（附件里的脚本会替你改 `package.json`）。
3. 最后写一段发布说明，只写「用户能感知到的变化」，内部重构不写。

顺序不能换：先升版本号再跑测试的话，测试一红你就得再改一次版本号，
而那次改动很容易忘记，于是发出去的包版本号是对的、内容却是上一版。

## 发布说明的格式

一行一条，动词开头，不写实现细节：

```text
- 修复 divide 在除数为 0 时返回 Infinity 而不是报错的问题
```

反例（写了实现细节，用户看不懂也不关心）：

```text
- 在 divide 入口增加 b === 0 的早返回分支
```

## 不要做的事

- 不要手改 `package.json` 里的版本号，手改容易把 `0.0.9` 改成 `0.0.10` 时漏掉进位。
- 不要在发版提交里夹带功能改动：出了问题没法只回滚发版那一步。
- 不要给还没合进主干的东西写发布说明。
