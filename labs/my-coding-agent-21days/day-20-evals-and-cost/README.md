# D20 实验：一个自动判分的基准集与一张能看通过率、轮数、token 与命中率的面板

> 目标：把「这次改完感觉好像好一点」换成一个能重复跑的数。五道题各自带初始状态与
> **可自动判定的终态**，判分器自己跑测试、自己比文件，跑完给出通过率、平均轮数、
> token 与缓存命中率，落盘成 JSON，再由 3120 上的面板读出来。
>
> 现象最好看的两条：第五题 **`already-green` 过程里必然有一次工具失败，终态却是达标的**
> ——按过程判会判它输，按终态判会判它赢；以及**加一句提示词之后，通过率一点没变、
> token 多了约 341（1.2%）**，这一条把「离线 A/B 测得出成本、测不出效果」摆在了脸上。

## 你会学到

- 出一道基准题的四条判据：明确的初始状态、可自动判定的终态、有难度梯度、**必须有负例**
- 判分为什么只能看**终态**不能看过程，以及「模型说它做完了」是最危险的一种判分
- 判分器为什么要**自己跑测试**，而不是借用被测对象的 `run_command`
- 负例题为什么光断言「测试还是红的」不够，必须再加一条逐字节未改动
- 四类指标各自解释什么：通过率是结论，轮数、token、命中率都是解释
- 缓存命中率的分母是**输入 token** 不是总 token，以及 `cachedTokens` 全是 0 时为什么必须报「不可用」
- 成本怎么谈：单价全部由你自己填、默认 0、没配时显示「不可用」而不是 0.00
- 「假 A/B」长什么样：两个变体跑出来一模一样，而且它从不报错
- 抖动为什么必须重复跑才看得见，以及离线下抖动近乎为零**恰恰说明它没在测模型**

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env

# 验收入口：全课二十一天统一用这一条
MOCK=1 SELFTEST=1 pnpm start

# 主现象一：跑一整轮基准集，五道题的通过率、轮数与 token 一次看全
rm -rf work
printf '/eval\n/exit\n' | MOCK=1 pnpm start

# 主现象二：只跑第五题。过程里有一次工具失败，终态达标所以判通过
rm -rf work
printf '/eval --task=already-green\n/exit\n' | MOCK=1 pnpm start

# 主现象三：同一题跑三次看抖动。离线下极差接近 0——这说明它没在测模型
rm -rf work
printf '/eval --task=fix-divide --repeat=3\n/exit\n' | MOCK=1 pnpm start

# 主现象四：面板。起在 3120，页面读的是 /api/runs 那条 JSON
rm -rf work
printf '/eval --task=fix-divide\n/panel\n' | MOCK=1 pnpm start &
sleep 20 && curl -s http://127.0.0.1:3120/api/runs | head -c 400 && kill %1

# 主现象五：把单价填上，成本那一列才有数。这几个数是你自己填的，不是任何一家的报价
rm -rf work
printf '/eval --task=fix-divide\n/exit\n' | \
  MOCK=1 LLM_PRICE_CURRENCY=元 LLM_PRICE_IN=1 LLM_PRICE_OUT=4 LLM_PRICE_CACHED=0.1 pnpm start
```

> **哪些数字可复现：** 通过率（5/5）、每题的轮数（4 / 1 / 4 / 5 / 4）、工具调用次数
> （3 / 0 / 3 / 4 / 3）、每条判据的真假、变体之间的差异方向——这些连跑两次完全一样。
> **token 有大约 0.1% 的抖动**，来源只有一个：回灌给模型的测试输出里带着
> `node --test` 那行 `duration_ms`。合计 token 在 28075–28080（基线）与
> 28415–28420（改过提示词的变体）之间晃，差值稳定在 +340 到 +342。
> **耗时完全不可复现**，所以自检里没有任何一项去比它。
> **缓存命中率在离线下恒为「不可用」**：剧本 provider 的 `cachedTokens` 一直是 0，
> 而 0 有两种可能（真没命中／网关不回传），代码分不出来就不该装作分得出来。
> token 本身还是**估算值**——离线没有真实 usage 可校准，用的是第十二天那对默认系数。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `Ignored build scripts: esbuild`，
> 这不代表安装失败——看 `node_modules` 有没有生成、`pnpm typecheck` 过不过就够了。

## 验收标准

- [ ] `MOCK=1 SELFTEST=1 pnpm start` 打印 `14/14 通过`
- [ ] 判分器那一项：原样仓库红的、手动修好之后绿的（反向确认它不恒真）
- [ ] 负例那一项：`explain-only` 零次工具调用，两个文件逐字节没被动过
- [ ] 终态判分那一项：`already-green` 过程里有工具失败，终态达标所以判通过

## 常见坑

- **判分器最常见的坏法是「恒真」，而它不会报错。** `TODO(1)` 那个版本什么都没跑就说通过，于是通过率永远 100%。所以每一个判分器都要配一条**反向断言**：拿一个应该失败的输入喂给它，看它是不是真的判失败。自检第二项就是干这个的——原样的沙盒仓库必须被判成红的。
- **不要按过程判分。** 同一件事有很多条路都对，按过程判等于把你写基准集那天想到的那条路当成唯一答案。更糟的是过程判分很容易退化成「模型说它做完了就算做完」，而模型几乎从不承认自己没做到，于是通过率永远好看。
- **判分器不要借用被测对象的工具。** 用 `run_command` 去判 `run_command` 改出来的结果，工具层一有 bug（截断把失败摘要切掉了、超时被当成成功），判分会跟着一起错，而且错得看不出来。判分器自己 spawn 一个 `node --test`，只认退出码。
- **没有负例的基准集会奖励一个见什么改什么的 Agent。** 五道题里第二题的正确行为是**什么都不改**。而这道题光断言「测试还是红的」不够：模型可能把测试文件删了、把 `calc.js` 改坏了，测试照样红。必须再加一条「这两个文件逐字节没被动过」。
- **每一次尝试都要从 seed 重新开始。** 上一题留下的文件改动或对话历史会让这一题的结果无法解释，而基准集最要紧的性质就是「同样的输入给出同样的结果」。
- **缓存命中率的分母是输入 token，不是总 token。** 缓存只对输入生效，拿总量当分母会得到一个永远偏小、而且随输出长短乱晃的数。
- **`cachedTokens` 全是 0 有两种可能**：真的一次没命中，或者你所用的网关根本不回传这个字段。代码分不清这两件事，所以报「不可用」并写清原因，绝不打印一个看起来很确定的 `0.0%`。**更不要去猜某一家的缓存命中规则来倒推**——猜错了你会按一个不存在的规则去优化。
- **单价不要写进代码。** 价目随时会变，同一个模型在不同网关上也不一样。全部读环境变量、默认 0，并且**把「没配单价」和「零成本」显式分开**：默认 0 会让不可用看起来像不要钱。
- **「假 A/B」：两个变体跑出来一模一样，而它从不报错。** `TODO(5)` 就是这个坑——`systemSuffix` 被悄悄丢掉了，你只会得出「改了没用」的结论。做完 A/B 的第一件事是确认两边**确实不同**：至少 token 要有差别。
- **离线 A/B 测得出成本，测不出效果。** 剧本 provider 的回答是写死的，提示词改了它也不会换一条路走。所以离线下通过率必然一点没变，只有 token 涨了。要测行为变化必须接真实网关，而且**同一题要跑多次看方差**。
- **离线下抖动接近 0 不是好消息。** 它恰恰说明这一轮评估没有在测模型，只在测你自己的代码。真实模型的同一题多次运行会给出不同的路径、不同的轮数、不同的 token，判断一个改动是否有效**必须先知道噪声有多大**——改动带来的差异小于噪声时，那个差异什么都不能说明。
- **基准集是拿「今天这个 Agent」当被测对象，不是拿写题那天的 Agent。** 五道题复用的是 D14–D16 写的剧本，那时还没有钩子，模型都是凭记忆直接做精确替换。D18 加上 `read-before-write` 之后，这几场的第一次 `edit_file` 会被 pre_tool 钩子**拦下、工具根本不执行**——而剧本照样跑完、报告照样出、一个错都不报，只是通过率从 5/5 掉到 2/5。所以 `mock-scenes.ts` 里给那三场各补了一步 `read_file`。这条坑的一般形式是：**被测对象每长出一条新规则，基准集就可能在没有任何报错的情况下失效**，每次改完 Agent 都要重跑一遍基准集看通过率有没有无声地掉下去。
- **面板起了就要关。** `/panel` 起的是一个 `node:http` server，不关掉进程不会退出、端口 3120 也一直占着。`server.close()` 还不够：keep-alive 的浏览器连接会让回调一直不来，要先 `closeAllConnections()`。
