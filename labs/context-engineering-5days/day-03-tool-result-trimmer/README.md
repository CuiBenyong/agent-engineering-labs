# D3 实验：工具结果裁剪器

> 目标：给一个电商客服 Agent 攒下来的五次工具结果做裁剪，三条规则依次生效——
> 字段白名单、长度上限、陈旧结果丢弃——并用一张表证明「裁掉了多少」，
> 用一份关键事实存活检查证明「没裁过头」。
> 只有这两个数字同时成立，裁剪才算做对了。

## 你会学到

- 跑通 solution，用 MOCK=1 看三条规则对一批工具结果的前后 token 对比
- 在 starter 里补全字段白名单裁剪，只留下后续步骤真正会用到的字段
- 补全长度上限与截断标记，确认被截断的部分留下了可再次取回的标识
- 补全陈旧结果丢弃：保留最近若干次工具结果，更早的换成占位说明
- 故意喂一条超长工具结果，验证裁剪之后关键字段仍然在

## 目录

- `starter/`：挖了 4 个练习点的起始代码，`MOCK=1` 下可以直接跑（跑出来省 0.0%，因为三条规则都还没生效）
- `solution/`：参考答案
- `src/fixture.ts`：五次虚构的工具结果与四条必须存活的关键事实，两边完全相同，不用改
- `src/tokens.ts`：离线 token 估算器，与 D1 实验同一份

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 这个实验不发网络请求，key 留空也能跑
MOCK=1 pnpm start                     # 默认配置
MOCK=1 HUGE=1 pnpm start              # 额外注入一条 600 行的日志
MOCK=1 HUGE=1 KEEP_RECENT=1 pnpm start  # 故意裁过头，看检查变红
```

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. `MOCK=1 pnpm start` 打出六行对比表，「省了」这一列不再全是 0.0%，合计省下 96% 左右（solution 上是 96.4%）。
2. 每一行的「用了哪条规则」列出的规则与它实际发生的事情对得上：最近三条走字段白名单，更早的两条走陈旧丢弃。
3. `HUGE=1` 注入的 600 行日志被长度上限截断（solution 上 12727 token 变成 280），且截断处留下了带 `ref` 的取回标识。
4. 四条关键事实的存活检查全部为 ✅，脚本以 0 退出。
5. `HUGE=1 KEEP_RECENT=1` 时检查里出现 ❌ 且脚本以 1 退出——说明这份检查是真的在查，不是摆设。

## 常见坑

1. **裁剪把「还有更多」这件事也裁掉了。** 只删字段不留 `_dropped_fields`、只截断不留 `ref`，模型就会把残缺的结果当成全部，然后一本正经地基于半份数据回答。留一行标识的成本是十几个 token，省下的是一次错误结论。
2. **小结果越裁越大。** `get_policy` 本来只有 80 token，白名单裁完反而涨到 84——因为多写了一个 `_dropped_fields` 数组。裁剪本身有开销，给规则设一个「低于多少 token 就别裁」的下限，比无脑全量裁更划算。
3. **陈旧丢弃的占位写得太省。** 只写 `[已清理]` 会丢掉工具名与参数，模型连「要不要重新查一次」都判断不了。把 `KEEP_RECENT` 调到 1 跑一遍就能看到关键事实直接变红。
4. **只看省了多少，不看丢了什么。** 省 99% 很容易，把上下文清空就行。这个实验之所以要两张输出，就是因为单看压缩率的裁剪器一定会越调越激进，直到某天线上答错了才发现。
