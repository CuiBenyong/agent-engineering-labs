# D2 实验：精简一份持久指令文件

> 目标：拿一份真实攒出来的 43 条客服 Agent 系统提示，逐条判定它该保留、下沉还是删除，
> 再把留下来的重排成「通用规则 / 项目约定 / 任务变量」三层。
> 今天的产出是文档不是程序，但它决定了后面三天所有数字的起点——
> 系统提示是每一轮都在重发的那一块。

## 你会学到

- 读 solution 里填好的指令文件，对照臃肿版看每一段被删掉的理由
- 在 starter 的臃肿版指令文件里逐条标注：保留、下沉到引用文件、还是直接删除
- 把保留下来的规则按通用规则、项目约定、任务变量三层重排
- 填写前后对比表：行数、估算 token、被删规则的处置去向各是什么

## 目录

这是**文档型实验**：`starter/` 与 `solution/` 各只有一份同名 Markdown，不需要 `pnpm install`、不需要 `MOCK=1`、没有自检脚本。

| 文件                  | 干什么用                                                             |
| --------------------- | -------------------------------------------------------------------- |
| `instruction-file.md` | 指令文件本体。starter 里每条后面留了 `[ ]` 待判定，solution 里已填好 |

## 怎么用

1. 先只读 `starter/instruction-file.md` 的第 1 到第 8 节，**不要先看 solution**。凭自己的判断在每条后面的方括号里填 `保留` / `下沉` / `删除`，并补一句理由。
2. 判定用同一把尺子，按顺序问三个问题，第一个答「是」就落定：模型不看这条会做错吗（不会就删）；每类任务都用得上吗（不是就下沉）；剩下的保留。
3. 把保留下来的条目重写进文末的三层结构，**合并同类项**——原文里有好几组是同一件事的不同说法。
4. 填完前后对比表，再打开 `solution/instruction-file.md` 对答案。**分歧比一致更有价值**：找出你和它判得不一样的条目，想清楚谁的理由更硬。
5. 把你精简后的版本真的拿去用一次，看有没有哪条被删掉的规则的确该留。

## 验收标准

1. 43 条全部有判定，没有留空的方括号，且每条都有一句理由。
2. 三层结构填完，且**每一条「通用规则」都能被机械核对**——「不用感叹号」算，「语气自然」不算。
3. 「任务变量」那一层至少列出两条，它们在原文里是被当成长期规则写的，实际上每次都在变。
4. 前后对比表填完，精简后的估算 token 至少降到原来的一半以下（solution 是 881 降到 425）。
5. 能对着你的结果说出一句话：**删掉的那些条目里，没有一条是模型真正需要的。**

## 常见坑

1. **舍不得删，全判成「下沉」。** 下沉不是免罪符：搬进引用文件的内容仍然要维护、仍然会被读进上下文，只是晚一点。真正没用的条目要删掉，判据是「模型不看这条会做错吗」。
2. **把形容词当规则。** 「专业、友好、耐心、细致」这类词看着像要求，实际上模型加不加它行为都一样。检验方法很简单：**你能写出一个自动检查它有没有被遵守的断言吗？** 写不出就是废话。
3. **重复条目只删一条。** 原文里「不要编造物流时间」「不要猜订单状态」和「先查再答」是同一件事的三种说法。留一条最具体的，另外两条都删——重复不只是浪费 token，它还会让模型在冲突时不知道听谁的。
4. **把运行时信息写死进系统提示。** 「夜间工单更慢」「节假日物流延迟」看着像规则，其实是随时间变化的事实。写死在系统提示里，凌晨一点它是对的，中午十二点它就在骗用户。这类内容要么由工具返回，要么每次拼进用户消息。
