# D1 实验：上下文用量剖面脚本

> 目标：把一次电商客服 Agent 会话的请求体拆成系统提示、工具定义、对话历史、工具结果四块，
> 分别算出 token 数与占比，看清「到底是哪一块把窗口撑爆的」。
> 这份剖面是后面四天的基准线：D3 裁工具结果、D4 压历史，都要回到这张表上看数字有没有变好。

## 你会学到

- 跑通 solution，用 MOCK=1 看一次会话被拆成四块之后的 token 占比表
- 在 starter 里补全把请求体拆成四块的分块函数，确认四块之和等于总数
- 补全 token 计数的封装，让它在离线时走估算器、在线时走计数接口
- 把工具定义从 3 个加到 8 个再跑一遍，看哪一块的占比先失控
- 去掉 MOCK=1 用真实计数接口跑同一批输入，记录估算误差有多大

## 目录

- `starter/`：挖了 4 个练习点的起始代码，`MOCK=1` 下可以直接跑
- `solution/`：参考答案
- `src/fixture.ts`：虚构的会话数据（系统提示、8 个工具定义、含两次工具调用的历史），两边完全相同，不用改

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 ANTHROPIC_API_KEY；没有 key 先用 MOCK=1
MOCK=1 pnpm start              # 离线估算
MOCK=1 TOOL_COUNT=8 pnpm start # 把工具从 3 个加到 8 个
pnpm start                     # 走真实计数接口做差分计数
```

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. `MOCK=1 pnpm start` 打出一张五行的表（基础开销、系统提示、工具定义、对话历史、工具结果），每行都有 token 数与占比，占比之和是 100%。
2. 工具结果那一行不再是 0，且它是占比最大的一块——solution 上是 72.9%。
3. 把 `TOOL_COUNT` 从 3 调到 8，工具定义那一行的占比明显上升（solution 上从 10.2% 升到 21.3%），而系统提示与工具结果的绝对 token 数一个都没变。
4. 最后一行打印了窗口占用率，且这个数等于合计除以 `WINDOW`。
5. 去掉 `MOCK=1` 用真实接口跑一次，把两次的合计相减，能说出估算器是偏大还是偏小、差多少。

## 常见坑

1. **把工具结果算进对话历史。** 工具结果写在 `role: 'user'` 的消息里，一不留神就跟用户说的话混成一块。混了之后这张表就没用了——它们的增长方式完全不同：用户说的话每轮加几十 token，工具结果一次就能加两千。
2. **拆完之后留下了空消息。** 一条消息里如果只有 `tool_result` 一个块，挑走之后 `content` 就空了。空消息不但没意义，真发给接口还会被拒。
3. **差分计数没减 baseline。** 一个空请求本身就有几个 token 的固定开销，不减掉的话每一块都会被多算一次，五块加起来会超过总数。
4. **以为估算器可以直接拿去算钱。** 它只是让你在没有网络的时候也能看清比例。真要报成本，必须用计数接口按你实际要用的那个模型 id 重新数一遍——不同世代的模型分词器不一样，同一段文本的 token 数能差三成。
