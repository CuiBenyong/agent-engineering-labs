# D5 实验：上下文调优报告

> 目标：把前四天的手段收进一张能交出去的表——账单拆解、两个利用率指标、
> 失败模式定位、三条改动记录、以及一条停手判据。
> 今天的产出是文档不是程序，但它是这门课的落点：
> **能拿数字说清楚「改了什么、为什么改、改完好了多少」，才算学会了上下文工程。**

## 你会学到

- 读 solution 里填好的调优报告，看每一条改动分别是被哪个指标触发的
- 在 starter 的报告模板里填入 D1 剖面脚本与 D3 裁剪器跑出来的真实数字
- 对照四种失败模式表，给你的会话选出一种并写清判定依据
- 写三条改动记录，每条注明预期的指标变化与实际的指标变化

## 目录

这是**文档型实验**：`starter/` 与 `solution/` 各只有一份同名 Markdown，不需要 `pnpm install`、不需要 `MOCK=1`、没有自检脚本。

| 文件               | 干什么用                                                              |
| ------------------ | --------------------------------------------------------------------- |
| `tuning-report.md` | 报告本体。starter 是待填模板，solution 是用本课实验真实输出填好的样板 |

## 怎么用

1. 先把 D1、D3、D4 三个实验各跑一遍，把输出留在终端里或复制到草稿。
2. 打开 `starter/tuning-report.md`，从第 0 节往下填，**每个 TODO 都要指回某一次实际运行**。
3. 第 2 节的缓存那一栏不要跳过。它是这份报告里最容易出反直觉结论的地方——精简之后前缀可能反而变贵。
4. 第 4 节选失败模式时，判定依据必须是上面某个数字，不能是印象。
5. 填完再打开 `solution/tuning-report.md` 对照，重点看它的第 5 条改动记录为什么会出现一个「指标变好、账单变差」的改动。

## 验收标准

1. 报告的六节全部填完，没有剩下的 TODO。
2. 第 1 节的剖面表四块占比之和是 100%，且能指出最大的一块是哪块。
3. 第 2 节算出了优化前后的合计，并单独算了缓存折算后的等效前缀开销；如果你的前缀跨过了最小可缓存长度这条线，报告里要写清是哪个方向。
4. 第 4 节选定了一种失败模式，且判定依据引用了第 1 到第 3 节里的具体数字。
5. 第 5 节三条改动记录里，**至少有一条的实际变化与预期不一致**——全部符合预期通常说明你没有真的重测。

## 常见坑

1. **只报总数不报构成。** 「省了 80%」这句话没有可操作性。要能说出省下来的是哪一块、剩下的大头还在哪，下一步才有方向。
2. **忘了算缓存。** token 数降了不等于账单降了。稳定前缀被缓存之后单价只有原价的十分之一，把它优化掉换来的是全额重发。
3. **两个指标只看一个。** 窗口占用率低不代表没问题，有效信息占比才是「值不值」。这次的样板里占用率只有 5.6%，看起来毫无压力，实际上八成 token 都是干扰。
4. **一次改三处。** 改动记录里的「实际变化」就是为了逼你一次只动一处。三处一起改再测，出了问题你分不清是哪一处的功劳或锅。
