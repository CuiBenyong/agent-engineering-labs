# 上下文调优报告（示例，已填写）

> 这份是拿本课四个实验的真实输出填出来的样板。你自己那份的数字会不一样，
> 但**每一栏都必须能指回某一次实际运行**——这是它和「感觉优化了一下」的唯一区别。

## 0. 场景

- 被测对象：「小店严选」电商客服 Agent，处理一笔已发货订单的退货咨询
- 一次完整任务的轮数：20 轮
- 使用的模型 id 与窗口上限：`claude-sonnet-5`，窗口 200000
- 测量方式：离线估算器（D1 实验里的 `estimateTokens`）。计数接口用来校准一次，估算器的相对误差在比例级别上够用，绝对值报成本时以计数接口为准

## 1. 单轮上下文剖面（来自 D1）

`MOCK=1 pnpm start`，挂载 3 个工具：

| 块       | token | 占比  |
| -------- | ----- | ----- |
| 基础开销 | 8     | 0.3%  |
| 系统提示 | 280   | 9.3%  |
| 工具定义 | 308   | 10.2% |
| 对话历史 | 218   | 7.3%  |
| 工具结果 | 2191  | 72.9% |
| 合计     | 3005  | 100%  |

最大的一块是：工具结果，一块就占了七成以上。把工具从 3 个加到 8 个（`TOOL_COUNT=8`），
工具定义从 308 涨到 731、占比从 10.2% 升到 21.3%，而工具结果的绝对值一个都没变——
**这说明两块的增长互相独立，得分开治。**

## 2. 一次任务的 token 账单

增长模型（20 轮，工具平均每 3 轮调一次，共 6 次）：

| 组成                                    | 增长方式                | 优化前合计 | 优化后合计 |
| --------------------------------------- | ----------------------- | ---------- | ---------- |
| 稳定前缀（系统提示 881 加工具定义 731） | 每轮重发                | 32240      | 14660      |
| 对话历史                                | 线性增长（每轮约 55）   | 11550      | 3684       |
| 工具结果                                | 阶梯增长（每次约 1424） | 89712      | 3276       |
| 合计                                    |                         | 133502     | 21620      |

三处优化分别来自：D2 把系统提示从 881 精简到 425、把工具从 8 个裁到 3 个（731 降到 308）；
D3 的裁剪器把每次工具结果从 1424 压到 52（省 96.4%）；D4 的压缩器把历史压掉 68.1%。
合计省下 83.8%。

缓存这一栏必须单独算，因为它会得出一个反直觉的结论：

- 稳定前缀的 token 数：优化前 1612，优化后 733
- 所用模型的最小可缓存长度：`claude-sonnet-5` 是 1024 token
- 前缀是否满足最小长度：优化前满足，优化后**不满足**
- 按写入 1.25 倍、命中 0.1 倍折算后的等效前缀开销：优化前 5078，优化后 14660
- 结论：**前缀这一块被我优化得更贵了。** 精简之后它掉到 1024 以下，缓存直接失效，
  20 轮全按原价重发。三条修法：一是把稳定的少样本示例或常用引用文件放回前缀，
  把它抬回 1024 以上（这些内容本来也有用）；二是换一个最小可缓存长度更低的模型
  （Claude Opus 5 与 Fable 5.1 是 512，733 就能命中）；三是接受它——
  前缀只占总账单的一小部分，全局仍然省了 79.7%（把缓存折算进去之后的口径）。

## 3. 两个利用率指标

| 指标         | 定义                                      | 优化前                   | 优化后       | 阈值                    |
| ------------ | ----------------------------------------- | ------------------------ | ------------ | ----------------------- |
| 窗口占用率   | 单轮输入 token 除以窗口上限               | 5.6%（第 20 轮的 11256） | 0.7%（1396） | 超过 50% 就该动手       |
| 有效信息占比 | 裁剪器判定为必须保留的 token 除以总 token | 19.1%                    | 100%（见下） | 低于 20% 说明在搬运垃圾 |

两个指标各自暴露什么问题：**窗口占用率管的是「会不会撑爆」，有效信息占比管的是「值不值」。**
它们经常不同步——这次优化前占用率只有 5.6%，离撑爆远得很，看起来完全不用管；
但有效信息占比只有 19.1%，意味着八成 token 是在给模型制造干扰，同时还在按原价计费。
**只盯占用率的人会一直等到出事那天才开始优化。**

有效信息占比优化后是 100%，这不是好消息，是**这把尺子失效了**：它用的判据就是裁剪器自己的
保留规则，优化之后携带的正好是保留下来的部分，分子分母必然相等。想继续用这个指标，
就得换一把更严的尺子（比如按模型实际引用到的字段统计），否则它从此只会一直显示 100%。

## 4. 失败模式定位

| 模式     | 典型现象                                   | 命中的指标              | 是不是我的情况                        |
| -------- | ------------------------------------------ | ----------------------- | ------------------------------------- |
| 塞太满   | 模型漏读早期指令，违反系统提示里明写的约束 | 窗口占用率高            | 否，占用率只有 5.6%                   |
| 找不到   | 信息就在窗口里，模型却说没有               | 有效信息占比低          | **是**，占比只有 19.1%                |
| 说不清   | 同类问题答法不稳定，一会儿这样一会儿那样   | 占用率不高但错误率高    | 部分是，43 条规则里有 3 组互相重复    |
| 越走越偏 | 前二十轮正常，后面开始违反最初的约束       | 压缩前后的保留检查有 ❌ | 否，`KEEP_TURNS=6` 时四条事实全部存活 |

判定结论：主要是「找不到」，次要是「说不清」。所以先做 D3 的工具结果裁剪（治主症），
再做 D2 的指令文件精简（治次症），压缩放到最后——它治的是我现在还没有的病。

## 5. 改动记录

| #   | 改了什么                                | 依据哪个指标           | 预期变化           | 实际变化                                         | 留下还是回滚                             |
| --- | --------------------------------------- | ---------------------- | ------------------ | ------------------------------------------------ | ---------------------------------------- |
| 1   | 给工具结果加字段白名单与长度上限        | 有效信息占比 19.1%     | 工具结果降八成以上 | 每次 1424 降到 52，省 96.4%，四条关键事实全存活  | 留下                                     |
| 2   | 把系统提示 43 条精简到 14 条，13 条下沉 | 说不清（3 组重复规则） | 前缀降一半         | 881 降到 425                                     | 留下                                     |
| 3   | 把工具从 8 个裁到 3 个                  | 工具定义占比 21.3%     | 前缀再降           | 731 降到 308，但前缀总量掉到 1024 以下，缓存失效 | 留下，同时把常用引用文件放回前缀补足长度 |

第 3 条是这次调优里唯一一个「指标变好、账单变差」的改动。
它之所以还是留下了，是因为总账单仍然降了 79.7%，而且工具变少之后模型选错工具的情况也少了——
**但如果当初只盯着 token 数不看缓存，这一步会被记成纯粹的胜利。**

## 6. 停手判据

同时满足下面三条就停手，不再继续调：

1. 有效信息占比稳定在 50% 以上，且连续三次测量没有继续上升的空间。
2. 单轮窗口占用率在最长的那条用例上不超过 50%。
3. 关键事实存活检查连续三轮全绿，且最近一次改动带来的账单降幅低于 5%。

第 3 条是真正的刹车：**降幅低于 5% 说明剩下的都是必要开销，继续压就是在拿正确率换钱。**
