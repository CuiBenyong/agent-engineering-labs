# D4 实验：压缩策略

> 目标：给一段 32 轮的客服会话做压缩——按窗口占用率触发、最近几轮留原文、
> 更早的折叠成「已定结论 / 待办事项 / 硬约束」三段摘要——
> 并用一份关键事实存活检查证明压缩没有压过头。
> 压缩率和保留检查必须同时给出，只报压缩率的压缩器一定会越调越激进。

## 你会学到

- 跑通 solution，用 MOCK=1 看一段长会话压缩前后的 token 数与保留检查结果
- 在 starter 里补全触发判据：达到窗口占用阈值才压缩，且保留最近若干轮原文
- 补全摘要提示词，让它按已定结论、待办事项、硬约束三段输出
- 补全关键信息保留检查：预置若干必须存活的事实，压缩后逐条核对
- 把阈值调到很低再跑一遍，看过度压缩最先丢掉的是哪一条事实

## 目录

- `starter/`：挖了 4 个练习点的起始代码，`MOCK=1` 下可以直接跑
- `solution/`：参考答案
- `src/fixture.ts`：32 轮虚构会话与四条必须存活的事实，两边完全相同，不用改
- `src/tokens.ts`：离线 token 估算器，与 D1、D3 实验同一份

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 ANTHROPIC_API_KEY；没有 key 先用 MOCK=1
MOCK=1 pnpm start                  # 离线摘要（本地抽取式，形状与模型输出一致）
MOCK=1 KEEP_TURNS=1 pnpm start     # 故意压过头，看检查变红
pnpm start                         # 摘要交给真模型生成
```

> 说明：`WINDOW` 默认 3000，是为了让这段两千多 token 的会话能触发压缩而设的演示值，
> 不是任何模型的真实窗口。真实窗口请按你用的模型填。
>
> `starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. `MOCK=1 pnpm start` 先打印占用率（solution 上是 73.3%），达到阈值才进入压缩，把 `THRESHOLD` 调到 0.9 时会直接打印「未达到触发阈值」并退出。
2. 压缩后的上下文明显分成两段：`【前情摘要】` 的三段式，加上 `【最近 6 轮原文】` 的逐字保留部分。
3. 压缩率打印出来且在 65% 到 90% 之间（solution 默认配置是 68.1%）。
4. 四条关键事实的存活检查全部为 ✅，脚本以 0 退出。
5. `KEEP_TURNS=1` 时「用户要求的答复时限」变成 ❌ 且脚本以 1 退出——这条事实只活在最近几轮原文里，一折叠就没了。

## 常见坑

1. **按轮数触发压缩。** 轮数和 token 数不成正比，一次工具返回顶得上二十轮闲聊。要盯的是窗口占用率，不是回合数。
2. **把最近几轮也折叠掉。** 正在进行的那件事一旦被摘要，模型立刻失去指代对象，下一句就会开始问「你说的是哪一单」。starter 的默认实现就是这么干的，跑一次就能看到最近 0 轮原文长什么样。
3. **摘要提示词不点名要保留标识符。** 订单号、工单号、政策条目编号这类字符串在摘要里最容易被改写成「相关订单」「对应工单」，一改写就再也对不上了。提示词里要明确要求逐字保留。
4. **压缩率报得漂亮，检查形同虚设。** starter 的 `checkRetention` 返回空数组，于是每次都宣布「一条没丢」。一个不检查的检查函数比没有检查更危险——它会让你放心地把阈值一路调低，直到线上答错。
