# D11 实验：父子索引与上下文检索的实现，以及它们相对第九天配置的指标提升

> 目标：在**同一份语料、同一套第九天的混合检索**上，把父子索引、上下文检索、摘要索引三种
> 索引结构各建一遍，用第八天的 20 题标准答案集量出每一种的召回率、答案文档名次与 nDCG@10，
> 再把成本拆成「一次性建索引」和「每次查询」两笔分开记。
> 做完之后，「上下文检索到底值不值得上」这个问题在你这里不再是一句流传的经验，而是一张表。

## 你会学到

- 实现父子索引：小块入索引、大块另存，命中之后按 `parentId` 回填并去重
- 给每个块生成上下文块头并重建索引，离线模式下用规则生成替代模型调用
- 在同一评估集上对比第九天配置、父子索引、上下文检索、两者叠加四档
- **把第四天在纯 BM25 下量到的「块头是负收益」这条结论放到三条检索路线上复核一遍**
- **量出离线环境本身的边界**：向量路在融合里到底贡献了什么，以及它让哪个问题变得回答不了
- 实现摘要索引的两段式检索，并解释它为什么在这份语料上是净亏
- 选一个概括全文的问题，看清为什么任何「取前 k 块」的检索都答不了它
- 把一次性建索引费用与每次查询费用分开算，看出哪一笔才是长期账

### MOCK 说明（**这一条决定了你能从这个实验里得出什么结论**）

`MOCK=1` 换掉三处网络出口：

| 出口       | 离线替身                              |
| ---------- | ------------------------------------- |
| 向量       | 确定性哈希向量（D2 定，全课一致）     |
| 上下文块头 | 按标题路径拼的规则版 `《标题》路径：` |
| 文档摘要   | 标题 + 全部标题路径 + 每节首句        |

切块、索引、融合、重排、命中判定、预算装填、成本核算**全部真实执行**。

但是两条边界必须记住，**表六就是专门用来量它们的**：

1. **哈希向量保留的是字面重合度**，所以离线模式下「向量一路」的行为接近另一路关键词检索。
   实测：融合后的前 20 条里只有 **5.8%** 是向量路独有的，而这些独有候选
   在 20 道题里**一次都没有带进答案文档**（0/20）。也就是说
   **离线模式下混合检索的召回率基本全靠 BM25**，向量路只是重洗了一次名次。
2. **规则块头里只有标题词**，而真实模型写的块头会带上文中没有明说、要通读全文才知道的信息。

两条合起来，恰好把「模型写出文中没明说的信息 → embedding 因此编码到文档位置」
这条上下文检索赖以生效的因果链整段抹掉了。所以：

> **本实验能回答的只有 BM25 那一半。**「真实向量侧受不受益」它回答不了，
> 表二第③列在「纯向量」上的涨幅**不能**当成真实 embedding 会受益的证据。
> 想知道块头在你的语料上值不值，把 key 填上跑真实模式，自己看表二。

另外三条口径：

1. 本天的评估**不带 D7 的准入门槛**（D9 的融合路径上没有分数闸门），
   所以 `none` 类问题的拒答率不在本实验的量程内。
2. **不要看平均倒数排名**——第八天已经量出它在这份语料上顶格 1.0，是指标饱和不是系统满分。
3. **本实验的绝对数字与 D8 / D9 不严格可比。** 那两天建索引时把标题路径拼了两遍
   （`chunkDoc` 已经把它拼进 `text`，`retrieve.ts` 又拼了一次），本天的 `indexTextOf` 只拼一次——
   因为表二要精确控制「块携带多少上下文」，多拼一遍会把 ①②③ 三个层次的区分污染掉。
   这个差异**一致地作用于本天的全部配置**，所以本章内部的相对比较是成立的；
   但**不要拿本章的召回率去对 D8 基线报告里的数字**。

## 验收标准

跑 `MOCK=1 pnpm start`，对着输出逐条核：

1. **表一**「父子索引」那一行的块数是 **158**（基线是 134），上下文 token 与基线相当（532 对 539）——
   说明子块真的切出来了，而且回填父块之后没有把预算撑爆。
2. **表一**最后两行的索引 token 相同（22339）但上下文 token 不同（500 对 536）——
   说明「块头只进索引、不进上下文」这个开关真的生效了，而且五列指标一个都没变。
3. **表二**三条检索路线各给出三个层次的数字，且「纯向量」那一行的召回率在第③列
   **从 81.3% 涨到 87.5%**，而「混合检索」那一行召回率三列全是 **93.8%**、
   nDCG@10 却从 **0.6438 涨到 0.7218**。一个指标动、一个不动，这个实验才算跑对。
4. **表三**摘要索引的 multi 召回率明显低于基线（50% 对 75%），你能说出为什么。
5. **表五**「开缓存」比「不用缓存」便宜，省下来的比例是**正数**（约 29%）。
6. **表六**量出向量路独有候选占 **5.8%**、含答案文档 **0/20**，
   并且你能据此说清这次复核**回答不了**哪个问题。

`starter/` 原样跑时，第 1、2、3、4、5 条都是不达标的：块头那一列跟标题路径一模一样、
摘要索引两行完全相同、缓存那一笔是**负数**。做完五个练习它们会一条条变对。

## 常见坑

1. **父块回填忘了去重。** 一个父块被它的三个子块同时命中时，如果不用 `seenParents` 挡一下，
   同一段会被重复塞进上下文三遍，600 token 的预算两块就见底，召回率反而掉。
   跳过重复父块要用 `continue` 不是 `break`——后面的名次里还有别的父块。
2. **块头进了上下文。** 块头是给检索器看的，模型不需要它。
   进了上下文就等于在**每一次查询**里都为这几十个 token 付一次钱，而它一个字都没帮上生成。
   表一最后两行就是这一条的代价：同一套索引，只改这一个开关，预算里能多装进 36 个 token，
   五列指标一个不变。
3. **拿 `MOCK=1` 的块头收益去下结论。** 规则块头只有标题词，基线块的块首**已经带着标题路径**，
   两者信息量几乎一样；再加上向量路对召回的独立贡献实测为 0（表六），
   这个环境根本没有能力回答「真实向量侧受不受益」。真实结论只能在真实模式下取。
   顺带一个更普遍的教训：**替身环境的边界要自己量出来，不能靠猜**——
   表六只有六行，却决定了前面五张表能被解读到什么程度。
4. **把「没检索到」和「检索到了但没进预算」混为一谈。** 表四里 `q06` 的 21 属于前者——
   `doc-014` 在候选池里一次都没出现，换切法、加块头、父子回填一律无效，只能换检索手段（见正文的图检索一节）。
   后者是名次退到预算之外，调预算或调重排就够了。日志里先分清是哪一种，再决定改什么。
