# D3 实验：一条把 PDF、HTML、Markdown 统一解析成带标题层级与页码元数据的中间表示的管道

> 目标：把四种来源（Markdown 原件、HTML 页面、PDF 文本层、扫描件走 OCR 之后的纯文本）
> 解析成**同一种节点结构**，给每个节点补齐后面十一天都要用的元数据，
> 再给整条管道加上三条会真的报警的质量断言。
> 这一天不切块——切块是 D4 的事，今天只负责把文档变成一串带结构、带出处的节点。

## 你会学到

- 写三个解析器：Markdown 走行级语法、HTML 走选择器、PDF 走文本层加位置信息
- 把三者的输出统一成同一个节点结构，附上标题路径与页码
- 对解析结果加质量断言：空文本比例、乱序疑似度、表格是否塌陷，越线就报警
- 把一份双栏 PDF 跑一遍，记录失败现象与你的修补策略
- 为每份文档算一个内容指纹，为第十三天的增量更新埋好伏笔

## 全课统一的节点结构（D3 定，后面十一天不许改字段名）

```json
{
  "docId": "doc-005",
  "chunkId": "doc-005#c07",
  "text": "专业版席位价 69 元每人每月……",
  "headingPath": ["套餐与配额对照表", "文字说明"],
  "page": 2,
  "department": "product",
  "updatedAt": "2026-08-28",
  "contentHash": "374d2ff23765b53c"
}
```

- `page` 只有 PDF 来源有，Markdown / HTML / OCR 一律 `null`。
- `contentHash` 是**整篇文档**内容的 sha256 前 16 位，同一篇文档的所有节点共享同一个值。
- `chunkId` 形如 `doc-005#c07`，两位补零。今天的一个节点 = 一个解析单元（一段、一个列表、一张表）；
  D4 的切块会把这些节点重新合并成检索用的块，编号形式不变。

## 样例文件是怎么来的（**没有下载任何外部 PDF**）

`src/make-samples.ts` 用纯 JavaScript 从语料现造，跑一次生成五份：

| 文件               | 来源      | 造它是为了看什么                                         |
| ------------------ | --------- | -------------------------------------------------------- |
| `doc-003.html`     | `doc-003` | 导航 / 侧栏 / 页脚 / 统计脚本 / 代码块 / 脚注 / 相对链接 |
| `doc-019.pdf`      | `doc-019` | 单栏正常件：页码、页眉页脚、按字号认标题                 |
| `doc-005.pdf`      | `doc-005` | **双栏 + 那张本来就串行的表**，本天最难的一份            |
| `doc-024.scan.pdf` | —         | 扫描件：整页是图，文本层里只有页眉页脚                   |
| `doc-024.ocr.txt`  | `doc-024` | 上面那份送去 OCR 之后的结果：结构全丢 + 形近字错         |

PDF 是手写的最小字节流：目录、页树、每页一个内容流、末尾一张交叉引用表，
文字用 UTF-16BE 十六进制串写进 `Tj` 操作符。**它没有嵌入字体文件**，
所以用 PDF 阅读器打开只会看到空白页——但文本层是完整的，
真实的 PDF 解析库（pdfjs、pdfplumber）从任何一份 PDF 里读到的也正是这些
「第几页、什么坐标、多大字号、哪一段文字」的记录。本实验要练的就是从这堆记录里
把段落和阅读顺序推回来。

OCR 也是**假装**的：不装任何 OCR 引擎（那要系统级依赖），
而是把语料按「形近字替换 + 结构抹平」的规则造出一份带噪声的纯文本。
错字是确定性注入的，跑多少次都一样。

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 今天不需要任何 API key，这一步可以跳过
MOCK=1 pnpm start
```

一次性脚本，跑完就退出，**不要**用管道喂输入。

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `[ERR_PNPM_IGNORED_BUILDS]`，
> 这只是 pnpm 拦了 esbuild 的构建脚本，依赖已经装好了。以 `pnpm typecheck` 和 `pnpm start` 的结果为准。

### MOCK 说明

**今天这条管道全程离线**：解析、断言、指纹都在本地算，没有任何网络出口，
也不需要 `OPENAI_API_KEY` 或 `ANTHROPIC_API_KEY`。`MOCK=1` 加不加结果完全一样，
保留它只是为了跟其余十三天的命令一致。

从 D2 起「mock 用于验证代码路径，不用于验证效果」这句话在今天有个更强的版本：
**解析质量是可以离线验证到底的**——它不依赖模型，只依赖你的代码，
所以今天所有断言的数字都是真数字。

## 验收标准

1. `MOCK=1 pnpm start` 依次打印七段现象，最后写出 `out/nodes.json`（solution 是 224 个节点）。
2. 第 ① 段里 30 篇 Markdown 解析出的节点**全部带标题路径**，示例行显示的是
   `《任务板使用指南 / 泳道》` 这样的路径而不是「（无标题路径）」。
3. 第 ④ 段里，同一份双栏 PDF 按内容流原序读乱序疑似度是 0.33（❌），
   分栏排序后降到 0.00（✅）；「顺着读前四段」两行对照着看，
   前者从表格末尾跳到开头再跳到半句话，后者是通顺的。
4. 第 ⑤ 段里扫描件的空文本比例是 1.00（❌）被拦下，转 OCR 之后拿到 3 个节点、
   错字率 2.1%，术语命中从 36 次掉到 28 次，且标题路径全空。
5. 第 ⑥ 段里 224 个节点 chunkId 唯一、元数据零缺字段，
   同一篇文档改一个字之后内容指纹变成另一个值。

starter 原样跑起来第 2、3、5 条是不达标的（标题路径全空、双栏排序没修好、指纹全都一样），
第 ① 段的塌陷表格也会假装绿灯——四个练习点做完，五条才会全对。

## 常见坑

1. **以为 PDF 里有段落。** PDF 只存「在某页某坐标画某段文字」，段落、阅读顺序、
   标题层级全是你从坐标和字号里推出来的。多栏文档尤其危险：排版软件常按 y 值成带地写内容流，
   直接照抄顺序就会把左右两栏一行一行地拌在一起，而且**拌出来的句子每一句都通顺**，
   肉眼扫一遍很难发现。
2. **把页眉页脚留在正文里。** 每页都出现的那行「云梯科技 · 内部资料」会在全库高频出现，
   既拉低区分度，又会让检索命中一段毫无信息量的文字。按 y 值切掉上下两条带最省事，
   但要顺手打印剔除条数确认没误伤——本实验里单栏两页应该剔掉 4 条。
3. **清洗清过头。** 相对链接 `./doc-002.md`、页码、更新时间这些东西，
   删的时候一行代码，删完就再也追不回来了——除非你把原件重新解析一遍。
   本实验把相对链接内联进正文（`任务板（链接：./doc-001.md）`），
   就是为了在不加字段的前提下把它留住。
4. **内容指纹不做换行归一化。** 同一份文件从 Windows 和 Mac 各上传一次，字节不同、内容相同，
   不归一化的话 D13 的增量同步会判定「全库都变了」，白重算一遍。
5. **术语命中这个探针在练习 1 做完之前是失真的。** 标题路径为空时，
   Markdown 原件那一侧少算了标题里的词，会出现「OCR 版命中数反而更高」的怪现象。
   做完练习 1 再看这一行。
