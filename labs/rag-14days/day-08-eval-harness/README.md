# D8 实验：一套可复跑的评估脚本与第一周系统的基线报告

> 目标：给第一周装完的那套检索问答服务称一次重。造一份 20 题的标准答案集，实现召回率、平均倒数排名、归一化折损累计增益三个检索指标，再用模型裁判评忠实度与答案相关性，最后把这一切封成一条命令，输出一份可以跟下一次跑对比的报告文件。**第二周每一天的优化都要拿这份报告证明自己有用。**

## 你会学到

- 从语料里挑二十个问题标好答案文档，其中留出三个是语料里没答案的
- 实现三个检索指标，对第一周的系统跑出基线数字
- 写模型裁判的提示词，评忠实度与答案相关性，输出结构化分数
- 人工抽检十条裁判结果，算一致率，把不一致的原因写下来
- 把评估脚本封成一条命令，输出可对比的报告文件

## 语料说明

`corpus/` 是 D1 造的 30 篇虚构语料（云梯科技，一家虚构 SaaS 公司），MIT 许可，随 lab 分发。
里面刻意埋了两篇结论冲突的文档、一条要跨两篇才能答上的事实、一段排版糟糕的表格——

## golden set 说明

20 题，字段 `{ id, question, answerDocIds, type }`：

| type     | 含义               | 命中判定                              | 题数 |
| -------- | ------------------ | ------------------------------------- | ---- |
| `single` | 单篇文档就能答     | `answerDocIds` 里**任意一篇**进上下文 | 12   |
| `multi`  | 必须跨文档才能答   | `answerDocIds` **全部**进上下文       | 4    |
| `none`   | 语料里根本没有答案 | 不算召回，看它有没有**正确拒答**      | 4    |

- **前 10 题（`q01`–`q10`）与 D4 的 `eval/questions-10.json` 逐字相同**，改一个字两天的数字就不能比了。
- 对照的尺子是 **600 token 上下文预算**，不是「取前 k 块」——按固定条数比不同切法是不公平的，
  口径与 D4 完全一致。
- `none` 那四题都留了强干扰词：问「网页端支持哪些浏览器」，语料里有一句「提交工单时请附上浏览器与版本」；
  问「私有化部署要多少 CPU 和内存」，语料里既有「私有化部署」也有「CPU、内存」，只是从来没写过硬件配置。
  没有干扰词的无答案题太好答，测不出东西。

## MOCK 说明

`MOCK=1` 下有两处被换成离线替身，其余代码路径完全一致：

1. **向量**换成确定性哈希向量（规格见 `src/embed.ts`，全课 14 天逐字一致）。
   它保留字面重合度，所以向量检索的行为接近关键词检索——**它验证代码路径，不验证检索效果**。
2. **裁判**换成确定性规则裁判：按「这句话的词元有多大比例能在上下文里找到」判有没有支撑。
   **指标的计算、聚合、一致率、闸门这些逻辑一行都没有被 mock 掉**，走的是同一份代码。

规则裁判有一个必须知道的盲区：**它抓不住「把数字改掉」**。
把「保留 30 天」改成「保留 90 天」，词元重合度几乎不变，规则判它有支撑。
`src/judge.ts` 的第三个探针专门把这条盲区打印出来（标成 ⚠️，不计入验收）。
真模型裁判能抓住它——这就是 MOCK 的边界所在，也是为什么忠实度这个指标必须接真模型才有意义。

## 人工抽检怎么做（十条，半小时）

一致率是唯一能判断「裁判靠不靠谱」的东西。做法：

1. 跑一次 `MOCK=1 pnpm start`，打开 `reports/latest.json`。
2. **分层抽 10 条**，不要随机抽：各类型都要有，命中的和没命中的都要有，
   裁判给高分和给低分的都要有。全抽命中的题，你只会得到一个好看的假一致率。
3. 每条只回答一个问题：**这段回答里有没有材料里没写的东西**。
   只判忠实度，不判好不好——判「好不好」你和裁判会各说各话，一致率就没有意义了。
4. 写进 `eval/human-labels.json`（`questionId` / `faithful` / `note`），
   `note` 里写清你为什么这么判，尤其是跟裁判不一致的时候。
5. 再跑一次，看第五段的一致率。**低于 0.8 就别再拿这个裁判的分数拦合并**，先去改提示词。

一致率很高不一定是好消息：如果被抽的十条都是「答案直接抄自材料」的简单题，
裁判判对是理所当然的，这时候 100% 说明的是你的抽检没有难度，不是裁判可靠。

## 验收标准

1. `MOCK=1 pnpm start` 跑完，「七、验收」七项全部 ✅
2. 报告里 `single` 与 `multi` 两档召回率不同（说明 `multi` 用的是「全部命中」口径而不是抄了 `single`）
3. 归一化折损累计增益的值与召回率不相等，且逐题表里能看出哪几题排序差
4. 裁判探针里「与材料无关的编造」那条被抓出来（忠实度低于 0.7）
5. 把召回率人为调低 15 个点，回归闸门会拦住（第六段最后一行显示「闸门拦住了」）

## 常见坑

1. **只看召回率会瞎。** 本实验的基线里召回率 87.5%，看着不错；但无答案题的拒答率是 **0%**——
   四题全部被塞了一堆不相干材料。少了「无答案题」这一类，这个故障你永远看不见。
2. **平均倒数排名会顶格。** 基线里它是 1.0000，因为题目是从语料反向出的，字面重合度太高，
   第一名永远是答案文档。指标顶格不是好消息，是「这份题集已经量不出区分度了」的信号——
   接真 embedding、或者把问题改写得离原文更远，它才会重新有分辨力。
3. **裁判会被标题片段坑。** 块里带着标题路径，摘出来的「监控告警与日志规范 > 日志规范」
   剔掉高频词后一个可判词元都不剩。早期版本把它算成「没支撑」，忠实度凭空掉了一截。
   现在 `overlapRatio` 返回 `null` 表示**判不了**，判不了的不进分母——这个坑是人工抽检 q13 时撞出来的。
4. **别用 `process.cwd()` 找 `corpus/` 和 `eval/`。** 你在 lab 根目录敲和在 `solution/` 里敲会得到两个结果。
   一律用 `import.meta.url` 往上两级定位。
5. **闸门的容差不要设太大。** 同一份数据、同一份配置本该逐位相同，`GATE_TOLERANCE` 留 0.01
   只是给换 embedding 后端用的。设成 0.05，一次真实的退步就能大摇大摆走过去。
