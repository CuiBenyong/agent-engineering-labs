# D9 实验：混合检索加重排的实现与三档配置在同一评估集上的指标对比

> 目标：把关键词与向量两路检索拆成两个独立的检索器，用倒数排名融合把它们的**名次**合到一起，
> 再拿一个交叉编码器对融合后的前 20 条精排，最后在 D8 那份 20 题标准答案集上跑出
> **纯向量 / 纯 BM25 / 混合 / 混合+重排**四档对照，每一档都报三笔账：指标、延迟、成本。
> **这一天的产出不是「混合检索更好」这句话，是一张能让你据以取舍的表。**
>
> 注意 D8 的基线里平均倒数排名已经顶格 1.0000（题目从语料反向出、字面重合度过高），
> 本实验四档里也有三档是 1.0000。**它是指标饱和，不是系统满分，不能拿来当任何改进的证据。**
> 可用的证据只有召回率（尤其 multi 档）、nDCG@10 和拒答率这三个还有空间的量。

## 你会学到

- 把关键词与向量两路检索拆开各跑各的，各取前 50 条
- 实现倒数排名融合，调一次那个常数 k 看前 5 名怎么变
- 接一个交叉编码器对融合结果的前 20 条精排，离线模式下用可复现的替身打分
- 在 D8 的评估集上跑出四档指标对比，并看清「每路取多少条」这个旋钮的杀伤力
- 记录每一档的延迟与调用成本，给出你的推荐配置和理由

## 真实重排后端接什么（D9 定，D10–D12 沿用）

`rerank.ts` 里有两个真实后端，都实现同一个 `Reranker` 接口：

| 后端                                      | 怎么开                                                                                  | 什么时候选它                                                                                    |
| ----------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **Cohere Rerank，默认模型 `rerank-v3.5`** | 填 `COHERE_API_KEY`                                                                     | 默认。多语言、按「检索次数」计价、不用自己养 GPU                                                |
| **自部署 `BAAI/bge-reranker-v2-m3`**      | 填 `RERANK_BASE_URL`（指向一个 `/rerank` 端点，text-embeddings-inference 就是这个形状） | 数据不能出内网、或者调用量大到按次付费不划算时。权重是 Apache-2.0，多语言，一张消费级显卡放得下 |

两者都用原生 `fetch` 调，没有额外依赖。想换别家，照着 `cohereRerank` 再写十行就行——
**接口是稳定的，后端是可换的**，这是把重排放在 `rerank.ts` 一个文件里的全部理由。

## MOCK 说明（**这一条决定了你能从本实验里得出什么结论**）

`MOCK=1` 下有两处被换成离线替身，其余代码路径完全一致：

1. **向量**换成确定性哈希向量（规格见 `src/embed.ts`，全课 14 天逐字一致）。
   它按 2-gram 的字面重合度算相似度，**所以向量那一路的行为接近关键词检索**。
2. **重排**换成确定性替身：按「查询词元与文档词元的加权重合度」打分。它只会数词，
   读不懂「组长是谁」和「周敏」是一回事。

由此产生一条**必须知道的边界**：

> **`MOCK=1` 下向量那一路几乎没有独立贡献，所以本实验跑出来的「混合检索提升了多少」不是真实结论。**
> 报告第四段会直接把这件事打印出来：只有关键词一路命中的题有 3 道（`q07`、`q17`、`q18`），
> **只有向量一路命中的题是 0 道**。两路高度重复的时候，融合能做的事本来就很有限。
>
> 可信的是**代码路径与账本**：融合有没有真的改写名次、重排有没有真的重排、
> 每一档的 token 数与调用次数是多少。**不可信的是提升幅度**。
> 想要真实幅度，去掉 `MOCK=1`、填上 `OPENAI_API_KEY` 与 `COHERE_API_KEY` 再跑一遍。

同理，延迟那一列在 `MOCK=1` 下没有任何网络往返，只能说明「代码本身有多重」；
真实系统的延迟由那两次网络往返决定，所以报告里单独有一列「建模网络 ms」，用的是可覆盖的占位值。
成本账里的单价同样是**占位值**，真正由实测撑着的只有 token 数与调用次数。

## 常见坑

1. **别把两路的分数直接相加，也别指望归一化能救。** BM25 的分是没有上界的对数和
   （本语料上 top-1 常在 5–52 之间），余弦被钉死在 -1 到 1（mock 后端上相关块只有 0.2 出头）。
   各自除以本路最高分再加权看着很合理，但最高分随查询浮动：一条最不相干的结果只要碰巧是本路第一，
   归一化之后照样拿到满分 1.0。**RRF 只看名次，就是为了绕开这件事。**
2. **同分不按 id 兜底排序，跨天的数字会飘。** `rrfFuse` 里两条结果拿到同一个分数是常事
   （两路名次对称时必然同分），`Array.prototype.sort` 的稳定性只保证相等元素的相对顺序，
   而 Map 的遍历顺序又取决于插入顺序——插入顺序会随查询变。加上 `a.id < b.id ? -1 : 1` 才可复现。
3. **每路取多深是个大旋钮，而且方向和直觉相反。** 本语料只有 134 块，每路取 50 等于把 37% 的库
   灌进融合。报告第六段实测：`PER_ROUTE_K` 从 50 收到 5，混合那一档的召回率从 87.5% 回到 93.8%、
   multi 档从 50.0% 回到 75.0%（nDCG@10 则从 0.7186 掉到 0.6281，两个指标在这里打架）。
   **取深了不是更保险，是把噪声也一起投了票。**
4. **重排只作用于融合后的前 20 条，不要对全库重排。** 交叉编码器把查询和文档拼在一起过模型，
   没有任何东西可以预先算好：134 块就要跑 134 次前向，是重排 20 条的 6.7 倍；
   换到十万块的真实语料，这个比值是 5000 倍。名次靠后的那些块本来就进不了上下文预算，
   为它们付前向成本没有任何回报。
5. **重排改不了拒答率，别指望它替你闭嘴。** 准入判定卡在每一路的原始分上（`bm25 >= 6 || cos >= 0.2`），
   重排只改顺序、不改准入，所以四档里重排那两档的拒答率都是 0.0%。
   唯一把拒答率提上去的是**纯向量**那一档（25.0%）——0.2 的余弦门槛真的挡住了一道无答案的题，
   而 D7 的 6 分 BM25 门槛对本语料形同虚设。生成侧的拒答是 D6 的活，不是重排的活。
6. **多跳档的两道失败题要分开归因，别混着谈。** `q07`（需要 `doc-029` + `doc-021`）纯 BM25 命中、
   融合之后丢了、重排又救了回来——这是一条干净的、可归因的改进。`q06`（需要 `doc-019` + `doc-014`）
   **四档全部未命中**，因为 `doc-014` 从头到尾没进过候选池：融合和重排都只能重排已有的候选，
   变不出新的。把这两种失败混着说，你会得出「混合检索能修多跳」这个错误结论。
7. **门槛要卡在每一路的原始分上，不能卡在融合分上。** 融合分是相对的，一次检索里最不相干的
   那批结果照样有人排第一。`evaluate.ts` 里的 `admitted` 判定用的是 `bm25 >= 6 || cos >= 0.2`
   这两个 D7 定下的原始分门槛，不是 RRF 分数。
