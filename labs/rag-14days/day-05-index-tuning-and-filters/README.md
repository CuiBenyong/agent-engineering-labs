# D5 实验：同一份数据在两种索引与三组参数下的召回与延迟对照，加一份带租户过滤的查询实现

> 目标：把「该用 HNSW 还是 IVFFlat、参数该调多大、要不要上量化、带条件的检索为什么会漏」
> 这四个问题，从争论变成一张你自己跑出来的表。做完之后你手里会有一份写着数据规模的选型备忘，
> 而不是一堆从博客上抄来的经验值。

## 你会学到

- 给同一张表分别建两种索引，记录建索引耗时与占用空间
- 固定一批查询，扫描关键参数，画出召回与延迟的取舍曲线
- 把向量列换成半精度重跑一遍，对比空间、速度与召回的变化
- 加一个租户字段做带过滤的检索，构造一个会漏召回的场景并修好它
- 把三组结论写成一页选型备忘，列明每条结论成立的数据规模

## 目录

- `corpus/`：三十篇虚构的「云梯科技」语料，与 D1 逐字相同的一份副本（**不要改，也不要对它跑格式化**：`doc-005` 那张排版错乱的表格是 D3 的教学素材）
- `docker-compose.yml`：带 pgvector 扩展的 PostgreSQL，映射到宿主 **5555** 端口
- `starter/`：挖了 4 个练习的起始代码，原样也能跑完整流程，只是数字全是错的
- `solution/`：参考答案，跑完会在自己目录下写出 `report.md`

两个目录的 `src/` 结构一样：

| 文件         | 作用                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| `embed.ts`   | 全课统一的 embedding 接口，与 D2 的 `embed.ts` 逐字相同的一份副本，本天不改 |
| `dataset.ts` | 读语料、切块、用确定性伪随机把行数补到 `SCALE`，并给每行分配租户            |
| `db.ts`      | 连库、建表、灌数据、量表和索引大小                                          |
| `bench.ts`   | 一次查询、召回率、参数扫描、执行计划                                        |
| `index.ts`   | 把上面这些按顺序跑一遍并输出报告                                            |

## 怎么跑

```bash
# 1. 先起库（在本 README 所在目录执行，不是 starter/solution 里）
docker compose up -d

# 2. 再跑实验
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 想用真 embedding 就填 OPENAI_API_KEY；只想看索引行为就一直用 MOCK=1
MOCK=1 pnpm start     # 离线：不需要网络、不需要 key，但需要上面那个库
EMBED_BACKEND=mock pnpm start  # 同上，D2 定的写法：哈希向量 + 真实 pgvector
SCALE=5000 MOCK=1 pnpm start   # 机器慢就把行数调小，结论方向不变
```

跑完要看到的是一串表格，最后一段是「一页选型备忘」，同时 `report.md` 已经写好。

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

### 数据规模是怎么来的（重要）

三十篇语料只能切出 87 块。**几百个向量的规模上 HNSW 和暴力扫描没有任何区别，参数扫描出来全是噪声**，
所以本实验在真语料之上做了一次可复现的合成扩增，把行数推到 `SCALE`（默认 20000）：

- 先把 `corpus/` 的 30 篇按段落切成 87 个真块，它们原样入库。
- 再用固定种子的 mulberry32 伪随机（`dataset.ts`，种子写死 20260906）从真块的句子池里随机取 2–4 句拼成合成块，补齐到 `SCALE` 行。同一台机器、同一个 `SCALE` 跑两次，数据完全一样。
- 合成块**只在内存里生成，不落盘、不写进 `corpus/`**。它们不用来回答问题，只用来把向量空间填到有密度——本天量的是索引行为，不是检索效果。
- 租户按行号确定性分配（`i % 100 === 7` 归到 `t07`），所以稀有租户正好占 1%，且与内容无关。

### MOCK 说明

`MOCK=1`（等价于 `EMBED_BACKEND=mock`）只替换 embedding 这一个外部依赖，换成全课统一的确定性哈希向量：
文本转小写去空白后按 Unicode 字符切 2-gram，每个 2-gram 取 **UTF-8 字节**的 FNV-1a 哈希，对维度取模定下标、
最高位定正负，累加后 L2 归一化，维度 384。这份实现是从 D2 的 `embed.ts` 整份复制过来的，**本天不改**，
改了各天的向量就对不上。
这套向量保留的是**字面重合度**，不是语义，所以 **mock 用于验证代码路径，不用于验证检索效果**。

数据库这一侧没有 mock：本天要量的就是 PostgreSQL 的索引本身，用内存实现替代等于什么都没量。
连不上库时脚本会打印怎么起库然后干净退出。

## 验收标准

1. `MOCK=1 pnpm start` 跑完，输出里有 HNSW、IVFFlat、halfvec、二值量化四组表格，各带召回率与 p50 / p95。
2. HNSW 的 `ef_search` 从 10 调到 400，召回率单调上升、p50 也单调上升——你亲眼看到了这条取舍曲线。
3. IVFFlat 的 `lists` 取 `rows / 1000`，`probes` 从 1 调到 `lists` 时召回率能回到 100%，代价是延迟接近全表扫描。
4. 带 `tenant_id` 过滤的那一节里，默认配置**平均返回不足 1 条**（不是 10 条），开 `hnsw.iterative_scan` 之后回到 10 条、召回率回到九成以上。
5. `report.md` 最后一段「一页选型备忘」里的每一条都带着本次实测的数字和数据规模。

## 常见坑

1. **建 HNSW 索引报 `could not resize shared memory segment`。** Docker 默认只给容器 64MB `/dev/shm`，
   而 HNSW 的并行建图走共享内存。本 lab 的 `docker-compose.yml` 已经写了 `shm_size: 1gb`；
   你换别的 compose 文件时记得带上这一行。
2. **「召回率」量出来永远是 100%。** 十有八九是真值那一条查询自己也走了索引。
   真值必须 `SET LOCAL enable_indexscan = off` 强制全表扫描，否则你是在拿索引跟自己比。
3. **索引谓词里不能放绑定参数。** `create index ... where (tenant_id = $1)` 会直接报错，
   部分索引的条件只能是常量，所以每个租户都要单独建一条 DDL——这正是「每租户一套索引」不便宜的原因。
4. **迭代扫描不是万能解药。** 它修的是「结果条数不够」，不修「条数够了但排序不对」。
   在 IVFFlat 上你会看到开不开迭代扫描召回率一模一样，因为 `probes` 已经凑够了 10 条，只是凑得不准。
5. **同一台机器重跑两次，召回率会差一两个百分点。** HNSW 建图带随机性、延迟受负载影响。
   本天实测里半精度在 `ef_search = 40` 上甚至偶尔比全精度高一点，那不是量化变准了，那是噪声。
   看趋势和量级，不要盯小数点；要减小噪声就把 `SCALE` 和重复轮数调大。
