# D13 实验：一个带内容指纹增量同步、访问控制过滤、多级缓存与链路追踪的索引服务

> 目标：把 D7 那个「能查能答」的服务补上上生产前缺的最后一段——文档会变、人有权限差别、
> 重复问题不该每次都重算、出了问题要能查到是哪一步慢和贵。做完你会有一个跑得动的对账器、
> 一条把权限压进 SQL 的检索、三层各有失效规则的缓存，以及一份能指着说「就是这一段最贵」的追踪记录。

## 你会学到

- 实现基于内容指纹的增量索引器，支持新增、修改与删除三种变更
- 给文档加访问控制标签，把过滤条件下推到检索查询里
- 加两级缓存并写出各自的失效规则，构造一个必须失效却没失效的错误用例再修好
- 给一次完整问答加上分段计时与花费统计，输出一份追踪记录
- 写一份换 embedding 模型的迁移方案，说明怎么双写与切换

## 目录

```
day-13-incremental-and-acl/
├── docker-compose.yml    PostgreSQL 16 + pgvector，端口 5563
├── corpus/               30 篇「云梯科技」语料，与 D1 完全相同的副本
├── starter/              挖了 5 个练习点的起始代码
└── solution/             参考答案
```

`starter/src/` 与 `solution/src/` 是同样的八个文件：

| 文件        | 干什么用                                                        |
| ----------- | --------------------------------------------------------------- |
| `corpus.ts` | 读语料（来自 D1，本天不改）+ 造「第二次同步的来源快照」         |
| `chunk.ts`  | D3 的块结构与 `contentHash`（**练习 1**）                       |
| `embed.ts`  | D2 定下的 `embed()` 接口与三个后端，逐字照抄，本天不改          |
| `sync.ts`   | 三向对账与落库：新增 / 修改 / 删除 / 重传 / 重复（**练习 2**）  |
| `store.ts`  | 索引端口 + pgvector 实现 + 内存实现，权限过滤下推（**练习 3**） |
| `cache.ts`  | 三层缓存与它们各自的 key（**练习 4**）                          |
| `trace.ts`  | 最小 span 记录器与成本折算（**练习 5**）                        |
| `index.ts`  | 查询链路的编排 + 十项自测                                       |

三个模块边界是按「什么变了谁得跟着变」画的：来源变了动 `sync.ts`，
权限模型变了动 `store.ts`，模型或提示词变了动 `cache.ts` 的 key。
它们唯一的交点是 `cache.ts` 里那个索引版本号——同步改了索引就把它 +1，缓存自然作废。

## 怎么跑

零依赖跑法（不用 Docker、不用 key，几秒钟出结果）：

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
MOCK=1 pnpm start     # 跑完十项自测后退出，退出码等于「有没有 ❌」
```

真实链路（PostgreSQL + pgvector）：

```bash
cd ..                 # 回到 lab 根目录
docker compose up -d  # 起库，端口 5563
cd solution
EMBED_BACKEND=mock DATABASE_URL=postgres://rag:rag@localhost:5563/rag pnpm start   # 真库 + 哈希向量
DATABASE_URL=postgres://rag:rag@localhost:5563/rag pnpm start                       # 真库 + 真模型（要 key）
docker compose down -v
```

改单价看成本账怎么变（单价的单位是美元 / 每百万 token）：

```bash
PRICE_GEN_IN=0.8 PRICE_GEN_OUT=4 MOCK=1 pnpm start    # 换成便宜的生成模型，看四项占比怎么翻转
```

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `[ERR_PNPM_IGNORED_BUILDS]`，
> 这只是 pnpm 拦了 esbuild 的构建脚本，依赖已经装好了。以 `pnpm typecheck` 和自测结果为准。

### MOCK 说明

`MOCK=1` 换掉两个网络出口，其余一行不改：

- **向量化**：换成全课统一的确定性哈希向量（2-gram + FNV-1a + L2 归一化，384 维）。
- **生成**：不调模型，从排第一的那个块里挑出与问题字面最贴的一句返回。

对账、切块、入库、权限过滤、三层缓存、追踪与成本折算**全都真实执行**。
存储也不是打桩：没有 `DATABASE_URL` 时走内存实现，它把 pgvector 那套语义
（按文档整篇替换、删除连带块与向量、过滤先于排序、同分按 chunkId 决胜）重写了一遍，
所以离线跑出来的十项结果与真库**逐项一致**（已实测）。

一件必须记牢的事：**哈希向量保留的是字面重合度，所以 MOCK 下向量检索的行为接近关键词检索**。
**MOCK 验证的是代码路径，不是检索效果。**

同样地，**MOCK 下的延迟分布不代表真实系统**：生成那一段没有走网络，所以它只花几毫秒；
真实系统里它通常占整条链路九成以上的时间。追踪记录里可信的是「哪一段花了多少 token」，
以及你改了配置之后这个分布**怎么变**。

1. `MOCK=1 pnpm start` 在 solution 里 **10 项全 ✅**、退出码 0；在原样的 starter 里有 **5 项 ❌**，
   正好对应五个练习点。
2. 第 2 项打印「新增 doc-031｜修改 doc-006｜删除 doc-030｜重复 doc-032→doc-031」，
   且 `doc-005` 只把换行符换成 `\r\n` 之后仍被判为**未变**（练习 1 没做时它会被误判为修改）。
3. 第 3 项显示这次同步只向量化 **6 块**，而全量重建要 **151 块**，省了 96.0%。
4. 第 4 项显示 `doc-030` 从 `documents` 里消失，检索前 30 名里一条都捞不到，
   且 `chunks` 与 `embeddings` 两个计数相等（没有孤儿向量）。
5. 第 5、6 项显示：限定 `support` 之后比较的行数从 149 降到 26；行级过滤与索引隔离
   前 8 名**完全一致**，但前者「碰过 149 行」、后者「碰过 26 行」。
6. 第 7 项先复现出陈旧答案（索引已经是 500 MB，缓存还在答 200 MB），
   并且 hr 用户直接命中了 product 用户的答案；补全 key 之后两个现象同时消失。
7. `docker compose up -d` 之后带 `DATABASE_URL` 再跑一遍，十项结果与内存版完全一致。

## 常见坑

1. **`contentHash` 不做换行归一化，等于每次同步都全量重建。** 同一份文件从 Windows 传一次、
   从 Mac 传一次，字节不同、内容相同，指纹却对不上。它不报错，只是让你的账单看起来像在做全量。
   归一化要在**算指纹之前**做，不是在比较之后补救。
2. **删除不是一个事件，是一个缺席。** 只监听「文件变动」的同步器永远等不到「我不存在了」这条通知，
   所以必须**反过来遍历索引**，找出来源里已经没有的那些 id。漏掉这一步，被删的文档会一直出现在
   检索结果里——而这类幽灵通常是靠用户投诉发现的。
3. **权限过滤写在排序之后，等于没过滤。** 先全库排序取前 k、再筛掉不该看的，两个后果：一是越权的行
   已经参与了排序、挤掉了合法结果的名额（用户看到的结果变少甚至变空）；二是这条链路上任何一处
   忘记筛，数据就直接出去了。过滤必须和排序、`LIMIT` 在同一条查询里。
4. **缓存 key 少一样东西，那样东西就永远不会让它失效。** 这是本天最贵的 bug，因为它不报错，
   只是安静地一直给旧答案。写完 key 之后逐条自问：索引变了会不会失效？换个人问会不会串？
   换模型、改提示词会不会失效？三个问题里有一个答不上「会」，key 就是错的。
5. **别拿索引版本去作废向量缓存。** 向量是内容寻址的：文本没变、模型没变，向量就没变。
   把索引版本塞进 L3 的 key，一次同步就把几万条向量全作废，正好回到了全量重建。
