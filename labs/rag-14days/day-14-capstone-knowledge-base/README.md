# D14 实验：一个多租户、带引用与评估报告的企业知识库问答项目，以及一页 RAG 决策地图

> 目标：把前十三天的零件装成一个**能放进作品集**的项目——两个工作区各有自己的索引、回答带可点击的引用、
> 拒答按原因分开记账、指标按租户分开统计，最后用一张决策地图把自己的每一个配置复核一遍。
> 它值得做的地方不在代码量，而在**你能拿着它回答面试里那五个追问**。

## 你会学到

- 多租户的三处落点：摄取时打标、检索时过滤、评估时分租户统计
- 把第八天的一次性评估脚本做成一份可以持续看、可以贴进项目说明的面板
- 把「答不出来」拆成四类可归因的失败模式，每一类指向一条不同的排查路径
- 一张 RAG 决策地图：四个输入推出十个旋钮，每条建议都指得出它出自哪一天的哪个实测结论
- 用地图复核一份**已经在跑**的配置，把不一致的地方逐条解释掉

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
MOCK=1 pnpm start     # 零依赖：哈希向量 + 内存索引，跑完自测退出

# 想跑真数据库（多一项内存与 pgvector 的并排校验）
cd .. && docker compose up -d
cd solution && MOCK=1 DATABASE_URL=postgres://rag:rag@localhost:5564/rag pnpm start
```

> `starter/` 与 `solution/` 都不属于仓库根 pnpm workspace，`pnpm install` 时要加 `--ignore-workspace`。
> 安装最后可能打印一行 `[ERR_PNPM_IGNORED_BUILDS]` 并以非 0 退出，那不代表安装失败——看 `pnpm start` 跑不跑得起来。

### MOCK 说明（每天都要读一遍的那一段）

`MOCK=1` 下换掉的是两个外部依赖：embedding 走确定性哈希向量，重排走词元重合度替身，生成不调模型
（从命中块里挑出与问题字面重合最高的那一句，配上块编号）。**哈希向量保留字面重合度，所以离线模式下
向量检索的行为接近关键词检索**——它验证的是代码路径（打标有没有生效、谓词有没有下推、名次有没有被融合改写、
引用校验有没有真的拦下东西），**不验证检索效果**。

所以本天报告里的数字要分两类看：

- **可以直接讲的**：块数、租户分布、候选池构成、失败分类、token 数与调用次数。它们由实现结构决定，
  换成真模型也不会变。
- **只能当量级看的**：任何「提升幅度」。想要真实幅度，去掉 `MOCK=1`，配上 `OPENAI_API_KEY`
  与 `COHERE_API_KEY`（或自部署的 `RERANK_BASE_URL`）再跑一遍。
- **金额一律是占位单价**（写在 `panel.ts` 顶部，可用 `PRICE_GEN_IN` 等环境变量覆盖）。
  账里唯一由实测撑着的是 token 数。

## 练习点

`starter/` 挖了 5 个练习，**原样跑起来 9 项里有 6 项是 ❌**（第 9 项是连带的——
闸门本来就该拦住一个比基线更差的版本）。每做完一个就有一项翻绿，把它当进度条用。

1. `corpus.ts` 的 `ingest()`：按租户订阅范围投影，而不是所有租户共用一批文档。
2. `store.ts` 的 `MemoryVectorStore.search()`：把范围谓词挪到打分之前。
3. `retrieve.ts` 的 `rrfFuse()`：实现倒数排名融合（规格照抄 D9，同分要按 id 兜底）。
4. `panel.ts` 的 `aggregateByTenant()`：分组键用 `tenantId`。
5. `panel.ts` 的 `ledger()` 里那笔费用折算：单价的单位是「每百万 token」。

## 验收标准

1. `MOCK=1 pnpm start` 跑完，`solution` 九项全部 ✅、退出码 0；原样的 `starter` 有六项 ❌。
2. 摄取那一项打印「总部工作区 134 块 / 试用工作区 44 块」，块 id 形如 `t-yunti/doc-001#c01`；
   拿试用工作区问一个工程问题，走的是 `out-of-tenant-scope` 而不是「资料中没有找到」。
3. 客服范围（23 块）下向量一路返回 23 条——前置过滤的条数不会被悄悄砍掉；跨租户块 0 条。
4. 面板主表里两个工作区**不是同一行**：召回率 93.8% 对 100.0%、拒答率 0.0% 对 20.0%，
   而全局平均把它们抹成召回 95.2% / 拒答 15.8% 一行。
5. 失败模式分成三类各自列出题号：`t-yunti/q06` 是「答案文档没进候选池」，
   `t-yunti/q13` 是「引用与句子对不上」，另外 16 题是「该拒答却答了」。
6. 决策地图对着本项目实际配置报出 2 处不一致（`queryRewrite`、`evalCadence`），每处都带依据；
   把输入换成五百万篇 / 秒级 / 准确度优先，索引读出 `dedicated`、同步读出 `incremental`。

起了容器数据库再跑一遍会多出第 10 项：**内存索引与 pgvector 排出逐条相同的名次**，
十项全绿。那一项是「内存版可以拿来做评估」这个说法的全部依据。

## 常见坑

1. **多跳题的失败诊断不能用 `some()`。** 一道 multi 题少一篇就算没中，而少的那一篇病在哪一层
   跟已经捞到的那篇无关。用「答案文档里有没有任意一篇进了候选池」去判，会把 `q06` 那种
   「第一篇稳稳排第一、第二篇一次都没出现」误判成预算问题，然后你去调预算，调一整天也没用。
   正确做法是只诊断**缺的那几篇**。
2. **空集合的平均值是 0，但「0.0%」和「这一档没有题」是两件事。** 试用工作区一道多跳题都没有，
   面板上印 `0.0%` 会让人以为多跳全崩了。这是评估报告里最常见、也最伤人的一种谎，面板里用 `—` 区分。
3. **BM25 索引按租户建，不按部门建。** 逆文档频率是语料统计量，共用一张索引意味着
   A 租户导入一万篇就改变了 B 租户看到的词权重（D5 那条「大客户挤掉小客户」的关键词版）；
   反过来按部门建，同一个租户内部的词权重会因为「这次是客服在问」而变，也不对。
   权限收窄发生在候选过滤那一步，不在统计量这一层。
4. **报告里的时间戳要固定。** 每跑一次就 diff 一行 `generatedAt`，两周之后没人愿意看这份 diff，
   面板也就没人再看了。本实验把它写死成一个固定值，真做成服务时应该把它挪到文件名或元数据里。
