# 审计日志字段表（示范）

> 对象同样是 D4 那个服务端。先写问题，再倒推字段。

## 第一步：我要能回答的问题

1. 昨天 14 点到 15 点，谁调用了 `book_meeting`？
2. 某个会议是被哪一次对话创建的？是用户点了确认，还是模型自己决定的？
3. 那次调用用的令牌是发给谁的？带了哪些作用域？
4. 上周 `analyze_corpus` 的 P95 耗时是多少？有没有在某个时间点突然变慢？
5. 有没有人拿着一个校验不通过的 `requestState` 反复试？试了多少次、从哪来？
6. 一次多轮请求的两半（第一轮 `input_required`、第二轮带输入重试）能不能串起来看？

## 第二步：字段表

| 字段                 | 类型       | 示例                                          | 能回答第几问 | 敏感吗                    |
| -------------------- | ---------- | --------------------------------------------- | ------------ | ------------------------- |
| `ts`                 | 时间戳     | `2026-09-06T14:03:11.244Z`                    | 1、4         | 否                        |
| `request_id`         | 字符串     | `req_7f3a91`                                  | 2、6         | 否                        |
| `correlation_id`     | 字符串     | `conv_2214`                                   | 2、6         | 否                        |
| `principal`          | 字符串     | `user_8812`                                   | 1、2、5      | 是（用内部 id，不用邮箱） |
| `client`             | 对象       | `{"name":"d5-mini-client","version":"0.1.0"}` | 2            | 否                        |
| `method`             | 字符串     | `tools/call`                                  | 1            | 否                        |
| `tool_name`          | 字符串     | `book_meeting`                                | 1、4         | 否                        |
| `args_digest`        | 字符串     | `sha256:9c1f…`                                | 2            | 否                        |
| `args_keys`          | 字符串数组 | `["topic","attendee_email"]`                  | 2            | 否                        |
| `result_type`        | 枚举       | `complete` / `input_required`                 | 6            | 否                        |
| `is_error`           | 布尔       | `false`                                       | 4            | 否                        |
| `duration_ms`        | 整数       | `812`                                         | 4            | 否                        |
| `token_audience`     | 字符串     | `https://mcp.example.com/mcp`                 | 3            | 否                        |
| `token_scopes`       | 字符串数组 | `["files:read"]`                              | 3            | 否                        |
| `confirmed_by_human` | 布尔       | `true`                                        | 2            | 否                        |
| `state_verify`       | 枚举       | `ok` / `bad_signature` / `expired` / `absent` | 5            | 否                        |
| `protocol_version`   | 字符串     | `2026-07-28`                                  | 4            | 否                        |
| `remote_ip`          | 字符串     | `203.0.113.7`                                 | 5            | 是（按留存策略裁剪）      |

三个字段值得单独说：

- **`args_digest` 加 `args_keys`，不记参数全文。** 摘要能回答「是不是同一组参数」，字段名能回答「调用形状对不对」，
  两者合起来足够排查绝大多数问题，又不会把用户输入原样落盘。真需要看全文时走单独的、有审批的调试开关。
- **`confirmed_by_human`。** 这一栏是事后区分「用户授意」和「模型自作主张」的唯一依据。
  没有它，第 2 问永远答不出来。
- **`state_verify`。** 把 `requestState` 的校验结果单独成列，第 5 问才能变成一次简单的聚合查询，
  而不是从错误日志里捞文本。

## 第三步：不许记进日志的东西

- 访问令牌、刷新令牌、`Authorization` 头的任何部分（只记受众与作用域，那是结论不是凭证）。
- `requestState` 的原文（只记校验结果；要定位问题就记它的前 8 位加长度）。
- 工具参数全文（用摘要加字段名代替）。
- 邮箱、手机号、身份证件号（`book_meeting` 的 `attendee_email` 正好属于这一类，
  所以它只出现在 `args_keys` 里，值不落盘）。

**参数里夹带敏感值时的处理**：默认整段不记，只记字段名与摘要。
需要按值排查时，用「字段级白名单」显式列出可以记全文的字段，而不是反过来做黑名单——黑名单永远漏。

## 第四步：留存与检索

**留存 90 天。** 依据是排查窗口：绝大多数「上个月那次是谁干的」的问题发生在 30 天内，
90 天留出两倍余量；再长的话，`remote_ip` 这类个人相关字段的存储合规成本会超过它的排查价值。
安全事件确认之后，相关时间段的日志单独归档，不受 90 天限制。

**检索**：日志写成一行一条 JSON，按 `ts` 分区，`principal` / `tool_name` / `correlation_id` 三个字段建索引。
最常跑的三条查询是「某人某段时间的全部调用」「某个工具的耗时分布」「某次对话的完整调用链」，
分别对应这三个索引。
