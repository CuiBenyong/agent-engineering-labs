# MCP 服务端安全检查清单（示范）

> 填的对象：`labs/mcp-7days/day-04-streamable-http-deploy/solution`，也就是 D4 那个 Streamable HTTP 服务端。
> 填写日期：2026-09-06。
>
> **这是一份示范，不是标准答案。** 它的价值在于让你看清楚「证据」那一格该长什么样：
> 每一条要么指向一行代码，要么指向一条能重跑的命令。
> 注意示范里有好几条是**红的**——一个课堂用的服务端本来就不该假装自己生产就绪。

---

## A. 传输与来源

| #   | 条目                               | 现状   | 证据                                                                                                                                                              | 风险                                                                                  | 计划                                                                           |
| --- | ---------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| A1  | 校验 `Origin`，非法回 403          | 是     | `server.ts:235` 调 `originAllowed`；`curl -s -o /dev/null -w '%{http_code}' -X POST http://127.0.0.1:3034/mcp -H 'origin: https://evil.example.com' …` 返回 `403` | 不做就是 DNS 重绑定的入口：任意网页能驱使浏览器打到本机端点，接管一个能读文件的服务端 | 保持                                                                           |
| A2  | 本机只绑回环                       | 是     | `server.ts:281`，默认 `BIND_HOST=127.0.0.1`；容器里才由 compose 映射端口                                                                                          | 绑 `0.0.0.0` 等于把本机服务端暴露给同网段的任何人                                     | 保持                                                                           |
| A3  | 本机优先 stdio；用 HTTP 时要求令牌 | **否** | 这个端点没有任何认证，任何本机进程都能调                                                                                                                          | 同一台机器上的其它进程（包括浏览器扩展、恶意 npm 包的 postinstall）可以直接驱动它     | **修**：本机模式下要求一个启动时生成的随机 bearer 令牌，或者改走 unix 域套接字 |
| A4  | 日志只走 stderr                    | 不适用 | 这是 HTTP 传输，stdout 不承载协议消息                                                                                                                             | stdio 传输下 stdout 多一个字就会让客户端的 JSON 解析失败                              | 保持                                                                           |

## B. 授权与令牌

| #   | 条目                     | 现状   | 证据                                         | 风险                                                                                    | 计划                                     |
| --- | ------------------------ | ------ | -------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------- |
| B1  | 校验令牌受众             | **否** | 全项目搜 `authorization` 头零命中            | 规范要求 MCP 服务端作为受保护资源必须校验令牌是发给自己的，不校验就会接受别处签发的令牌 | **修**：上公网前必须做；本机课堂环境暂缓 |
| B2  | 不接受也不转接别处的令牌 | 不适用 | 没有下游调用，没有令牌流转                   | 令牌转发是规范明令禁止的反模式：绕过限流与审计、打穿信任边界                            | 加下游依赖时同步补 B1、B2、B3            |
| B3  | 调下游用服务端自己的凭证 | 不适用 | 三个工具全是纯计算，不出网                   | 同上                                                                                    | 同上                                     |
| B4  | 第三方凭证不经由客户端   | 不适用 | 同上                                         | 第三方令牌经客户端转手，等于把它交给一个你控制不了的进程                                | 同上                                     |
| B5  | 实现受保护资源元数据     | **否** | 没有 `/.well-known/oauth-protected-resource` | 客户端无从发现该找哪个授权服务器，只能靠人工配置                                        | 与 B1 一起做                             |
| B6  | 最小权限作用域           | 不适用 | 没有授权层                                   | 万能作用域会把一次令牌泄漏放大成全量失守                                                | 与 B1 一起做                             |

## C. 状态句柄与请求状态

| #   | 条目                                                | 现状   | 证据                                                                                                         | 风险                                                           | 计划               |
| --- | --------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- | ------------------ |
| C1  | 句柄安全随机                                        | 不适用 | 这个服务端没有跨调用的业务句柄，只有 `requestState`                                                          | 可猜的句柄等于把别人的购物车挂在公网上                         | 加购物车类工具时补 |
| C2  | 句柄绑主体                                          | 不适用 | 同上                                                                                                         | 规范明说不得把「持有句柄」当成身份认证                         | 同上               |
| C3  | 每次调用重新鉴权                                    | 不适用 | 同上                                                                                                         | 同上                                                           | 同上               |
| C4  | 句柄有过期                                          | 不适用 | 同上                                                                                                         | 过期能显著缩小被捡到之后的可用窗口                             | 同上               |
| C5  | `requestState` 做了完整性保护并签进主体、来源、过期 | 是     | `protocol.ts` 的 `signRequestState` / `verifyRequestState`；`selftest.ts` 第 8 项专门验被篡改的 state 会被拒 | 它经客户端转手，是攻击者可控输入；不验签就能被改写成任意上下文 | 保持               |
| C6  | 定长比较                                            | 是     | 用 `crypto.timingSafeEqual`，且先比长度再比内容                                                              | 按字节提前返回会泄漏比对进度，理论上可被用来逐位爆破签名       | 保持               |

> C5 的补充：签名只能**缩小**重放窗口，挡的是跨用户、跨请求和超时三种复用。
> 要求一个 state 只能兑一次的场景（比如一次性优惠券），必须另外在服务端加一层消费记录。这里没有这种场景。

## D. 不可信输入

| #   | 条目                           | 现状   | 证据                                                                                               | 风险                                                                                 | 计划                                                 |
| --- | ------------------------------ | ------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| D1  | 客户端把描述与注解当不可信输入 | **否** | D5 的 `registry.ts` 里，`def.description` 只加了一句来源前缀就进了给模型的工具表，没有任何边界标注 | 服务端作者（或被投毒的服务端）可以往描述里写指令，和你自己的系统提示同处一个信任层级 | **修**（这是本次复现的那一条，见 `attack-repro.md`） |
| D2  | 工具返回进上下文前有处理       | **否** | D5 的 `resultText` 把文本原样拼进消息                                                              | 工具返回同样是外部可控文本，注入面和描述一样大，而且更新更频繁                       | 修：加长度上限与来源标注，与 D1 一起做               |
| D3  | 破坏性工具执行前向人确认       | **否** | D5 的客户端没有确认环节，`close_ticket` 说调就调                                                   | 一次成功的注入可以直接产生副作用，而不只是骗出几句话                                 | **修**：优先级高于 D1，因为它挡的是后果不是入口      |
| D4  | 服务端校验全部工具输入         | 部分   | `tools.ts` 三个工具都按 schema 取值并做了类型判断；但没有对 `documents` 的条数与总长度设上限       | 超大输入是最廉价的拒绝服务；参数直接拼进 shell 或 SQL 则是命令注入                   | 修：补输入规模上限                                   |
| D5  | 服务端清洗输出                 | 是     | 三个工具的返回都是自己构造的字符串，不透传上游内容                                                 | 原样转发上游 HTML 或控制字符，会把上游的注入直接搬进用户的上下文                     | 接入真实上游 API 时重新评估                          |
| D6  | 跨服务端数据流同样审查         | 不适用 | 单服务端，无跨服务端数据流                                                                         | A 的返回喂给 B 时，如果只审查了直接调用，等于留了一条绕过路径                        | 做代码模式或多服务端编排时补                         |

## E. 代理型服务端

整节**不适用**：这个服务端不代理任何第三方 API，没有静态 client id，也不做动态客户端注册。
混淆代理需要「静态 client id + 允许客户端动态注册 + 第三方设了同意 cookie + 缺少按客户端的同意确认」四个条件同时成立，
这里一个都不成立。

> 但要记住判断方法：只要你的服务端开始**代表用户去第三方拿令牌**，E 整节立刻从「不适用」变成「必须做」。

## F. 客户端侧的义务

| #   | 条目                            | 现状   | 证据                                  | 风险                                                                | 计划                         |
| --- | ------------------------------- | ------ | ------------------------------------- | ------------------------------------------------------------------- | ---------------------------- |
| F1  | 只接受 http 与 https 的授权 URL | 不适用 | D5 的客户端不走 OAuth                 | `javascript:` 形式的授权 URL 会让客户端在自己的上下文里执行任意脚本 | 客户端接远程服务端时必须先做 |
| F2  | 打开 URL 不经过 shell           | 不适用 | 同上                                  | 经 shell 打开等于把 URL 交给命令解释器，直接是远程代码执行          | 同上                         |
| F3  | 防 SSRF                         | 不适用 | 同上                                  | 恶意服务端可以把发现用的 URL 指向云元数据地址，骗客户端去取凭证     | 同上                         |
| F4  | 一键配置前展示完整启动命令      | 不适用 | D5 的服务端由代码里写死，不走一键配置 | 一条启动命令就是一次任意代码执行，截断展示等于把危险部分藏起来      | 做配置界面时必须做           |

## G. 审计日志

| #   | 条目                       | 现状   | 证据                     | 风险                                                   | 计划                                  |
| --- | -------------------------- | ------ | ------------------------ | ------------------------------------------------------ | ------------------------------------- |
| G1  | 每次工具调用一条日志       | **否** | 只有零散的 `console.log` | 出事之后无法回答「谁、什么时候、调了什么、结果是什么」 | **修**：按 `audit-log-fields.md` 落地 |

| G3  | 可按用户 / 工具 / 时间检索 | **否** | 没有结构化日志           | 排查一次事故要肉眼翻文本                               | 与 G1 一起做                          |
| G4  | 提权事件单独记             | 不适用 | 没有授权层               | 说不清一个令牌是怎么一步步拿到高权限的                 | 与 B1 一起做                          |

## 自评

适用 26 条，做到 8 条，明确没做到 8 条，其余不适用。

**结论：这个服务端可以留在本机当教学与调试用，不能上公网。** 上公网前的最小集是
B1（受众校验）、B5（受保护资源元数据）、G1（审计日志）、A3（本机模式的令牌）。

**这次复现挑的是 D1**——不是因为它最好复现，而是因为它的前置条件最低：
攻击者不需要拿到任何凭证，只需要能影响一段会被读进上下文的文本。
