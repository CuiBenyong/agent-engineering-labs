# D6 实验：一份填好的 MCP 服务端安全检查清单与复现记录

> 目标：把「MCP 有哪些安全问题」从一份读过的清单，变成一份**填过的**清单——每一条都有你自己项目的现状、证据和判断。然后挑一条没做到的，在本机真的打一次，把现象记下来。今天的产出是文档，不是程序，但每一格「证据」都必须是你跑出来的。

## 你会学到

- 读 solution 的检查清单，理解每一条对应的是哪一类攻击
- 在 starter 的清单里逐条填写你自己服务端的现状与证据
- 挑一条你没做到的，在本地复现一次并把现象记下来
- 为这一条写出修复方案与验证方法
- 补上审计日志字段表，说明每个字段在事后能回答什么问题

## 目录

这一天**没有代码**，所以不需要 `pnpm install`、不需要 `MOCK=1`、也没有自检脚本。

- `starter/`：三份挖空的模板，表格骨架和提示问句都写好了，待填处是 `TODO`
- `solution/`：填好的示范，对象是 `labs/mcp-7days/day-04-streamable-http-deploy/solution`

两个目录里的文件一一对应：

| 文件                    | 干什么用                                                |
| ----------------------- | ------------------------------------------------------- |
| `security-checklist.md` | 七组共 26 条的检查清单，逐条填现状 / 证据 / 风险 / 计划 |
| `attack-repro.md`       | 挑一条没做到的，在本机复现并记录                        |
| `audit-log-fields.md`   | 先写「出事之后要能回答什么问题」，再倒推字段            |

**顺序是固定的**：`security-checklist.md` → `attack-repro.md` → `audit-log-fields.md`。
先把面铺开，再往下扎一个点，最后补上事后能救你的那一层。

## 怎么用

1. 先选对象。默认是 D4 的服务端；**有自己的项目就用自己的**，这份清单的价值全在填的是真东西。
2. 通读 `solution/security-checklist.md`。**重点不是抄结论，是看「证据」那一格长什么样**：
   要么是一个 `文件:行号`，要么是一条能重跑的命令加它的输出。示范里有 8 条是红的——
   一个课堂用的服务端不该假装自己生产就绪，你的也一样，红了不丢人，填成绿的才丢人。
3. 回到 `starter/security-checklist.md` 逐条填。填不动的条目说明那一条你还没看懂，
   回去看正文对应的小节，或者读规范里安全最佳实践那一页。
4. 挑一条**没做到**的去 `attack-repro.md` 复现。挑选原则：优先挑「一旦被利用后果最重」的，
   不是最好复现的那条。推荐题目（工具描述里的提示注入）只需要 D5 的实验目录，不联网、不花钱。
5. 最后填 `audit-log-fields.md`。**先写问题再写字段**，顺序反了就会写出一堆没人查的字段。

## 验收标准

1. `starter/security-checklist.md` 里适用的条目全部填完，**没有一格「证据」是「应该做了」「印象中有」这类话**；
   每条填了「不适用」的都写清了为什么不适用。
2. 每一条「否」都写出了具体风险——不是「不安全」，而是「攻击者能拿这一条做什么」。
   写不出来的，说明这条还没看懂，回去补。
3. `attack-repro.md` 的第 3 节能被别人照着敲一遍复现出同样现象；第 4 节贴的是**你自己跑出来的输出**。
4. 第 6 节的修复方案能说清它挡住的是链条上的哪一环，且第 7 节的验证方法是**可重复执行**的
   （「我看了一眼代码」不算验证）。
5. `audit-log-fields.md` 里每个字段都对应至少一个问题，每个问题都至少有一个字段能回答；
   敏感字段的处理写的是具体做法，不是「注意脱敏」。

## 常见坑

1. **把清单填成愿望单。** 「计划：以后加上」写满一屏，等于什么都没做。每条「否」后面要么写「修，什么时候修」，
   要么写「不修，因为这个风险在我的场景里可以接受，理由是……」。**明确决定不修，比含糊地打算修强得多。**
2. **拿注解当权限判据。** 规范要求客户端把工具注解当成不可信输入。`readOnlyHint: true` 是服务端的自我声明，
   不是安全证明。要不要弹确认框可以参考它，谁能调什么绝不能依赖它。
3. **只防入口，不防后果。** 提示注入的防线是概率性的，没有一条能保证挡住。真正靠谱的是把后果卡住：
   破坏性操作执行前向人确认、界面上显示每一次工具调用。**先做后果那一层，再回头做入口。**
4. **复现完就算完。** 没写验证方法的复现是半份工作。第 7 节要能在修完之后原样再跑一遍，
   而且要顺手验一条容易被忽略的事：加了确认与拦截之后，被拒绝的调用**不能把整轮对话打断**。
5. **审计日志记参数全文。** 图省事把 `arguments` 整个落盘，等于把用户输入连同里面可能夹带的敏感值一起长期留存。
   用摘要加字段名，需要看全文时走单独的、有审批的调试开关。
6. **E 组一律填不适用。** 只要你的服务端开始代表用户去第三方拿令牌，混淆代理那一组立刻从「不适用」
   变成「必须做」。判据是「我有没有替别人去要授权」，不是「我是不是叫代理」。
