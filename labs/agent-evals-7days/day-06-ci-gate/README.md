# D6 实验：回归门禁

今天给 `evalkit` 加上最后一块工程件：**一条能拦住合并的门禁。**

跑完这一天，你手里会有一条命令：它读基线、跑评估、判断这次下降是抖动还是退化，
并在真的退化时**以非零退出码结束**——那是它能被流水线当回事的唯一前提。

## 你会拿到什么

| 文件                  | 说明                                               |
| --------------------- | -------------------------------------------------- |
| `src/core/types.ts`   | 五个核心名词的类型（**冻结文件，与 D1 逐字相同**） |
| `src/core/runner.ts`  | 试次执行器与两个指标（**冻结文件**）               |
| `src/agent/target.ts` | 靶子 Agent（**冻结文件**）                         |
| `src/agent/mock.ts`   | 可复现的随机源（**冻结文件**）                     |
| `src/tasks/day06.ts`  | 冒烟档 3 条 + 全量档 8 条，带任务集版本号          |
| `src/ci/baseline.ts`  | 基线快照：环境指纹 + 分数，**有两处 TODO**         |
| `src/ci/gate.ts`      | 三态门禁与灰区复跑，**有两处 TODO**                |
| `src/ci/weaken.ts`    | 削弱装饰器：用来人为制造一次退化（已给全）         |
| `src/index.ts`        | 门禁 CLI：`--record` / 跑门禁 / `--noise`          |
| `scripts/selftest.ts` | 十一条不变量自检，**它就是今天的验收标准**         |

## 跑起来

```bash
cd starter
pnpm install --ignore-workspace
MOCK=1 pnpm selftest        # 现在应该红 7 项，这是正常的
```

> `pnpm install --ignore-workspace` 可能以非 0 退出并打印 `[ERR_PNPM_IGNORED_BUILDS]`，
> 这**不代表安装失败**。看 `node_modules` 有没有生成、以及 `pnpm typecheck` 过不过，那两个是准的。

## 今天的练习

1. **`baseline.ts` 的 `toScores`** —— 把一次运行折算成三个比率与逐任务分数。
   所有数字过一遍 `round4`，并且**不许放时间戳**：这一块必须做到同种子两次逐字相同。
2. **`baseline.ts` 的 `compareFingerprint`** —— 逐字段比对环境指纹，返回不一致的字段名。
   返回空数组是最危险的错误答案：它会让你拿换了模型之后的分数去和旧基线比。
3. **`gate.ts` 的 `judge`** —— 三道判定：指纹、逐任务全绿变全红、总分区间。顺序不能换。
4. **`gate.ts` 的灰区复跑** —— 只对灰区加大样本重跑一次，再判警告还是拦截。

做完之后：

```bash
MOCK=1 pnpm selftest        # 十一项全绿才算过
```

## 手动验收清单

自检全绿**不等于**做完了。下面这条完整流程要你亲手走一遍，
**它演示的正是「门禁真的拦得住」这件事**——而一条从没红过的门禁，
和一条永远放行的门禁，在流水线上长得一模一样。

```bash
cd solution      # 或做完练习的 starter
pnpm install --ignore-workspace
```

- [ ] **第一步：先看噪声，再定阈值。**

      ```bash
          MOCK=1 pnpm start -- --noise 30
          ```

          实测输出（全量档 8 条任务、k=5、30 个种子）：

          ```text
          噪声实测：full 档 8 条任务，k=5，30 个种子
            区间 0.8500 – 0.9750
            均值 0.9167　最大单轮偏离均值 0.0667
          ```

          **同一个 Agent、同一套判据、什么都没改，通过率就能差 12.5 个百分点。**
          再看一眼冒烟档：`--noise 30 --tier smoke` 的区间是 `0.8000 – 1.0000`，
          整整 20 个百分点。任务越少噪声越大，这是分档要付的代价。

- [ ] **第二步：记录基线。**

      ```bash
          MOCK=1 pnpm start -- --record
          cat work/baseline.json
          ```

          打开那个文件，确认里面除了分数还有 `fingerprint`（模型、提示词版本、
          任务集版本、evalkit 版本、k、档位）和 `seed`。
          **少记任何一样，下次分数变了你都说不清是谁动的。**

- [ ] **第三步：基线正常，门禁放行。**

      ```bash
          MOCK=1 pnpm start ; echo "退出码 $?"
          ```

          期望：`门禁：通过`，退出码 `0`。

- [ ] **第四步：换种子再跑几次，门禁仍然放行。**

      ```bash
          MOCK=1 pnpm start -- --seed 1097 ; echo "退出码 $?"
          MOCK=1 pnpm start -- --seed 2261 ; echo "退出码 $?"
          ```

          这一步验的是**不误报**。一条天天误报的门禁，三周之内就会被团队学会跳过。

- [ ] **第五步：制造一次真实退化，门禁必须拦下。**

      ```bash
          MOCK=1 pnpm start -- --weaken 0.35 ; echo "退出码 $?"
          ```

          期望输出（退出码 `1`）：

          ```text
          门禁：拦截
            基线通过率 92.5%　本次 57.5%
            · 总体通过率下降 35.0 个百分点，超过拦截线 20.0 个百分点，已远离噪声区间。
          ```

          `--weaken` 把靶子包了一层「有一定概率多退一笔款」的缺陷——
          **它不改 `target.ts`**（那是冻结文件），只在外面套一个装饰器。

- [ ] **第六步：看一次灰区复跑。**

      ```bash
          MOCK=1 pnpm start -- --record --seed 4201    # 记在一个偏幸运的种子上
          MOCK=1 pnpm start -- --seed 1097             # 对比一个偏倒霉的种子
          ```

          期望：`门禁：警告`，输出里有 `已触发灰区复跑（k=15）`，
          并且复跑后的差距收敛到警告线以内。**这一格就是灰区存在的理由**：
          单点差 12.5 个百分点，加大样本之后只剩 7.5 个。

          记得跑完把基线记回默认种子：`MOCK=1 pnpm start -- --record`。

- [ ] **第七步：量一下两档的成本差。**

      ```bash
          MOCK=1 pnpm start -- --record --tier smoke
          MOCK=1 pnpm start -- --record --tier full
          ```

          实测：冒烟档 15 次试次 / 36 次工具调用 / 3.77 分，
          全量档 40 次试次 / 105 次工具调用 / 10.42 分。
          离线跑没什么感觉，**换成真实网关就是 2.8 倍的账单和 2.8 倍的等待**。

- [ ] **第八步：确认指纹会拦住不可比的比较。**

      打开 `src/index.ts`，把 `PROMPT_VERSION` 改一个字，再跑一次门禁。
          期望：`门禁：拦截`，理由是「环境指纹不一致……这两次结果不可比」。
          改回来。**这条比分数阈值更重要**：拿换了提示词之后的分数去和旧基线比，
          得出的结论毫无意义，但它看起来非常正常。

## 接进流水线

门禁的接法只有一条要求：**拦截时退出码非零。** 剩下的都是配置问题。

```yaml
# 示意：每次提交跑冒烟档，打了 tag 才跑全量档
- run: MOCK=1 pnpm start -- --tier smoke
- run: MOCK=1 pnpm start -- --tier full
  if: startsWith(github.ref, 'refs/tags/')
```

基线文件要**进版本库**（本 lab 为了不留产物才写在 `work/` 下）。
基线进库之后，「重新记录基线」就变成了一次带审阅的提交——
这正是你想要的：放宽标准必须有人点头，而不是某个人在本地悄悄跑一下 `--record`。
