## 今天的练习

`src/health/suite-health.ts` 里有四处 TODO：

1. **`detectSaturation`** —— 连续多轮满分才算饱和，单轮不算。
2. **`detectAlwaysFailing`** —— 一次都没蒙对过的任务。注意措辞报的是「任务可疑」而不是「Agent 不行」。
3. **`detectGradingDefect`** —— 从失败理由里找「两个数字只差一点点」的模式，**并且同一条任务只报一次**。
4. **`detectUnrepresentativeBaseline`** —— 基线是不是记在了极值上。

### 练习 4 值得多想三分钟

它要回答的问题是：你那个基线数字，是不是恰好记在了运气特别好的那一次上？

如果是，之后每一次正常运行都会显得像退化，D6 那道门禁会长期误报。而**一个天天喊狼来了的门禁比没有门禁更糟**——它让所有人相信自己是有保护的，然后学会无视它。

写之前先想清楚一个边界：**如果所有运行的分数完全相同会怎样？**

那时候基线必然**同时**是最高和最低。如果你的判据是「基线大于等于最高值就报警」，它对每一个完全稳定的套件都会报警——一个恒真的检测器。

这个坑不是假设。写这份 solution 的第一版就踩了，跑出来的报告里赫然写着「基线 60.0% 落在最高端（区间 60.0%–60.0%）」，言之凿凿地报了一个不存在的问题。自检第 4 条就是为它加的。

## 手动验收清单

自检全绿**不等于**做完了。下面几条要你亲眼看一遍：

- [ ] `MOCK=1 pnpm start` 最后两行是判分缺陷的代价：
      **严格相等比较 0%，整数域比较 100%**。
      翻开 `src/graders/defective.ts` 看那两个评分器——退款金额一模一样，
      差距全部来自判分那三行代码。
- [ ] 报告顶部有**环境指纹**。想清楚：少了「任务集版本」这一行，
      这份报告下周还能和今天比吗？
- [ ] 体检报告里 `ev-703-broken` 被标成 `always-failing`。
      打开 `src/tasks/day07.ts` 看它坏在哪（prompt 里的订单号根本不在 seed 里）。
      这就是「0% 通过率先怀疑任务」的实物。
- [ ] 把 `src/tasks/day07.ts` 里 `ev-706-flaky` 那条**注释掉**再跑。
      套件不再抖，基线代表性检测应当**保持沉默**而不是报警。
      恢复它，报警回来。这一对是练习 4 的手动版变异检验。
- [ ] 读一遍报告末尾的「本轮要读的轨迹」清单。
      它同时给了失败样本和通过样本——想清楚为什么不能只给失败的。
