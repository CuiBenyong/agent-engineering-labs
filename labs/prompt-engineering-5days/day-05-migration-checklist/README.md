# D5 实验：一份跨模型迁移检查清单，并用它完成示例任务提示词的一次迁移

> 目标：做出一张以后每次换模型都能照着过的检查清单，并用它把「给 TODO API 补校验与测试」这份提示词从一家模型搬到另一家——搬之前把系统提示拆成三块，搬之后用 D4 的测试集验证有没有退步。
> 今天的产出是文档；「跑测试集」那一步复用 D4 的脚本，把 `PROVIDER` 换掉即可。

## 你会学到

- 读 solution 里填好的迁移检查清单，看每一项对应正文的哪一处差异
- 在 starter 里把示例任务的系统提示拆成通用规则、厂商适配、任务变量三块
- 按检查清单逐项过一遍，把每一项的检查结果与修改记录填进表格
- 用 D4 的测试集在目标模型上重跑，把通过率填进清单的验证栏

## 目录

这是**文档型实验**：`starter/` 与 `solution/` 各只有一份同名 Markdown，不需要 `pnpm install`、不需要 `MOCK=1`、没有自检脚本。

| 文件                     | 干什么用                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `migration-checklist.md` | 三部分：系统提示三块拆分、搬前搬后检查表、验证栏。starter 待填处是 `> TODO：`，solution 已填好 |

## 怎么用

1. 先通读 `solution/migration-checklist.md`，注意第二部分每一项右边的「对应差异」一栏——它告诉你这一项在防正文讲的四处断裂里的哪一处。
2. 回到 `starter/migration-checklist.md`，先填第一部分：把你 D1–D2 写好的示例任务提示词拆成「通用规则 / 厂商适配 / 任务变量」三块。判据写在模板里。
3. 填第二部分「搬之前」五项：对着你自己的提示词逐项检查，每项写「通过 / 需改」与一句修改记录。
4. 选一个目标模型（Claude 与 GPT 之间互搬，或搬到任何一家兼容 OpenAI 接口的国产模型），改「厂商适配」块，填「搬之后」五项。
5. 到 `labs/prompt-engineering-5days/day-04-prompt-ab-eval/solution`，把 `.env` 里的 `PROVIDER`（以及对应的 key 与模型 id）换成目标模型，`pnpm start` 跑一遍，把通过率与失败的 case id 填进第三部分。没有 key 就用 `MOCK=1` 走一遍流程，验证栏注明「MOCK」。
6. 对着「验收标准」自检。

## 验收标准

1. 第一部分三块拆完，每块至少两条，且「通用规则」块里没有任何一句提到具体厂商的格式或语气偏好。
2. 「搬之前」五项全部填了「通过 / 需改」，每一项「需改」的都有一句具体的修改记录（改了哪句、改成什么）。
3. 「搬之后」五项全部填完，其中「格式标签」与「长度习惯」两项写出了在目标模型上实际观察到的现象，而不是照抄正文。
4. 验证栏填了目标模型上的通过率与失败的 case id，并与源模型的通过率并排；如果退步了，写出退步的那几条属于四处断裂的哪一处。
5. 整份清单能在不看正文的情况下被另一个人照着执行——把它给一位同学试一次。

## 常见坑

1. **把厂商偏好写进通用规则。** 「用 XML 标签包住输入」是某家模型的适配，不是通用规则；写进通用块后换厂商时你会忘了改。判据：这一句换一家模型还成立吗？不成立就属于厂商适配块。
2. **只改系统提示不改示例。** few-shot 示例里的格式（标签、代码块风格）也是厂商相关的，系统提示改了示例没改，模型会学示例。
3. **搬完不跑测试集，凭两三条手动试的结果宣布迁移成功。** 迁移最常坏的是边界与刁难用例，正常输入几乎不会出问题，手动试两条恰好都是正常输入。
4. **把通过率下降全归咎于「新模型更差」。** 多数退步是四处断裂之一没处理干净，逐条看失败用例的字段就能对上；真的是模型能力差异的情况远比想象的少。
