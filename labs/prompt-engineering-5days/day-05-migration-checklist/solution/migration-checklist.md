# 跨模型迁移检查清单（示范）

> 源模型：claude-sonnet-5　　目标模型：OpenAI 当前推荐型号（`OPENAI_MODEL`）
> 一句话规矩：**搬之前把系统提示拆成三块，搬之后跑同一份测试集。** 中间的每一项都是为这两件事服务的。
> 本示范用的是全课示例任务（给 TODO API 补校验与测试）在 D4 抽取形态下的提示词；验证栏的数字来自 `day-04-prompt-ab-eval/solution` 的 MOCK 运行，换成真模型时以你自己跑出来的为准。

---

## 第一部分：把系统提示拆成三块

判据：这一句**换一家模型还成立吗**？成立 → 通用规则；不成立 → 厂商适配。**每次调用都在变吗**？在变 → 任务变量。

### 通用规则（任何模型都成立，长期不变）

- 你是负责接口评审的后端工程师，从需求描述里抽取接口路径、HTTP 方法、失败状态码与需要校验的字段名。
- 需求写了失败状态码就必须用需求里的；没写才用 400。
- HTTP 方法大写；路径以 / 开头，口语描述还原成标准路径；字段名原样保留英文标识符，路径参数与查询参数也算字段。
- 需求中途改口以最后一次为准；与校验无关的顺带要求忽略。
- 输出必须符合给定的 schema（endpoint / method / failureStatus / fields）。

### 厂商适配（换模型时要改的，独立可替换）

- **Claude 版**：需求文本用一对自定义标签包住（例如 requirement 标签），系统提示里写「只抽取标签内的内容」；结构化输出用强制调用工具的方式，schema 放在工具的 input_schema。
- **OpenAI 版**：需求文本直接作为 input，前面加一行「需求描述如下：」；结构化输出用 Responses API 的 json_schema 严格模式，schema 放在 text.format。
- **长度提示**：目标模型在 fields 里倾向多列一些「可能相关」的字段，适配块加一句「fields 只列需求明确要求校验的字段，不要补充你认为应该校验的」。

### 任务变量（每次调用都不同）

- 需求文本本体。
- 输出语言（本任务只有 summary 受影响；D4 抽取形态没有 summary，此变量为空）。
- 团队默认失败状态码（本团队 400）。

自检：

- [x] 通用规则里没有任何一句提到具体厂商的格式或语气偏好
- [x] 厂商适配块单独删掉，通用规则 + 任务变量仍然是一份能读懂的提示词

## 第三部分：验证

| 模型                         | 通过率 | 失败的 case   | 失败属于哪处断裂                                   |
| ---------------------------- | ------ | ------------- | -------------------------------------------------- |
| 源模型                       | 9/10   | c10           | —（源模型自身的已知回退，见 D4 CHANGELOG）         |
| 目标模型（第一次）           | 7/10   | c01、c07、c10 | c01 / c07 是长度习惯（多列字段）；c10 与源模型相同 |
| 目标模型（修完厂商适配块后） | 9/10   | c10           | 与源模型一致，迁移未引入新退步                     |

**结论：**

迁移完成。目标模型第一次跑退步了两条，全部属于「长度习惯」这一处断裂（倾向多列字段），在厂商适配块加一句长度提示后恢复到与源模型相同的 9/10；通用规则块一个字没改。c10 是两家共同的失败，属于提示词自身的已知回退，与迁移无关，按 D4 的变更记录在下一版修。
