# D4 实验：十条测试集加 A/B 评估脚本，输出两版提示词的逐条对比与通过率

> 目标：把「感觉这版更好」变成「这版在十条测试上多对了三条、弄坏了一条」。
> 你会写一份十条的小样本测试集（正常 / 边界 / 刁难三类）、一个对同一批输入分别跑两版提示词并逐字段判分的脚本、以及一份带通过率的变更记录。抽取任务沿用 D3（从需求描述里抽接口、方法、状态码、字段名）。

## 你会学到

- 跑通 solution，用 MOCK=1 看两版提示词在十条测试上的逐条对比表
- 在 starter 里补全十条测试集，覆盖正常、边界与故意刁难三类输入
- 补全判分函数，让字段比对能容忍顺序与大小写差异
- 补全汇总输出，算出两版各自的通过率与互有胜负的条目
- 改动 B 版提示词再跑一遍，把结果记进变更记录

## 目录

- `starter/`：挖了 4 个练习点（3 个代码 + 1 个文档），`MOCK=1` 下可以直接跑，但只有 4 条用例、判分过死、没有汇总
- `solution/`：参考答案

两个目录里文件一一对应：

| 文件             | 干什么用                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| `src/cases.ts`   | 测试集：十条输入 + 人工标注的 expected，分 normal / edge / adversarial |
| `src/prompts.ts` | 两版提示词 v1 / v2，只放正文；两目录一致                               |
| `src/index.ts`   | 评估脚本：模型出口（含 MOCK）→ 逐字段判分 → 逐条表 + 通过率 + 互有胜负 |
| `CHANGELOG.md`   | 变更记录：每版改了什么、为什么、通过率、已知回退                       |

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 ANTHROPIC_API_KEY（或 PROVIDER=openai + OPENAI_API_KEY + OPENAI_MODEL）；没有 key 先用 MOCK=1
MOCK=1 pnpm start     # 离线模拟：十条 × 两版，输出对比表
pnpm start            # 真模型
```

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace，`pnpm install` 时要加 `--ignore-workspace`。
> 安装可能以非 0 退出（`ERR_PNPM_IGNORED_BUILDS`），不影响运行；目录里冒出 `pnpm-workspace.yaml` 就删掉。

`MOCK=1` 下模型出口用规则模拟「v1 在哪些边界上出错、v2 修了哪些又弄坏了哪条」，并故意把 v1 的方法小写、字段顺序打乱——这样你在离线状态也能看到「两版有差异、差异可解释、判分要容忍写法差异」三个现象。真模型下每条会有随机性，可以把每条跑三次取多数。

## 验收标准

1. `MOCK=1 pnpm start` 跑 starter，对比表有 10 行，`kind` 一列 normal / edge / adversarial 三类都出现，每类至少 3 条。
2. 判分后 v1 不再因为「方法小写」或「字段顺序反了」被判错：MOCK 下 v1 通过 6/10，失败的四条分别报 `failureStatus`、`endpoint`、`fields`、`endpoint`，而不是笼统的 strict mismatch。
3. 汇总里能看到两版各自的通过率、「v2 修好的」四条、「v2 弄坏的」一条（c10），以及 v2 按 kind 的分类通过数。
4. `CHANGELOG.md` 的 v2 条目填完：改动、原因（对应 case id）、通过率（脚本跑出来的数字）、已知回退（c10 及下一版打算怎么改）。
5. 改一版 v3（修 c10 的回退）再跑一遍，把结果作为新条目追加进 `CHANGELOG.md`，包括它有没有弄坏别的。

## 常见坑

1. **测试集全是正常输入。** 十条都是规范写法，两版都 10/10，评估等于没做。测试集的价值全在边界和刁难上——先想「旧版最可能在哪里猜错」，再把那种输入写成用例。
2. **expected 标错了。** 标注是人工的，标错一条整份评估就偏了，而且你会以为是提示词的问题去反复改提示词。每条 expected 写完自己再读一遍输入，确认答案唯一。
3. **判分太死或太松。** 太死（整个对象序列化相等）会把写法差异算成错误，你会去修根本不存在的问题；太松（只比方法）会放过真的错误。原则是「比你在意的字段、容忍你不在意的差异」，并且返回不匹配的字段名而不是布尔值。
4. **只看总分。** 6/10 → 9/10 看起来是进步，但如果那 9 条里有一条是原来对现在错的，你就引入了一个回退。「互有胜负」那两行比总分重要，回退要进 CHANGELOG 的「已知回退」，下一版要专门修。
5. **通过率是估的。** CHANGELOG 里的数字必须是脚本跑出来的。估出来的数字下次没法对比，整份记录就失去了意义。
