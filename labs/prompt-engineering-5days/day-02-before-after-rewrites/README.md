# D2 实验：五个改写前后对照，每个标注用了哪种技巧与为什么

> 目标：拿五个真实感很强的「烂提示词」，各改写一版，并写清楚每一版用了哪种技巧（少样本示例、思维链、分步、自检）以及**为什么是这一种而不是别的**。
> 练的不是技巧本身，是「看到一个任务先判断它缺什么、再选技巧」的判断力；其中第五个案例是故意留下的——改写之后仍然做不对，你要说出它属于哪种失效情形。

## 你会学到

- 读 solution 里五个改写前后对照，先猜每个用了什么技巧再看答案
- 在 starter 里为五个原始提示词各写一版改写，并标注技巧名与理由
- 为示例任务补两个少样本示例，注意示例要与目标输出格式一致
- 挑一个改写后仍然做不对的案例，写出它属于哪种失效情形

## 目录

这是**文档型实验**：`starter/` 与 `solution/` 各只有一份同名 Markdown，不需要 `pnpm install`、不需要 `MOCK=1`、没有自检脚本。

| 文件          | 干什么用                                                                           |
| ------------- | ---------------------------------------------------------------------------------- |
| `rewrites.md` | 五个案例。starter 里每个案例给了「改写前」，待填处是 `> TODO：`；solution 里已填好 |

## 怎么用

1. **先别看 solution。** 打开 `starter/rewrites.md`，把五个「改写前」读一遍，每个先在心里判断：它缺的是示例、是推理空间、是拆分、还是复查？把判断写在「技巧」一栏。
2. 为每个案例写「改写后」。只用一种主技巧，不要把四种全堆上去——堆上去的那版不算完成。
3. 写「为什么选这个技巧」，一到两句，要能说出「换成别的技巧为什么不行」。
4. 案例五改完之后把改写前后都丢进模型跑一跑，你会发现它还是做不对。在「失效情形」一栏写出原因属于三种里的哪一种，以及正确的解法是什么（不是提示词层面的）。
5. 最后填第二部分：为示例任务的提示词补两个少样本示例，对着「验收标准」第 4 条自检。
6. 全部填完再打开 `solution/rewrites.md` 对照。技巧选得不一样不一定是错——看理由能不能站住。

## 验收标准

1. 五个案例的「改写后」全部填完，每个只用一种主技巧，且「技巧」一栏与改写内容一致。
2. 每个案例的「为什么选这个技巧」都能回答「换成别的为什么不行」，不是复述技巧定义。
3. 案例五的「失效情形」写的是三种情形（缺知识、缺工具、任务写错）之一，并给出了提示词之外的解法。
4. 第二部分的两个少样本示例，输出部分与你 D1 写的「格式」栏一模一样（段数、代码块数、语言标记），并且两个示例覆盖的是**不同**的坏输入类型。
5. 随便挑两个案例，改写前后各跑一次，改写后的输出至少在一个可核对的点上更好。

## 常见坑

1. **把四种技巧全堆到一个提示词上。** 每种技巧都有代价（更长、更慢、更贵），全堆上去的提示词跑一次要比原来贵好几倍，而效果往往不比只用对的那一种好。练习的目的是学会选，不是学会堆。
2. **示例的格式跟你要的输出格式不一致。** 你要三段式输出，示例却是两段，模型会学示例不学说明。示例是最强的格式信号，写完先对着格式栏核一遍。
3. **两个示例覆盖同一类情况。** 两个都是「必填字段缺失」，模型会以为校验只有这一种。示例的数量不重要，覆盖的类型才重要。
4. **给案例五硬凑一个提示词解法。** 它就是设计成提示词救不了的，硬凑出来的解法要么依赖模型碰运气，要么其实是在偷偷改任务。承认「这题不该用提示词解」也是判断力的一部分。
