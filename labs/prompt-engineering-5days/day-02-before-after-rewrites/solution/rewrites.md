# 五个改写前后对照（示范）

> 每个案例只用**一种**主技巧。四种可选：少样本示例（few-shot）、思维链（chain of thought）、分步、自检。
> 判断顺序：先问缺什么，再选技巧，最后写「换成别的为什么不行」。你的技巧选择与这里不同不一定错，看理由能不能站住。

---

## 案例一：分类任务，模型总把边界情况分错

**改写前：**

> 把下面这条用户反馈分类成「bug」「需求」「咨询」三类之一，只输出类别名。
> 反馈：「导出 Excel 的时候如果标题里有逗号，列就错位了，能不能顺便也支持导出 CSV？」

**技巧：** 少样本示例

**改写后：**

> 把用户反馈分类成「bug」「需求」「咨询」三类之一，只输出类别名。
> 一条反馈里同时有多类内容时，以**用户最先提到的那件事**为准。
>
> 反馈：「登录之后点头像没反应」 → bug
> 反馈：「能不能加个夜间模式」 → 需求
> 反馈：「你们支持导出 PDF 吗」 → 咨询
> 反馈：「列表加载很慢，另外希望能按标签筛选」 → bug
>
> 反馈：「导出 Excel 的时候如果标题里有逗号，列就错位了，能不能顺便也支持导出 CSV？」 →

**为什么选这个技巧（换成别的为什么不行）：**

模型分错的不是三个类别的定义，是**边界规则**——一条反馈里既有 bug 又有需求时该算哪个。这种规则用文字描述很拗口，用一个「混合反馈 → bug」的示例一眼就懂。思维链在这里是浪费：类别判断本身不需要多步推理，让它「先分析再回答」只会更慢，而且最后一步还是要面对同一个边界规则。注意第四个示例就是专门放的边界样本，没有它前三个示例只教了「各类长什么样」，没教「混合时怎么办」。

## 案例二：算一道多步骤的账，模型直接给结论且经常算错

**改写前：**

> 一个 TODO 接口每天被调 12 万次，其中 3% 的请求体非法。加校验后每个非法请求提前返回，省下平均 40ms 的数据库往返。数据库每毫秒成本按 0.000002 元算。一个月（30 天）能省多少钱？直接给数字。

**技巧：** 思维链

**改写后：**

> 一个 TODO 接口每天被调 12 万次，其中 3% 的请求体非法。加校验后每个非法请求提前返回，省下平均 40ms 的数据库往返。数据库每毫秒成本按 0.000002 元算。一个月（30 天）能省多少钱？
>
> 请先逐步列出计算过程：每天非法请求数、每天省下的毫秒数、每天省下的钱、一个月省下的钱，每一步写出算式和中间结果；最后单独一行给出最终答案，格式为「答案：X 元」。

**为什么选这个技巧：**

「直接给数字」是在逼模型跳过中间步骤，而多步算术恰恰是模型最容易在跳步时出错的地方。思维链给它把中间结果写出来的空间，每一步都是对下一步的校验。少样本示例在这里帮不上忙——你给它三道算对的例题，它依然会在第四道上跳步。分步（拆成多次调用）能解决但太重，一道四步的算术不值得四次请求。代价要说清楚：输出从一个数字变成七八行，慢一点贵一点，但对这种「错了就很难发现」的任务值得。顺带核一下答案：每天 3600 个非法请求，省 144000 毫秒，合 0.288 元，一个月 8.64 元。这类题在真实场景里更好的做法是让模型只写出算式、由代码来算——D3 的结构化输出会讲这条路。

## 案例三：一口气让模型「审查并修复并写测试并写文档」，输出总是前面细后面糙

**改写前：**

> 审查下面这个 TODO API，修复所有问题，补上单元测试，再写一份 README。
> （代码略）

**技巧：** 分步

**改写后：**

> 这是一个分四步的任务，**现在只做第一步**，其余步骤我会在后续消息里逐个发给你。
>
> 第一步：审查下面这个 TODO API，只输出一个问题列表，每条格式为「位置：问题：严重程度（高 / 中 / 低）」，按严重程度从高到低排。不要修改代码，不要写测试，不要写文档。
> （代码略）

后续三条消息分别是：「第二步：只修复列表里严重程度为高的问题，输出修改后的代码」「第三步：为第二步修改过的每一处各写一个测试」「第四步：基于以上内容写 README，只包含运行方式与接口列表两节」。

**为什么选这个技巧：**

四件事塞进一次调用，模型会把注意力和输出长度预算平均分配，结果就是前面详细后面潦草——这不是它偷懒，是一次回答的长度有上限。拆成四张便签之后每一步都有独立的预算和独立的格式要求，而且第二步可以拿第一步的输出当输入，这在一次调用里做不到。思维链解决不了这个问题：它让模型想得更细，但输出预算还是同一份。自检也不行，让它「检查一下 README 有没有写全」只会得到一句「已检查」。代价是四次调用、四倍的往返延迟，以及需要你在中间传递上下文——这正是后面 Agent 类工具要自动化的事。

## 案例四：生成的测试代码里经常有引用不存在的函数名

**改写前：**

> 为下面这个 Express 接口写单元测试，覆盖必填缺失、类型错误、超长三类坏输入。
> （代码略）

**技巧：** 自检

**改写后：**

> 为下面这个 Express 接口写单元测试，覆盖必填缺失、类型错误、超长三类坏输入。
> 写完之后，**逐个检查测试代码里引用的每一个函数名、变量名与导入路径，确认它们都在下面给出的代码里真实存在**；如果引用了不存在的名字，改成真实存在的，或者删掉那个测试并在末尾说明原因。
> 最后输出两部分：测试代码（一个代码块）；一个「引用核对」列表，列出测试里用到的每个外部名字及其在原代码中的位置。
> （代码略）

**为什么选这个技巧：**

引用不存在的函数是典型的「写的时候顺手编了一个合理的名字」，模型在生成过程中不会回头看。自检就是把「回头看」变成任务的一部分，而且要**指定检查什么**——「检查一下有没有问题」没用，「逐个核对引用是否存在于给定代码」才有用。要求它输出「引用核对」列表是关键：这让自检从「口头保证」变成「可验证的产出」，你能一眼看出它有没有真的核对。少样本示例在这里帮助有限，因为问题不是格式而是事实；思维链让它想得更多，但不保证想的是「名字存不存在」这件事。代价是输出更长、稍慢，以及自检本身也可能出错——所以真正的兜底还是把测试跑一遍，自检只是把错误率压下来。

## 案例五：让模型告诉你项目里当前用的校验库版本有没有已知漏洞

**改写前：**

> 我们项目用的校验库是 package.json 里那个版本，它有没有已知的安全漏洞？有的话列出来。

**技巧（先试着改一版）：** 把缺的信息补齐——贴上库名与版本号，要求输出格式为漏洞编号、影响版本、修复版本三列的表格。

**改写后：**

> 我们项目使用的校验库是 `some-validator@3.2.1`。请列出这个版本的已知安全漏洞，输出表格三列：漏洞编号、受影响版本范围、修复版本。没有已知漏洞就回答「未发现」。

**跑完之后它还是做不对。失效情形与提示词之外的正确解法：**

这属于**缺知识**，还叠加了一点**缺工具**。模型的知识有截止日期，截止之后披露的漏洞它一个都不知道；更糟的是它可能编出一个格式完全正确的漏洞编号——格式越严格，编出来的东西越像真的。提示词写得再好也改变不了「它不知道」这个事实。正确解法在模型外面：跑 `pnpm audit` 或查漏洞数据库，把查到的结果贴给模型，让它做的是「解读与排序」而不是「回忆」。更进一步是给模型接一个能查漏洞库的工具，让它自己去查——这就是工具调用，也是本平台 MCP 专题课要讲的内容。判断一个任务是不是这类情形有个简单的问法：**如果这个信息是昨天才出现的，模型有可能知道吗？** 不可能，就别指望提示词。

# 第二部分：为示例任务补两个少样本示例

示例任务：给一个 Express / FastAPI 的 TODO API 补上输入校验和对应的单元测试。
格式栏（D1）：按顺序三段——不超过 5 条的校验缺口列表；修改后的接口代码（一个代码块）；测试文件（另一个代码块）。

**示例一（输入 → 输出）：**

输入：

> 接口：`POST /todos`，请求体 `title`（字符串）。当前代码直接 `db.insert(req.body)`。坏输入类型：必填缺失。

输出：

> 校验缺口：
>
> 1. `title` 未校验存在性，请求体为空对象时会写入一条空标题
>
> ```js
> app.post('/todos', (req, res) => {
>   const { title } = req.body ?? {}
>   if (typeof title !== 'string' || title.length === 0) {
>     return res.status(400).json({ error: 'title is required' })
>   }
>   // …原有插入逻辑
> })
> ```
>
> ```js
> test('POST /todos rejects missing title with 400', async () => {
>   const res = await request(app).post('/todos').send({})
>   expect(res.status).toBe(400)
>   expect(res.body.error).toBe('title is required')
> })
> ```

**示例二（输入 → 输出）：**

输入：

> 接口：`PATCH /todos/:id`，请求体 `dueDate`（ISO 日期字符串）。当前代码直接 `new Date(req.body.dueDate)`。坏输入类型：日期格式非法。

输出：

> 校验缺口：
>
> 1. `dueDate` 未校验格式，传入 `"tomorrow"` 会得到 Invalid Date 并写入数据库
>
> ```js
> app.patch('/todos/:id', (req, res) => {
>   const { dueDate } = req.body ?? {}
>   if (dueDate !== undefined && Number.isNaN(Date.parse(dueDate))) {
>     return res.status(400).json({ error: 'dueDate must be an ISO date string' })
>   }
>   // …原有更新逻辑
> })
> ```
>
> ```js
> test('PATCH /todos/:id rejects malformed dueDate with 400', async () => {
>   const res = await request(app).patch('/todos/1').send({ dueDate: 'tomorrow' })
>   expect(res.status).toBe(400)
>   expect(res.body.error).toBe('dueDate must be an ISO date string')
> })
> ```

**自检：**

- [x] 两个示例的输出段数（3）、代码块数（2）、语言标记（js）与格式栏一致
- [x] 两个示例覆盖的坏输入类型不同（必填缺失 / 日期非法）
- [x] 示例里没有出现「等等」「以此类推」这类让模型自己脑补的词

注意两个示例的输出都严格是「列表、代码块、代码块」三段，没有任何开场白。**示例是最强的格式信号**——如果示例里有一句「好的，下面是我的分析」，模型学到的就是「先客套一句」，你在格式栏写多少遍「不要客套」都压不住它。
