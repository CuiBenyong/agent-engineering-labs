# D1 实验：一份四要素提示词模板，并用它改写示例任务的需求

> 目标：做出一张你以后每次跟模型说话都能套用的「工作便签」模板——角色、任务、格式、约束四个空位，
> 并用它把「给 TODO API 补上输入校验和单元测试」这句模糊需求改写成一份模型能稳定执行的提示词。
> 今天的产出是文档，不是程序；但它会贯穿后面四天，D2 加示例、D3 变模板、D4 上测试集、D5 做迁移。

## 你会学到

- 读 solution 里填好的四要素模板，对照示例任务看每个要素各占哪一段
- 在 starter 里为示例任务填写角色、任务、格式、约束四个空位
- 把四要素拆成系统提示与用户消息两部分，标出哪些是长期不变的
- 找一个你自己最近问过 AI 的问题，用同一张模板改写一遍

## 目录

这是**文档型实验**：`starter/` 与 `solution/` 各只有一份同名 Markdown，不需要 `pnpm install`、不需要 `MOCK=1`、没有自检脚本。

| 文件                    | 干什么用                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| `four-part-template.md` | 四要素模板本体。starter 里待填处是 `> TODO：` 引用块，solution 里已填好 |

## 怎么用

1. 先通读 `solution/four-part-template.md`，看一份填好的便签长什么样，**注意每个要素后面「为什么这么写」那一行**。
2. 回到 `starter/four-part-template.md`，把第一部分的四个 `> TODO：` 换成你自己为示例任务写的内容。不要抄 solution——它是参照物，不是答案。
3. 填第二部分：把你写好的四要素拆成「系统提示」与「用户消息」两栏，并在每一条后面标 `长期不变` 或 `每次变化`。
4. 填第三部分：找一个你最近真的问过 AI、而且答得不好的问题，用同一张模板重写，把改写前后都贴上。
5. 把改写后的提示词丢进任何一个你手边的模型（网页版即可），对着「验收标准」自检。

## 验收标准

1. 第一部分四个空位全部填完，每一条都能指出它在回答「模型缺的是哪一条信息」——说不出来的那条就是废话，删掉。
2. 「格式」一栏写的是**能机械核对**的东西（几段、什么顺序、有没有代码块、代码块什么语言），不是「清晰易读」这类形容词。
3. 「约束」一栏至少有一条是「不要做什么」加上「为什么」，且理由能让一个新同事信服。
4. 第二部分里每一条都标了 `长期不变` 或 `每次变化`，且所有 `长期不变` 的都落在系统提示栏。
5. 第三部分改写前后各跑一次，改写后的回答至少在一个可核对的点上比改写前好（例如多了原来漏掉的边界情况、格式对上了）。

## 常见坑

1. **把「角色」写成头衔而不是视角。** 「你是一位资深工程师」几乎没有信息量；「你是一位负责代码审查的后端工程师，见过很多因为没校验输入而被打挂的接口」才告诉模型该从哪个角度想问题、该在意什么。
2. **「任务」和「格式」混在一起。** 「写一份测试并整理成表格」是两件事：写测试是任务，表格是格式。混着写会让你后面改格式时不得不重写任务，D3 做模板时会很痛。
3. **约束只有「不要」没有「为什么」。** 模型对光秃秃的否定式指令执行得很不稳定（D4 会专门讲这个反模式），带上理由之后它会更容易在你没列到的相似情况里做出一致判断。
4. **把每次都在变的东西写进系统提示。** 比如把这一次要校验的具体字段写进了系统提示，下次换接口就得整段重写。判据很简单：这条内容下一个任务还用得上吗？用不上就放用户消息。
