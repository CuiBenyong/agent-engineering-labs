# 四要素提示词模板（示范）

> 一张便签，四个空位。这份是填好的示范，用的是全课贯穿的示例任务。
> 纪律只有一条：**每一条都要能回答「模型缺的是哪条信息」，答不上来就删。**

示例任务（全课贯穿）：**给一个 Express / FastAPI 的 TODO API 补上输入校验和对应的单元测试。**

---

## 第一部分：四要素

### 1. 角色（你是谁，从什么视角看问题）

你是一位负责代码审查的后端工程师，见过很多因为没校验输入而在线上被打挂的接口。你的习惯是先列出所有会进来的字段，再逐个问「这个字段是空、超长、类型不对时会怎样」。

为什么这么写：

模型缺的不是「后端知识」，而是**该从哪个视角审视这段代码**。「代码审查」让它偏向找漏洞而不是重写功能；「见过被打挂的接口」让它优先考虑边界情况而不是正常路径；最后一句直接把工作方法交给它，省掉它自己猜。

### 2. 任务（要做成什么样，做完的样子是什么）

对下面给出的 TODO API 代码，做两件事：第一，为创建与更新两个接口补上请求体校验，覆盖必填字段缺失、字段类型错误、字符串超长（标题上限 200 字符）、日期格式非法四类情况，校验失败统一返回 400 与一段可读的错误信息；第二，为每一类校验各写至少一个单元测试，另加一个正常路径的测试，测试框架沿用代码里已有的那个。完成的标准是：所有测试能跑、能过，并且每个测试名字能让人不看代码就知道它测的是哪种坏输入。

为什么这么写：

「补上输入校验」这五个字在人之间可以传达，是因为大家默认了一套「校验该覆盖什么」的常识；模型没有这套默认，所以要把「覆盖哪四类」「失败时返回什么」「测试覆盖到什么程度」全部写出来。最后一句是**完成标准**，有了它模型才知道什么时候该停。

### 3. 格式（输出长什么形状，能机械核对）

按顺序输出三段：第一段是一个不超过 5 条的列表，说明你发现的校验缺口；第二段是修改后的接口代码，放在一个代码块里，语言标记与原代码一致；第三段是测试文件，放在另一个代码块里。三段之间不要有过渡性的客套话。不要输出你没有修改的文件。

为什么这么写：

每一条都能机械核对：数段数、数列表条数、看代码块数量与语言标记。「不要客套话」和「不要输出没改的文件」是为了让输出能直接粘进代码库，而不是先删三段寒暄。这一栏写得越死，D3 把它变成结构化输出时越顺。

### 4. 约束（不要做什么，以及为什么）

不要引入新的校验库，因为这个项目的依赖需要走审批，加库会让这次修改卡在流程里。不要修改接口的路径、方法与成功时的响应结构，因为已经有前端在调用它们。如果原代码里有你认为应该重构但与本次任务无关的地方，只在第一段列表里提一句，不要动手改。

为什么这么写：

三条约束都带了理由。理由不是给人看的礼貌，是给模型的**判断依据**：有了「依赖要审批」，它在遇到你没列到的类似情况（比如想加一个日期解析库）时也能做出一致的决定。最后一条是在划定范围——模型很喜欢「顺手」重构，不划线它会把改动面扩大到你没法审的程度。

## 第二部分：拆成系统提示与用户消息

| 归属     | 内容                                                               | 变化频率 |
| -------- | ------------------------------------------------------------------ | -------- |
| 系统提示 | 角色全文（代码审查视角、先列字段再问边界的工作方法）               | 长期不变 |
| 系统提示 | 格式全文（三段结构、代码块规则、不输出未修改文件、不客套）         | 长期不变 |
| 系统提示 | 约束里的通用两条（不引入新依赖、与任务无关的重构只提不改）         | 长期不变 |
| 用户消息 | 任务全文（四类校验、400 与错误信息、测试覆盖要求、完成标准）       | 每次变化 |
| 用户消息 | 约束里与本接口相关的一条（不改路径、方法与成功响应，因为前端在调） | 每次变化 |
| 用户消息 | 待修改的 TODO API 代码本体                                         | 每次变化 |

自检：

- [x] 所有 `长期不变` 的都在系统提示栏
- [x] 换一个接口、换一种框架时，只需要改用户消息栏

注意「约束」被拆成了两半：「不引入新依赖」对这个团队的任何任务都成立，进系统提示；「不改路径与响应」只对这次要改的接口成立，进用户消息。**四要素是写作时的分类，系统提示与用户消息是部署时的分类，两者不是一一对应的。**

## 第三部分：改写你自己的一个问题

**改写前（原样贴上）：**

> 帮我看看这段代码有什么问题

**改写后（套第一部分的四要素）：**

> 你是一位负责代码审查的后端工程师，重点关注输入校验与错误处理。（角色）
> 下面是一个 Express 的 TODO API 创建接口，请找出所有没有校验的请求字段，并说明每一个在坏输入下会导致什么后果。（任务）
> 输出一个列表，每条格式是「字段名：缺什么校验：可能后果」，按严重程度从高到低排。不要给修改后的代码。（格式）
> 不要评论命名风格和代码格式，因为这次只看安全性。（约束）
>
> ```js
> app.post('/todos', (req, res) => { ... })
> ```

**改写后好在哪（至少一个可核对的点）：**

改写前的回答会同时讲命名、缩进、缺注释与缺校验，四五百字里真正有用的只有两句；改写后的回答是一张按严重程度排好的表，第一条就是「title 未校验非空与长度」，可以直接拿去建任务。**可核对的点**：改写后的输出条目数固定、每条格式一致、没有一条在讲命名。
