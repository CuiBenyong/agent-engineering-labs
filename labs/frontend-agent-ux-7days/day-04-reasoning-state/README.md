# D4 实验：推理过程与共享状态

两件让 Agent 界面真正区别于聊天界面的事：把模型的推理做成可折叠区域，
以及维护一份前后端共享的状态。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm start        # http://localhost:3134
```

```bash
pnpm typecheck && pnpm selftest
```

## 剧本

| 选项            | 效果                                                         |
| --------------- | ------------------------------------------------------------ |
| 推理 + 共享状态 | 先流式吐推理，再快照打底、三批增量补丁更新右侧面板           |
| 补丁打不上      | 快照之后来一条指向不存在路径的补丁，界面要发现并等待重新对齐 |
| 只读工具调用    | D3 的工具剧本                                                |
| 危险工具        | D3 的审批剧本                                                |

## 共享状态是什么

聊天记录之外，双方都看得见的那份数据。一个正在被填写的表单、一份逐步成形的报告、
一个走到第三步的流程——把它们塞进聊天气泡是别扭的，它们需要自己的一块地方并原地更新。

协议给了两种更新方式，各有各的场合：

- **快照**（`STATE_SNAPSHOT`）整份状态，权威，用来打底和恢复
- **增量**（`STATE_DELTA`）JSON Patch 操作数组，省带宽，用来推进

## 三个练习点

1. **`json-patch.ts`：`applyPatch`。** 全有或全无，失败不抛异常。
2. **`json-patch.ts`：`replace` 到不存在的键。** 成功还是失败？想清楚宽容处理的后果。
3. **`chat.tsx`：处理打不上的补丁。** 崩掉、静默忽略、还是标记不同步等重新对齐？

## 验收标准

1. 推理区默认收起，点击可展开，流式期间显示「正在思考…」和字数
2. 推理内容与正式回答在视觉上明确区分，不会被误读成最终答案
3. 右侧状态面板先由快照填充，随后被增量补丁逐步更新
4. 「补丁打不上」剧本下面板显示「与服务端不同步」，收到新快照后恢复正常
5. 补丁打不上时界面不崩溃，也不显示改了一半的数据
6. `pnpm typecheck && pnpm selftest` 退出码为 0

## 手动验收清单

- [ ] 推理区**默认是收起的**——默认展开会把正式答案挤到屏幕外
- [ ] 推理流式期间，折叠标题上的字数在涨，用户知道它在动而不是卡住
- [ ] 状态面板里的步骤逐个打勾，指标逐个出现，而不是最后一次性全变
- [ ] 选「补丁打不上」：面板出现橙色的「与服务端不同步」提示，随后被新快照清除
- [ ] 不同步期间面板显示的是**旧数据加提示**，而不是空白或错误数据

## 为什么 replace 到不存在的键必须失败

这是练习 2 的答案，做完再看。

宽容地当 `add` 处理，短期看「能跑」，长期是灾难：服务端发来 `replace`
说明它认为那个键存在，而本地没有——**这本身就是两边状态已经不一致的信号**。
把它悄悄补上，等于把不一致藏起来，直到某天以更难查的形式爆出来
（用户看到一份对不上的数据，而日志里什么都没有）。

严格失败反而是好事：它把一个隐蔽的数据问题变成一个明确的、可以立刻恢复的信号——
标记不同步，请求一份完整快照，重新对齐。
