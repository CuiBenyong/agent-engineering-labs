# D3 实验：工具调用可视化与人在回路审批

把四类工具事件归并成一张有状态的卡片，再实现审批——**并且用正确的方式实现它**。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm start        # http://localhost:3133
```

```bash
pnpm typecheck && pnpm selftest
```

## 这一天最重要的一件事

审批**不是**前端弹个框拦住请求。

打开「危险工具」剧本发送，观察网络面板：运行在工具执行前就**正常结束**了，
`RUN_FINISHED` 带着一个 `interrupt` 结局。你的决定会作为**下一次请求**的
`resume` 条目发回服务端，由服务端决定要不要真的执行。

为什么必须这样：前端的判断可以被绕过（改改请求就行）。把前端当安全边界是个典型错误。
前端的审批界面只负责**采集决定并解释清楚后果**，真正的门在服务端。

## 剧本

| 选项     | 效果                                                           |
| -------- | -------------------------------------------------------------- |
| 只读工具 | `search_documents`，参数流式到达，执行后返回结果，全程无需审批 |
| 危险工具 | `delete_files`，参数收齐后运行中断，等你确认                   |
| 报错     | `RUN_ERROR`                                                    |

## 五个练习点

1. **`tool-calls.ts`：`appendArgs`。** 想清楚这里能不能顺手 parse。
2. **`tool-calls.ts`：`finalizeArgs`。** 参数收齐才 parse，失败不要抛异常。
3. **`tool-calls.ts`：`describeArgs`。** 参数没收齐时显示什么。
4. **`chat.tsx`：处理 `interrupt` 结局。** 记下 interruptId，把卡片改成待审批。
5. **`chat.tsx`：把决定发回服务端。** 作为下一次请求的 `resume` 条目。

## 验收标准

1. 只读工具剧本下，卡片依次经过「准备参数 → 执行中 → 完成」三种状态
2. 参数流式到达期间，界面**不显示**半截 JSON 原文
3. 危险工具剧本下运行中断，卡片进入「等待你确认」并出现两个按钮
4. 点「同意执行」后工具真的执行并返回结果
5. 点「拒绝」后对话继续（模型换了个提议），而**不是**整个运行失败
6. `pnpm typecheck && pnpm selftest` 退出码为 0

## 手动验收清单

- [ ] 参数流式到达时，卡片显示「正在准备参数…（已收到 N 个字符）」而不是 `{"path":"repo`
- [ ] 工具执行的那段空窗期里，卡片显示「执行中」，用户知道在等什么
- [ ] 危险工具的卡片有视觉区分（橙色边框），审批区有明确的后果说明
- [ ] 审批按钮**没有**默认选中项——默认值等于替用户做决定
- [ ] 打开网络面板确认：点同意后发出的是**一个新请求**，请求体里带 `resume`

## 一条实测得到的测试教训

自检里「参数没收齐时不把半截 JSON 显示给用户」这条断言，第一版写的是
「参数收到一半时 `args` 仍为 null」。变异检验发现它**恒真**：
就算把 `appendArgs` 改成每片都 parse 一次，半截 JSON 本来就 parse 失败返回 null，
断言照样绿。

改成现在这条之后，破坏 `describeArgs` 会让它正确变红。

教训：**断言要盯用户能看见的后果，而不是盯内部变量的中间状态**。
内部状态常有多条路径通向同一个值，断言它往往验不出你以为在验的东西。
