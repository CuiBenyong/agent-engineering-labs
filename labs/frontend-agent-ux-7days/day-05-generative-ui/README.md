# D5 实验：生成式界面的三种范式

让模型决定界面长什么样。三种范式的控制权从前端一路让渡到模型，
本课实现前两种，第三种只讲为什么不该用。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm start        # http://localhost:3135
```

```bash
pnpm typecheck && pnpm selftest
```

## 三种范式

| 范式       | 模型决定什么                  | 前端保留什么               | 本课       |
| ---------- | ----------------------------- | -------------------------- | ---------- |
| 静态生成式 | 选哪个组件 + 填什么数据       | 组件实现、样式、交互       | 实现       |
| 声明式     | 一棵界面描述树（布局 + 内容） | 节点白名单、渲染规则、样式 | 实现       |
| 开放式     | 直接产出界面代码              | 几乎没有                   | **不实现** |

判据是**模型产出的是数据还是代码**。前两种是数据，可以校验、可以白名单、
可以降级；第三种是代码，一旦执行就没有中间地带。

## 剧本

| 选项       | 效果                                                       |
| ---------- | ---------------------------------------------------------- |
| 生成式界面 | 文字 + 三个静态组件 + 一棵声明式树                         |
| 未注册组件 | 未注册组件、非法数据、含非法节点的树，最后一个正常组件收尾 |

## 四个练习点

1. **`generative.ts`：`resolveComponent`。** 两种失败要分开报。
2. **`generative.ts`：深度上限。** 递归生成跑偏会产出深到爆栈的树。
3. **`generative.ts`：白名单外的节点类型。** 整棵树拒绝还是只降级这个节点？
4. **`generative-block.tsx`：兜底界面。** 说清楚发生了什么，且不影响其余内容。

## 验收标准

1. 正常剧本下三个静态组件与一棵声明式树都正确渲染
2. 未注册组件显示「这个版本还不支持」，而不是白屏或崩溃
3. 数据不合法显示的是另一套文案，与未注册组件区分开
4. 声明式树里混入非法节点时，**其余节点照常渲染**
5. 任何一个块渲染失败都不影响后续内容（剧本最后一个正常组件仍然出现）
6. `pnpm typecheck && pnpm selftest` 退出码为 0

## 手动验收清单

- [ ] 选「未注册组件」：页面上依次出现两种不同文案的兜底块，然后是一个正常的指标块
- [ ] 兜底块的文案是给**用户**看的（「这个版本还不支持」），不是抛给用户的技术错误
- [ ] 声明式树里被降级的那一行用斜体或浅色显示，与正常内容可区分
- [ ] 整个页面没有因为任何一个块失败而白屏

## 为什么本课不实现开放式范式

开放式范式让模型直接产出前端代码并在用户浏览器里执行。它最灵活，也最危险：

**模型产出的代码会以你的页面权限运行。** 它能读 cookie、读 localStorage、
发任意请求、改任意 DOM。而模型是可以被内容影响的——它读到的任何一段文本
（一封邮件、一个网页、一份文档）都可能包含让它产出恶意代码的指令。
这条攻击路径不需要模型「变坏」，只需要它**听话**。

沙箱（iframe + CSP）能降低风险但不能消除，而且会让生成的界面失去与主应用交互的能力，
那恰恰是当初想要开放式的理由。

所以生产上的建议很明确：**从静态范式开始，需要布局自由度时升到声明式，
除非你有非常强的理由并且准备好完整的沙箱方案，否则不要用开放式。**
