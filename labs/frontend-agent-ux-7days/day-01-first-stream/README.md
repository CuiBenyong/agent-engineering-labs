# D1 实验：浏览器里的第一条流

用原生 `fetch` 加 `ReadableStream` 读一条 AG-UI 事件流，把增量拼成一条逐字出现的消息。

这一天的产出是**后面六天的地基**：事件类型、解码器、离线剧本三个文件会被 D2–D7 原样复用，
所以值得写仔细一点。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm start        # http://localhost:3131
```

自检（不启动 Next，只验协议层）：

```bash
pnpm typecheck && pnpm selftest
```

`starter` 的自检**应该是红的**——五个练习点还没做。做完应该全绿。

## 本课默认离线

服务端不连任何真实模型，按 `src/server/scenarios.ts` 里的剧本逐事件吐。
这门课教的是「收到事件之后界面怎么办」，真实模型只会带来不确定性和 API Key 门槛。
想接真模型的做法在 D7 说明，不是必做项。

页面上的「故障注入」下拉框对应 `INJECT` 取值，也可以用查询参数 `?inject=burst`：

| 取值    | 效果                                                            |
| ------- | --------------------------------------------------------------- |
| `none`  | 正常剧本                                                        |
| `slow`  | 每个增量之间等 80ms，方便看清逐字过程                           |
| `burst` | 把文字切到一字一个增量并重复三遍，用来复现渲染风暴（D2 的主角） |
| `cut`   | 流到一半直接断，收不到 `RUN_FINISHED`                           |
| `error` | 开场后直接吐 `RUN_ERROR`                                        |

## 五个练习点

都在 `starter/` 里用 `【练习 N】` 标出来了。

1. **`decode.ts`：把字节流解成字符串流。** 用 `TextDecoderStream`，不要自己
   `new TextDecoder()` 逐块 `decode`。
2. **`decode.ts`：解码循环。** 按空行切事件，处理跨数据块的半个事件，`finally` 里释放锁。
3. **`decode.ts`：按 SSE 规范取 `data` 字段。** 丢掉注释行，多行 `data:` 用 `\n` 拼接，
   去掉冒号后的第一个空格。
4. **`chat.tsx`：把事件应用到界面状态。** 五种事件各自怎么改状态。
5. **`chat.tsx`：未知事件要忽略而不是报错。** 剧本末尾埋了一个协议里没定义的事件。

`solution/` 里每个关键函数都有注释说明为什么这么写。

## 验收标准

1. 打开页面点击发送，文字逐段出现，而不是等全部完成才一次性出现
2. 浏览器控制台能看到解码出的事件序列，包含 `RUN_STARTED` 与 `RUN_FINISHED`
3. 选 `error` 注入时，界面显示错误提示而不是永远转圈
4. 服务端返回的未知事件类型不会让页面崩溃，流照常读完
5. `pnpm typecheck && pnpm selftest` 退出码为 0

## 手动验收清单（自动断言覆盖不到的部分）

这是一门 UI 课，很多东西只能肉眼验，不要因为 `pnpm selftest` 绿了就以为做完了：

- [ ] 选 `slow` 发送，文字是**一段段**出现的，不是等几秒后整段蹦出来
- [ ] 流还没结束时，消息末尾有一个闪烁的光标；`TEXT_MESSAGE_END` 之后光标消失
- [ ] 选 `cut` 发送，流断在半路，但「发送」按钮**恢复可点**（没有一直卡在「接收中」）
- [ ] 选 `error` 发送，页面出现红色错误条，而不是静默什么都不发生
- [ ] 打开控制台，能看到一条 `[agent] 未处理的事件类型 FUTURE_EVENT_FROM_UPSTREAM` 的 debug 日志

## 一个写这个 lab 时踩到的坑

自检里有一条断言叫「切在汉字字节中间仍能解出完整文字」。它的第一版是恒真的：

原本的写法是走真实 HTTP 请求，然后断言拼出来的文本包含某几个词。
问题是**真实 HTTP 每次 `write()` 都是一个完整数据块，中文根本不会被切断**——
把 `TextDecoderStream` 换成不处理跨块字符的逐块 `TextDecoder`，那条断言照样是绿的。
它验的其实只是「文本没丢」，而不是它声称验的「解码器正确处理了字节边界」。

现在的版本自己构造一个从字节中间切开的流：先找到第一个多字节字符的首字节，再往后挪一格下刀。
这样改完，逐块 `TextDecoder` 的版本会解出 `���声传译`，断言正确地变红。

**教训有两条**：写死字节偏移量会让这类断言在数据一变就静默失效（`data: {` 这段前缀正好 6 字节，
第一版切在第 7 字节，压根没碰到汉字）；以及，**一条从来没红过的断言，不能算验证过任何东西**。
拿到一条绿的断言，随手破坏一下被测代码，看它会不会红——这个习惯值得带到你自己的项目里。
