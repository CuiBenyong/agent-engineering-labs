# D2 实验：不抖的流式渲染

在 D1 的基础上解决三件事：渲染风暴、不完整的 Markdown、滚动位置被抢。

三个冻结文件（`src/protocol/events.ts`、`src/protocol/decode.ts`、`src/server/scenarios.ts`）
从 D1 原样复制，不要改动。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm start        # http://localhost:3132
```

```bash
pnpm typecheck && pnpm selftest
```

## 先量后调

页面上有一个统计条，显示这一次运行的**增量数、状态更新次数、消息组件渲染次数**。
用法：

1. 选 `burst`，**关掉**「按帧合并」，发送，记下渲染次数（这是基线）
2. **打开**「按帧合并」，再发送一次，对比

本机实测（Playwright 驱动真实 Chromium，重复 3 次稳定）：

| 模式     | 增量 | 状态更新 | 消息渲染 |
| -------- | ---- | -------- | -------- |
| 逐增量   | 174  | 174      | 176      |
| 按帧合并 | 174  | 55       | 57       |

约 3.1 倍。整条流约 730ms，55 次更新合每 13ms 一次，与 60fps 的 16.7ms 同量级——
渲染频率被钉在了屏幕刷新率上，不再跟着模型吐字速度走。

> 注：开着 React StrictMode 时两边会同步翻倍（352 / 112），倍数不变。
> 上表是关掉 StrictMode 测的干净数字。

## 一个反直觉的实测结果（值得记住）

`burst` 剧本最初把增量间隔设成 0，想着「吐得越快越能复现风暴」。实测结果相反：
**174 个增量只渲染了 6 次**。

原因是 React 18 之后的**自动批处理**：同一个事件循环轮次里的多次 `setState` 会被合并。
间隔为 0 时整条流几乎在一两个数据块里到齐，客户端在同一轮里连续更新，React 全并了。

所以剧本改成了 2ms 间隔。**这不是 lab 细节，是个真实的工程陷阱**：
本地连 mock 跑得飞快、怎么测都不卡，一上线就卡——因为本地数据瞬间到齐，
自动批处理把问题藏起来了。**性能测试必须模拟真实的到达节奏。**

## 五个练习点

1. **`frame-buffer.ts`：按帧合并。** 保证一帧之内只排一次 flush。
2. **`incremental-markdown.ts`：未闭合的围栏。** 没闭合时也要产出代码块并标 `complete: false`。
3. **`incremental-markdown.ts`：未闭合的行内标记。** 想清楚为什么这里的结论和代码块相反。
4. **`use-scroll-anchor.ts`：判断贴底。** 距底阈值留一点余量。
5. **`use-scroll-anchor.ts`：条件跟随。** 只在贴底时滚，且不要用平滑滚动。

## 验收标准

1. 统计显示按帧合并开启后状态更新次数显著低于增量数
2. 关闭按帧合并再跑一次，渲染次数明显上升，两者可对照
3. 流式期间在输入框打字，输入不出现可感知的滞后
4. 未闭合的代码块在流式过程中就以代码块样式显示，闭合时不发生重排
5. 向上滚动后新内容不会把视图拽回底部，且出现「回到底部」按钮
6. `pnpm typecheck && pnpm selftest` 退出码为 0

## 手动验收清单（自动断言覆盖不到的部分）

- [ ] `burst` + 关闭合并：文字出现时能感觉到轻微的不连贯；打开合并后明显更顺
- [ ] 流跑起来时在「输入延迟测试框」里连续打字，**关掉**按帧合并时能感到输入滞后，打开后消失
- [ ] 消息里出现代码块时，围栏还没闭合就已经是代码块样式（左边一道高亮边），闭合时**位置不跳**
- [ ] 流式期间往上滚动，新内容继续到达但视图**不动**，右下角出现「回到底部」
- [ ] 点「回到底部」后恢复跟随
