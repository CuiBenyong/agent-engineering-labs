# D2 实验：一次云端并行任务的执行清单

> 目标：真的把两个任务同时派到 Codex 云端跑一遍，并把「配环境 → 派任务 → 审 diff → 复盘」整个过程写成一页下次能直接复用的清单。今天的产出是文档，不是程序——但每一个时间和每一个决定都必须是你自己跑出来的。

## 你会学到

- 为一个 GitHub 仓库配一个云端环境：写 setup 脚本装依赖，决定是否开公网
- 把 TODO API 的输入校验与单元测试拆成两个任务同时派出，记录每个任务的起止时间
- 回来逐个审阅 diff，用清单决定每个任务是接受、追问还是丢弃
- 对接受的那份 diff 跑一次 /review，把审查意见与你自己的判断做对照
- 把整个过程写成一页可复用的云端任务清单

## 目录

这是**文档型实验**：没有代码、不需要 `pnpm install`、不需要 `MOCK=1`。

- `starter/cloud-task-checklist.md`：留了空位的清单模板，待填处是 `> TODO：` 引用块
- `solution/cloud-task-checklist.md`：用本课 TODO API 示例填好的一份示范（时间与决定是示范值，不是你的）

## 怎么用

1. 没有可用仓库的话，把 D1 的 TODO API 推到一个新建的**私有**仓库。
2. 打开 `chatgpt.com/codex`，为这个仓库建一个环境：Node 运行时、setup 脚本 `pnpm install`、公网先关。发一个只读任务「列出项目里所有路由」验证 setup 能过——过不了先修 setup，别急着派正式任务。
3. 复制 `starter/cloud-task-checklist.md`，边做边填：两个任务同时派出，记发起时间；回来记完成时间、diff 规模、你的决定和理由。
4. 对接受的那份 `codex apply` 到本地、跑测试、跑 `/review`，逐条标同意 / 不同意。
5. 填复盘区。`solution/` 是参照物，看它每一格「写到什么粒度」，不要抄它的内容。

## 验收标准

1. 为一个 GitHub 仓库配好了一个云端环境，随便发一个任务，setup 脚本都能通过。
2. 「补输入校验」与「补单元测试」两个任务同时派出并都跑完，清单里记录了各自的起止时间。
3. 每份 diff 都按清单做出了接受、追问或丢弃的决定，且写下了理由。
4. 对接受的 diff 跑过一次 `/review`，清单里有一处你不同意审查意见并写明了原因。

## 常见坑

1. **setup 脚本没过就派正式任务。** 容器里没有你本地那套环境，setup 失败任务直接作废。先用一个只读小任务把 setup 调通。
2. **两个任务改同一批文件。** 「补校验」和「补测试」如果都要动 `src/todo.ts`，回来合并时会冲突。派任务前先在清单里写明每个任务预计改哪些文件，重叠就串行。
3. **把生产密钥放进环境变量。** 环境里的变量对容器里自主执行命令的程序完全可见。测试用假值，密钥不进环境。
4. **一键全接受审查意见。** `/review` 会有误报（把有意的设计当 bug）。清单里那一格「不同意的审查意见」是必填的，逼你逐条判断。
