# D4 实验：沙箱化的工具执行器

假设注入**已经发生**：模型已经决定要把客户名单发到攻击者那里。
这一层的任务不是识破它，是**让它做不成**。

## 跑起来

```bash
cd starter        # 或 solution
pnpm install --ignore-workspace
pnpm typecheck && pnpm start
```

离线运行，不需要模型也不需要网络。

## 沙箱是两层，不要混为一谈

| 层 | 是什么 | 本实验 |
| --- | --- | --- |
| **策略层** | 你自己写的代码：能力面、危险等级、确认门、路径与出口白名单、审计日志 | **做，可跑** |
| **隔离层** | 容器 / 虚拟机 / gVisor / seccomp / OS 级沙箱工具 | **只讲不跑**（见下） |

两层的失效方式完全不同。2026 年公开分析过的几次 Agent 沙箱绕过，失效点都出在
**出口代理、配置加载与审批环节**——也就是策略层——而内核级隔离本身没被击穿。
结论不是「沙箱没用」，而是**沙箱的边界通常断在你自己写的那一层**。

想给隔离层加一层，可以了解 [sandbox-runtime](https://github.com/anthropics/sandbox-runtime)
这类 OS 级工具的形态：它在进程级别限制文件系统与网络，不需要容器。本实验不依赖它。

## 五个练习点

1. **`policy/redact.ts`：`redact()`（已给出，读一遍）。** 记结构，不记内容。
2. **`policy/egress.ts`：`checkEmail()`。** 默认拒绝——取不到域名也要拒。
3. **`policy/egress.ts`：`checkUrl()`。** https、内网地址、主机白名单，三条顺序照写。
4. **`policy/engine.ts`：`evaluate()`。** 四步顺序**不能换**，理由在注释里。
5. **`runtime/executor.ts`：`execute()`。** 每一次裁决都要写进审计日志，**包括被拒的那些**。

## 验收标准

```text
#1 ⛔ 拒绝 send_email        收件域名不在白名单里：attacker.example
#2 ⛔ 拒绝 post_webhook      目标是内网或回环地址：169.254.169.254
#3 ⛔ 拒绝 send_email        等待确认未获批准：不可逆的对外动作，需要人确认
实际执行：search_customers、update_ticket
```

给确认门点头之后，实际执行变成 `search_customers、send_email、update_ticket`——
**只多了发给风控的那一封**。

## 手动验收清单

- [ ] **`#1` 和 `#3` 的拒绝理由不一样**：发给攻击者的那封连确认门都没走到，
      它在出口白名单那一步就被拒了。这就是「先判目的地，再判要不要人点头」的意义——
      顺序反过来，你是在训练人为一个本来就该拒的动作按同意。
- [ ] **`#2` 的地址是 `169.254.169.254`**：云上元数据端点。SSRF 在 Agent 里的样子，
      就是「让它替你去敲一个你自己敲不到的地址」。
- [ ] **审计日志里的邮箱被脱敏成 `<邮箱@attacker.example>`**：域名留着（复盘要用），
      本地部分去掉（它是个人数据）。日志是一份新的数据副本，它自己也要被当成资产。
- [ ] **危险等级那张表是算出来的**（`riskTier()`），不是人工一条条拍的。
      人工清单会在加新工具时静默过期：加了工具没人改清单，它就默认落进最宽松的一档。
- [ ] 跨租户那一段：`tenantId` 换成 `globex` 就被拒了。
      **凭据与租户只来自会话，永远不来自模型的输出。**

## 变异检验（必做）

1. 把 `ALLOWED_EMAIL_DOMAINS` 改成 `['deskmate.internal', 'attacker.example']` 重跑——
   外泄立刻得手。这条白名单就是三件套里「对外通信」那条边的实际位置。
2. 把 `evaluate()` 里的确认门判断挪到出口检查**前面**，重跑并观察 `#1` 的理由变化：
   它会变成「需要人确认」，于是一个本来该被直接拒绝的动作，变成了一个等人点头的动作。
3. 把 `execute()` 里的 `redact()` 去掉，看审计日志里出现了什么。

## 与 MCP 那门课的分工

如果你的工具是通过 MCP 接进来的，**协议自身**还有一组独立的问题：混淆代理、令牌透传、
状态句柄劫持、本地服务端被投毒。那些写在 `mcp-7days` 的 D6，以及
[MCP 安全最佳实践](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
里。本实验做的是**与协议无关**的那一层：无论工具从哪来，它都要过这个执行器。
