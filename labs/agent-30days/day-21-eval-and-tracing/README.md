# D21 实验：eval 脚本 + tracing

> 目标：给 W3 那套多 Agent 系统装上一整套「量得出来」的东西——15 条标准样本集（golden set）、
> 一个自己会被校准的 LLM-as-judge、一棵能还原完整调用链的 trace，以及一块失败率与成本面板。
> 做完之后，「这次改动到底让它变好了还是变坏了」这个问题第一次有了数字答案，
> 而且那个数字掉下去时你能立刻说出是哪几条挂了。

## 你会学到

- 整理一份 15 条的 golden set，覆盖每条路由、每种失败模式，以及历史上真出过事故的那几条
- 写一个 LLM-as-judge 脚本，对每条输出打 1–5 分并记录理由，低于 3 分算失败
- 亲手看到 judge 的三种失效模式：同源偏差、长度偏好、评分提示词漂移，以及各自的解药
- 给关键节点加上 tracing，把一次请求还原成一棵带耗时与并行标记的调用树
- 汇总 trace 数据，产出通过率、路由准确率、降级率、延迟与成本的面板，并且**数字能被手算复核**

本实验**没有** `docker-compose.yml`：评估、打分、trace、面板全在进程内，不需要任何外部服务。

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 OPENROUTER_API_KEY；没有 key 就一直用 MOCK=1

MOCK=1 SELFTEST=1 pnpm start   # 验收入口：七项自检逐项打印 ✅/❌，跑完按结果设退出码
MOCK=1 pnpm start              # 跑一条，看路由、产出、调用树和这一条的评分
MOCK=1 pnpm start "SO20260902 我要退款，顺便看下物流到哪了"   # 换一句试试
```

`MOCK=1` 下**零外部服务**，但假回复随输入变化：换一句请求会走不同的路由、拆出不同的子任务，
换一份产出、换一套评分提示词、换一个 judge 模型，分数都会跟着变——
否则今天要看的三种失效模式一个都看不见。去掉 `MOCK=1` 并配好 key，跑的是同一份业务代码。

> `pnpm install --ignore-workspace` 可能以非 0 退出（pnpm 会拦 esbuild 的 postinstall），
> 这不代表安装失败。装完顺手看一眼有没有冒出 `pnpm-workspace.yaml`，有就删掉。

## 验收标准

1. `MOCK=1 SELFTEST=1 pnpm start` 七项自检全部 ✅、退出码 0（`starter/` 原样跑只有第 1 项 ✅，
   其余六项各自点名对应的练习号）。
2. 第 2 项：15 条 golden **一条不落**地跑完，通过率 15/15、路由判对 15/15。
3. 第 3、4 项：同一份产出连评三次分数完全一样；换一套评分提示词分数不同，且面板**拒绝**把两套
   口径的记录混在一起算；把 compose 提示词里「针对评审意见补一句结论」那句删掉之后，
   通过率从 15/15 掉到 12/15，并点名是 g04、g05、g14 挂了。
4. 第 5 项：同一批产出上，同源 judge 给 14/15 而异源 judge 只给 12/15；灌水 141 字之后
   v1 那套提示词从 2 分涨到 4 分、v2 仍是 5 分；5 条人工标注上异源一致 5/5、同源只有 3/5。
5. 第 6、7 项：g03 的 21 个 span 还原成一棵树（路由 → 拆 3 件 → 4 次执行，其中 1 次是 Critic
   打回后的重跑 → 汇总），并行的执行者带 ‖ 标记；面板给出 76 次调用 ÷ 15 次请求 = 每请求 5.1 次，
   输入 8494 tokens 与输出 2844 tokens 按价目表手算得 $0.002980，与面板分毫不差。

## 常见坑

1. **judge 默认和被评估的系统用同一个模型。** 它会偏向认可自己的输出，通过率虚高而你察觉不到——
   本实验里同一批产出，同源 judge 给 14/15，异源只给 12/15，被放过去的正是最该抓的那两条边缘产出。
   默认就换一个模型，别指望调用方每次记得传参数。
2. **拿两套评分提示词的分数做比较。** 分数只在同一套 judge 提示词内部可比：本实验里 v1 给 2 分、
   v2 给 5 分，评的是同一份产出。所以每条评分记录都要带上 rubric 版本与 judge 模型，
   面板发现记录里混了两套口径要直接拒绝聚合，而不是算出一个没有含义的平均分。
3. **用 `Promise.all` 一次把 15 条 golden 打出去。** 会撞上限流，而且并发会让 trace 里的耗时
   互相污染，面板上的 p95 就不可信了。评估要的是可比较，不是快。
4. **span 忘了接父指针。** 调用树会塌成一张平铺列表：你只知道发生过什么，不知道谁在谁里面，
   也看不出哪两个执行者是并行的。父子关系靠 AsyncLocalStorage 传，别在每个函数里多加一个参数。
5. **成本按调用数摊。** 多 Agent 的一次用户请求会产生 5 次以上的模型调用，
   「每次调用多少钱」比真实单价小一个数量级。按请求算钱才反映真实成本，两个数字并排放才有说服力。
