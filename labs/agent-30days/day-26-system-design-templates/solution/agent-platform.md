# 模板一：Agent 平台（示范答卷）

> 一句话主线（开口第一句就说）：**无状态执行 + 有状态编排。**
> Gateway 无状态水平扩，run 的状态落 Postgres，长任务靠消息总线解耦，编排在 worker。

时间盒：澄清 5' / 估算 3' / 草图 8' / 深入 15' / 权衡 5'。

> 这份是照着 `mini-koda`（W2 里程碑）填出来的示范。**它是参照物不是答案**——你要把这里的项目细节换成你自己的，否则第一个追问就露馅。

---

## 1. 需求澄清（5 分钟）

五个通用问题，一个都不能省：

- 日活与并发会话数是多少？峰谷比大概多少？
- 单轮延迟预算是多少？首字要多快？必须流式吗？
- 成本预算是多少？按用户还是按租户结算？
- 是不是多租户？
- 失败可容忍度：一次执行失败，是重试、降级，还是必须成功？

这一题特有的三个问题：

- 单次执行大概多长？（三百毫秒别拆，三十秒必须拆）
- 工具有没有副作用？（有，则要人工确认档和参数上限）
- 需要主动推送吗？（需要，则多一个中心调度器）

**应对「你先自己假设一个」：** 给数并说依据，别推回去。原话可以是：「那我按日活 1 万、人均 5 轮、峰谷比 3 倍来算——这是一个内部工具型产品的常见量级；如果实际是十万级，我会在第五步说明哪三处要改。」关键是**这个假设后面每一步都要真的用上**，不能报完就扔。

五个答案分别把架构推向哪：

- **日活**：万级以下单进程消费就够；十万级以上必须按用户哈希分片，否则单个消费者的顺序保证会成为吞吐瓶颈。
- **延迟预算**：要求首字 1 秒内 → 必须流式，SSE 从 worker 一路回传到接入层；只要最终结果 → 直接异步返回 runId 轮询，架构少一半。
- **成本预算**：紧 → 第一天就要有按 token 的台账和模型分级路由；松 → 台账仍要有（否则出事时定位不了），但可以先不做路由。
- **多租户**：是 → 所有业务表第一列就是 `tenant_id`，闸门放数据层；否 → 别提前上，这层抽象加上去就撤不掉了。
- **失败可容忍度**：必须成功 → 消息总线要 at-least-once 加上业务侧幂等；可降级 → 预算耗尽时返回已有结果并打降级标记，不抛错。

## 2. 容量与成本估算（3 分钟）

价格口径：输入 0.15 美元 / 100 万 token，输出 0.60 美元 / 100 万 token。

单轮成本 = 输入 token ÷ 1000000 × 0.15 + 输出 token ÷ 1000000 × 0.60

**一边写一边说，别只报结果**：

- 单轮成本 = 2000 ÷ 1000000 × 0.15 + 500 ÷ 1000000 × 0.60 = 0.0003 + 0.0003 = **0.0006 美元**
- 每天轮次 = 1 万日活 × 5 轮 = **5 万轮**
- 每天模型费 = 5 万 × 0.0006 = **30 美元**；每月 ≈ **900 美元**
- 峰值 QPS：5 万轮均摊到 8 个活跃小时是 1.7 QPS，按峰谷比 3 倍取 **5 QPS**
- 峰值并发（利特尔法则）= 5 QPS × 单轮 6 秒 = **30 个并发执行**
- worker 副本数 = 30 ÷ 单 worker 并发度 8 ≈ **4 个副本**（再留一个冗余，起 5 个）

**这几个数要连成一句话说出来**：「一个月九百美元的模型费、五个 worker 副本——机器钱比模型钱还贵，所以这个规模下真正要控的不是 token，是别把架构做复杂。」这句话本身就是第五步的伏笔。

## 3. 架构草图（8 分钟）

四块，每块一句话：

- **接入层（gateway）**：只做四件事——鉴权、限流、落库、投递。收到请求立刻返回 **202 加 runId**，一个 token 都不在这里生成。**不能在这里执行**，因为它要保持无状态才能水平扩，而执行是有状态、长耗时、会被打断的。
- **执行层（worker）**：从消息总线的消费组取活，跑 Agent 循环，输出通过 SSE 逐块回传给等在接入层的连接。
- **存储**：`sessions`（会话）、`runs`（一次执行的状态机）、`messages`（逐条消息，带单调序号）、`usage_ledger`（token 台账）。幂等靠 `runs` 上 `external_id` 的**唯一约束**——最终裁判是数据库，不是应用层的先查后写。
- **可观测**：链路追踪回答「这一次为什么慢／为什么错」，成本台账回答「这个月的钱花在谁身上」。两者查的问题不同，不要合成一张表。

箭头与同步性（**面试官一定会指着某一根问**）：

```text
客户端 --同步--> gateway --同步--> Postgres（落 run，pending）
                    |
                    +--异步--> 消息总线 --异步--> worker
                                                   |
                    <--SSE 流式（异步推）-----------+
```

只有「客户端 → gateway → 落库」这一段是同步的，**其余全是异步**。把 worker 那根箭头画成同步调用，就等于把长耗时执行绑在了 HTTP 连接的生命周期上——用户一刷新页面，活就丢了。

## 4. 深入 2 到 3 个点（15 分钟）

三个「深入包」提前备好，面试官挑哪个你都有。

### 深入包 A：状态与保序

**消费组的分配单位和业务要求的串行单位对不上。** 消费组是按消息分配的，谁空闲谁拿；而业务要求「同一个用户的消息必须按顺序处理」。两个粒度不一致，同一用户的两条消息会落到两个 worker 上并发执行。

补法是**在消费之上再加一层分片租约**：`shard = hash(userId) % N`，每个 worker 用 `SET NX` 加 TTL 抢分片的租约、定时续约（比较持有者和续期必须在同一个原子步里，用 Lua 脚本）。拿不到租约的消息原样退回。这样消费组负责「谁来干」，租约负责「同一个用户只有一个人干」。

**序号必须连续不跳号**，因为它支撑的是**断线续传**：前端重连时带上「我收到第几号了」，服务端从那一号之后重放。跳号会让客户端永远等一条不存在的消息，表现是「回复卡在中间不动了」，而且日志里一切正常。

### 深入包 B：成本与限流

台账字段：`run_id`、`user_id`（多租户再加 `tenant_id`）、`model`、`prompt_tokens`、`completion_tokens`、`cost_usd`、`created_at`。

**金额要冗余存，不要查询时现算**，两个理由：一是单价会变，历史账单必须冻结在当时的价格上；二是月底出账要扫百万行，现算等于每次都做一遍除法和乘法，还得联表查价目。**存下来的是事实，算出来的是解释。**

超预算的处理**先降级再拒绝**：先切小模型、关掉可选工具、压缩上下文；只有硬顶被击穿才拒绝。理由是拒绝是用户唯一能直接感知到的一层，把它留到最后。

### 深入包 C：失败与重试

**判据是「重试有没有可能变好」**：超时、429、5xx、连接重置 → 重试（指数退避加抖动）；400 参数错、401 凭证无效 → 不重试，重试一百次也是同一个错。注意 404（模型下线）和 402（余额不足）虽然是 4xx，但**换一个 provider 有可能变好**，所以它们该走 fallback 而不是直接失败——把 4xx 一刀切成「不重试」是最常见的错。

**毒消息**（永远处理不了的那条）：消费失败计数达到上限就搬进死信流，带上最后一次的错误摘要，主流程继续。没有死信，一条坏消息会让整个消费组反复重试到天荒地老。

**持有者假死**：它醒来后不能让写入落地——所以每次写库都要带上「我持有租约的第几代」（fencing token），数据库侧比对代号，代号旧的写入直接拒绝。只靠 TTL 过期是不够的，TTL 只保证「别人能抢到」，不保证「旧的那个不会再写」。

## 5. 权衡与取舍（5 分钟）

**这个设计放弃了什么：**

- **放弃了同步返回。** 客户端必须处理「202 加 runId 加 SSE 订阅」这套两段式流程，前端复杂度实打实变高。换来的是长任务不受 HTTP 连接生命周期约束。
- **放弃了强顺序保证的全局性。** 顺序只在「同一个用户」这个粒度上成立，跨用户完全无序。换来的是可以按分片水平扩。
- **放弃了低延迟的极限。** 多一跳消息总线，首字时间比直连模型多几十毫秒。对话场景吃得下，实时语音就不行了。

**什么规模下推翻它：**

- **往下**：日活一千以内、单轮三秒内、没有主动推送——那 gateway 和 worker 就该合成一个进程，消息总线砍掉。这套架构在这个量级是纯负债。
- **往上**：日活百万级、单轮 token 涨到一万——先撞上的墙**不是 CPU，是 Postgres 的写入**：`messages` 表按每轮十几条算是每天上千万行。那时要做的是消息落对象存储、库里只留索引和状态。

**如果只能保留一个组件，保留 `runs` 状态机那张表。** 消息总线可以退化成内存队列，worker 可以和 gateway 合并，但只要「每一次执行现在处于什么状态」是持久且唯一的，系统就还能重建出其余部分；这张表一丢，重启之后没人知道哪些活干完了。
