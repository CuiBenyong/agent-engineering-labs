# 模板二：客服 Agent（示范答卷）

> 一句话主线（开口第一句就说）：**任何一通会话最后只能落到三条出口之一——自助解决、转人工、留工单。**
> 面试官想听的不是「我接了个知识库」，是「你怎么保证不把用户困在机器人里」。

时间盒：澄清 5' / 估算 3' / 草图 8' / 深入 15' / 权衡 5'。

> 照 `mini-koda` 加 `mini-multi-agent` 的电商客服域填的示范。换成你自己的业务再讲。

---

## 1. 需求澄清（5 分钟）

通用五问照模板一。这一题特有的四问与我的假设：

| 问题                 | 我的假设                           | 它改变了什么                                                          |
| -------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| 日活与并发会话数     | 日活 1 万、峰值 30 通并发          | 决定 worker 副本数（4 到 5 个），以及要不要按用户分片                 |
| 人工坐席有没有夜班   | **没有**，只有 9:00–21:00          | **出口三（留工单）必须存在**，否则夜里转人工等于把用户扔进空房间      |
| 退款谁执行           | Agent **只拟方案**，人工点头才执行 | 必须有人工确认档：模型照常发起 `apply_refund`，运行时拦下抛待确认事件 |
| 知识库多大、多久更新 | 两千条问答、每周更新               | 量小、更新慢 → **检索不是本题重点**，一句话带过，把时间留给转人工     |

最后一条尤其要说出口：**「知识库只有两千条，所以我不会在检索上花时间，重点放在转人工的判据上」**——主动声明什么不讲，比什么都讲一点更像做过的人。

---

## 2. 容量与成本估算（3 分钟）

- 单轮成本 = 2000 ÷ 1000000 × 0.15 + 500 ÷ 1000000 × 0.60 = **0.0006 美元**
- 每天轮次 = 1 万 × 5 = **5 万轮**；每天 **30 美元**，每月 ≈ **900 美元**
- 峰值并发 = 5 QPS × 6 秒 = **30**；worker 副本 = 30 ÷ 8 ≈ **4 个**（起 5 个留冗余）

**本题额外要算的那一笔**：一通会话按 5 轮算，一天 1 万通。转人工率 **15%** → 一天 **1500 通**落到人工手上。按坐席一通 8 分钟、一天有效工时 6 小时算，需要 **1500 × 8 ÷ 360 ≈ 33 名坐席**。

这一笔是本题的**杀手锏**：把转人工率从 15% 降到 10%，等于省 11 个坐席的人力——**比省九百美元的模型费重要一个数量级**。主动算出来，面试官立刻知道你分得清什么是主要矛盾。

---

## 3. 架构草图（8 分钟）

四块（接入层 / 执行层 / 存储 / 可观测）照模板一，另加本题独有的一笔：

```text
gateway --异步--> 总线 --> worker --> Agent 循环
                                        |
                              +---------+---------+
                              |         |         |
                            出口一     出口二     出口三
                          自助解决   转人工队列   留工单
                              |         |         |
                           结束会话  坐席工作台  工单系统
```

**三条出口的分叉点画在 Agent 循环的出口处**，也就是每一轮回复生成之后、返回用户之前，有一个**确定性的判定节点**（不是让模型自己决定要不要转人工——模型会为了显得有用而硬答）。

这一笔画上去，面试官立刻知道你答的是客服而不是通用平台。

---

## 4. 深入 2 到 3 个点（15 分钟）

### 4.1 转人工（本题题眼，优先讲）

**四条判据，任一命中就转，全部可以写进代码：**

1. **同一意图连续 2 轮未解决**——用「用户在下一轮又问了同一个意图」来判定，不是靠模型自我评估。
2. **用户明确要求**——命中「转人工／人工／客服／投诉」词表。这条是最简单也最不能省的一条。
3. **涉及金额超过阈值**——本次会话中任何一个待确认操作的金额大于 200 元。
4. **触发了不可逆工具**——`apply_refund` 一类被拦下来的调用，直接进人工队列。

**注意这四条里没有「识别到用户不满意」。** 情绪识别是概率性的，写不进 if；真要用就只能当**告警信号**进面板，不能当闸门。这个区分和 D22 的三条防线是同一个道理。

**交接给人工的结构化摘要，四段：**

1. 用户的诉求（一句话）
2. Agent 已经确认过的事实（订单号、金额、物流状态——**带上工具返回的原文**）
3. Agent 已经尝试过什么、为什么没解决
4. 建议的下一步（拟好的退款方案、需要人工核对的那一项）

**不能把原始对话整段丢过去**，三个理由：坐席读二十轮对话要三分钟，用户在那三分钟里会再问一遍；原始对话里混着模型的客套话，噪声比信号多；而且**原始对话里可能带着注入内容**（D22 的间接注入），直接展示给坐席等于把攻击面从模型扩大到人。

### 4.2 知识库

检索这一路一句话带过：混合检索加重排，进上下文 5 条，回答里带 `[1]` `[2]` 引用（D24）。

**检索不到（引用为空）时，系统做什么——这才是重点：** 不许让模型硬答。规则是**引用为空就不生成答案**，直接走出口二或出口三，回一句「这个问题我这边查不到准确信息，帮您转人工／登记工单」。让模型在没有依据时自由发挥，是客服 Agent 唯一会造成真实赔付的失败模式。

**引用编号防幻觉**：后处理阶段把回答里出现的编号和实际给出的 chunk 列表求交集，不存在的编号直接剔除；同时把「引用了不存在的来源」这件事**记成一个指标**（D21）——它的曲线一抬头，说明检索质量或提示词最近被改坏了。

### 4.3 多轮对话

**历史什么时候压缩**：超过 20 条或估算超过 8000 token 时触发摘要节点，**保留最近 6 条原文不动**。

**切口不能随便切**，因为一次工具调用是「模型发起 → 工具返回」成对出现的。从中间切开，上下文里就会剩一个没有结果的 `tool_call`，或者一个没有来由的工具结果——前者让模型重复调用，后者让它凭空编造。**摘要的边界必须落在完整的一轮之后。**

**用户中途改口**：判据是**当前这次执行有没有已经产生副作用**。没有（还在检索、还在生成）→ 取消当前执行、合并成一次新的；已经有了（已经发起了不可逆工具）→ 必须新建一次执行，并且明确告诉用户「刚才那笔已经在处理，我另外帮您登记这一条」。呼应 D11 的打断合并：合并的前提是可撤销。

### 4.4 出口三：留工单

**什么时候落到这条出口**：转人工判据命中，但**人工不可用**——夜间无坐席、排队超过阈值（比如 5 分钟）、或者用户主动选择「不等了」。

**工单里必须带的东西**，标准就是「第二天接手的人不用回来问用户任何一句话」：用户标识与联系方式、诉求一句话、Agent 已确认的事实（含订单号与工具返回原文）、已尝试的动作、建议下一步、**会话回放链接**（不是全文，是链接）、创建时间与承诺回复时限。少了最后一项，工单会变成一个没人认领的池子。

---

## 5. 权衡与取舍（5 分钟）

**转人工判据偏松还是偏紧：我选偏松。**

两种错法的代价不在一个量级：**误转**的代价是多占一次坐席，成本约等于八分钟人力；**漏转**的代价是用户在机器人里绕十轮之后带着火气离开，可能还带走一次差评或一次工单升级。前者是线性成本，后者是**声誉损失加二次成本**。所以宁可多转一些，然后用「转人工后坐席一句话就解决」的比例作为指标，反过来慢慢收紧判据。

**退款直接执行还是只拟方案：只拟方案。**

用「自动化率」换「不可逆错误为零」。小额（50 元以下）可以设参数级上限自动放行（D5），但那是一个**明确划定的窗口**，不是把闸门整个撤掉。这里要主动说出代价：人工点头意味着夜间的退款要等到第二天，所以出口三的工单必须带承诺时限，否则这个权衡就变成了甩锅。

**什么规模下推翻：**

- 日活到十万、转人工率仍是 15% → 需要 330 名坐席，人力模型直接破产。那时的重点会从「怎么转」变成「怎么把前三个高频意图彻底自助化」，架构上要加意图分布的离线分析和针对性的专用流程。
- 反过来，如果只有几百日活，三条出口就该简化成两条：能答就答，答不了直接留工单——转人工队列这套机制在那个量级是纯开销。
