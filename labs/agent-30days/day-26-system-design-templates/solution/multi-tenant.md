# 模板三：多租户（示范答卷）

> 一句话主线（开口第一句就说）：**数据、资源、计费三层隔离，缺哪一层就对应一类事故。**
> 只答数据隔离的人非常多，而线上真正翻车最多的是资源那一层。

> 三层各对应一类事故，开场就把这句说完：缺数据隔离 → **串号**（A 看到 B 的订单）；缺资源隔离 → **噪声邻居**（一个租户压垮所有人）；缺计费隔离 → **账单说不清**（月底对不上，谁都不认）。

---

## 1. 三层各写三到五条

### 数据隔离

**业务表怎么加租户维度**：每张业务表第一列就是 `tenant_id`，并且**进复合主键或至少进每个索引的第一位**（`(tenant_id, id)`、`(tenant_id, created_at)`）。放在索引第一位不是洁癖——它让「查某租户的数据」天然走索引前缀，同时让跨租户的全表扫在执行计划上一眼可见。

**闸门放应用层还是数据层：放数据层。** 用 Postgres 的行级安全（RLS），连接时设置 `SET LOCAL app.tenant_id`，策略里判 `tenant_id = current_setting('app.tenant_id')`。

理由和「幂等的最终裁判必须是数据库的唯一约束」完全同源：**应用层的过滤是靠自觉的**——三十个查询里漏写一个 `WHERE tenant_id = ?` 就串号了，而且那条漏网的 SQL 平时跑得很正常，只有在多租户数据交叉时才暴露。数据层的约束是**确定性**的，忘了带条件的查询直接返回空，而不是返回别人的数据。这也是 D22 那句「模型可以被说服，一个 if 不能被说服」的同一个形状：**闸门要落在最下游那个绕不过去的地方。**

**三档升级路径**：

1. **共享表 + `tenant_id` + RLS**——绝大多数场景的终点。
2. **schema 级**（每租户一个 schema，同一个库）——表结构可以按租户小幅差异化，备份粒度变细。
3. **库级 / 实例级**——物理隔离，合规和大客户专属场景。

### 资源隔离

**限流桶按什么维度分**：**至少两层**——租户级桶（防止一个租户吃掉全部配额）套用户级桶（防止一个租户内部的单个用户吃掉本租户的配额）。只做租户级，大租户内部一个写脚本的用户照样能把同租户的其他人饿死。

**worker 怎么分片**：`shard = hash(tenantId) % N`，worker 抢分片租约。

**和「按用户哈希保住顺序」是同一套机制，但目的完全不同**——这是本题最容易问到的追问。按 `userId` 哈希是为了**顺序**（同一用户的消息不能并发处理）；按 `tenantId` 哈希是为了**隔离**（一个租户的洪峰只淹自己那几个分片）。机制同源、目的不同，所以两者可以叠：先按 `tenantId` 选分片组，组内再按 `userId` 保序。

**噪声邻居在 Agent 场景里格外突出**，三个原因：

- **单次请求的资源消耗方差极大**——同样一句话，一次可能 300 毫秒直接回答，一次可能跑满 5 轮工具调用花 30 秒，相差两个数量级。传统 CRUD 的请求方差没这么大。
- **成本直接是钱**，不是 CPU 时间。一个租户的失控循环烧掉的是真金白银，而且当月就到账。
- **长连接占位**：流式回复期间连接一直挂着，并发槽位被真实占用，不像短请求那样很快归还。

### 计费隔离

**台账表加的那一列就是 `tenant_id`**（在 D13 已有的 `user_id`、`model`、token 数、`cost_usd` 之上）。

三件事分别怎么用它：

- **账单**：按 `tenant_id` 加月份聚合 `cost_usd`。金额冗余存、不现算，因为单价会变而历史账单必须冻结。
- **配额**：实时累加当日 `cost_usd`，和租户套餐里的日预算比对。
- **超支降级**：达到 80% 发预警、100% 切小模型并关可选工具、150% 硬顶拒绝。**降级要按租户生效，不能全局降级**——否则一个租户超支，所有人一起变笨。

## 2. 升级判据（最容易答成凭感觉的一段）

**判据不是租户数量。** 一万个小租户共享一张表非常正常，两个大客户反而可能各要一个库。真正的判据是这三条，命中任一才升级：

1. **合规要求物理隔离**——客户合同里写了数据不能和别人放在同一个库，这是硬约束，讨论到此为止。
2. **单租户的数据量或负载压过了共享层的调优空间**——某个租户占了全表 70% 的行，索引和统计信息被它带偏，其余租户的查询计划一起劣化。
3. **需要按租户做差异化的运维动作**——单独的备份周期、单独的版本、单独的维护窗口。共享表里这三件事做不了。

**库级隔离的代价**，重点是**运维成本是陡增不是线性增长**：

- 一次 schema 变更从「跑一条迁移」变成「跑 N 条迁移，并且要处理其中第 K 条失败、前 K-1 个租户已经迁了的中间态」——**这是从「一个操作」变成「一个分布式事务」，复杂度是跳变的**。
- 连接池从「一个池」变成「N 个池」，而每个库的最小连接数不为零，光空闲连接就能把数据库连接数吃光。
- 监控从「一条曲线」变成「N 条曲线」，告警必须重新设计成聚合视图，否则没人看得过来。
- 一个新租户从「插一行」变成「建库、跑迁移、配连接、加监控」——**开通流程必须自动化，否则销售签一单你加一次班。**

## 3. 幂等键的作用域（本题最见功力的追问）

**算法不用变，作用域必须变。**

幂等键仍然是「由业务事实算出来的确定性字符串」（比如 `order_id` 加操作类型），但**唯一约束必须是 `UNIQUE (tenant_id, idempotency_key)`，不能是 `UNIQUE (idempotency_key)`**。

**作用域不带租户标识会出现什么现象**：租户 A 和租户 B 各自有一张 `ORD-2001` 的订单（两个租户的订单号空间本来就是独立的，撞号是必然而不是意外）。A 先提交了退款，落库成功；B 随后提交，命中唯一约束，被当成重复请求**静默跳过**。

**为什么两边的日志看上去都完全正常**：A 那边是正常成功；B 那边幂等机制返回的是「这个操作已经处理过了」——这是一条**成功**的响应，不是错误。B 的日志里写着「幂等命中，跳过」，看起来是系统在正确工作。只有 B 的用户会发现钱没退，而这件事要等到客诉才浮出水面。

**这是本题最值得讲的一个坑**：它不报错、不告警、日志正常，唯一的症状是「有些操作莫名其妙没生效」，而且概率随租户数增长。呼应 D8 到 D25 幂等键的第五次出现——**同一招用了五次，第五次栽在作用域上。**

---

## 4. 权衡

**行级安全的性能代价**：每个查询多一层策略判断，等于给每条 SQL 隐式加一个 `AND tenant_id = ...`。代价主要不在那次比较，而在**执行计划**——如果 `tenant_id` 不在索引第一位，RLS 会把本来能走索引的查询打成扫描。所以第一节那条「进索引第一位」不是风格建议，是 RLS 的前提条件。另外连接复用要小心：连接归还池子时必须清掉 `app.tenant_id`（用 `SET LOCAL` 让它随事务结束自动失效），否则下一个借到这条连接的请求会带着上一个租户的身份。

**什么情况下这套设计应该被简化掉**：只有一个内部客户、或者所有租户都属于同一家公司同一个法人主体时，**数据层的 RLS 可以先不上**（保留 `tenant_id` 列，闸门放应用层），资源隔离降级成一个全局限流，计费隔离只保留台账打标不做配额。

但**三层里有一层不能省：`tenant_id` 这一列必须从第一天就加上**。加列是廉价的，事后给一张有千万行的表补上租户维度并回填历史数据，是要停机的。**能延后的是闸门，不能延后的是维度。**
