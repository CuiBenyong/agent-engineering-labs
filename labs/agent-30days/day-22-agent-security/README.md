# D22 实验：注入探针 + 工具白名单 + 参数上限 + 进程级沙箱 + 密钥脱敏

> 目标：亲手看着一个 Agent 被「说服」——指令不是用户打的，是 `query_order` 返回的
> **订单备注字段**里藏着的——然后用三条防线把它按住，并且看清这三条里**只有一条是确定性的**。
> 做完你能回答面试里最难缠的那句追问：「你怎么保证模型不会被绕过去？」
> 答案不是「我加了个正则」，而是「它绕不过去，因为执行工具的那个分支上有一道它够不着的闸」。

## 你会学到

- 用**无害口令探针**（暗号 `PWNED-CANARY`）判断防线有没有被突破，而不是拿真的攻击样本做实验
- 写出直接注入与**间接注入**两个现场，并理解为什么「只校验用户输入」的方案在后者面前全线失守
- 把工具结果包进 `<untrusted>` 并在系统提示词里声明——然后亲眼看到它**仍然会被绕过一次**
- 实现 `ToolPolicy` 权限信封：白名单、参数级上限、人工确认三道确定性闸门
- 用子进程 + 环境变量白名单 + 超时必杀做出**进程级沙箱**（沙箱三档里的第一档）
- 在日志出口统一 `redact()`，落实密钥四不入：不入代码、不入日志、不入 LLM 上下文、不入错误信息

## 目录

- `starter/`：挖了 5 个练习点的起始代码，`MOCK=1` 下可以直接跑（自检 2/8 通过）
- `solution/`：参考答案（自检 8/8 通过）

两个变体的 `src/` 结构相同，业务代码只写了一遍：

```text
src/index.ts     入口：自检编排（8 项）与常驻 HTTP 服务（端口 3022）
src/policy.ts    ToolPolicy / ParamLimit / enforceToolPolicy —— 唯一确定性的那条防线
src/guards.ts    两条概率性防线（wrapUntrusted、detectInjection）+ 日志出口 redact
src/tools.ts     五个电商客服工具 + zod 参数校验 + 三个注入探针变体
src/model.ts     唯一的网络出口。MOCK=1 下是一个**真的会上钩**的假模型
src/agent.ts     Agent 主循环：模型提议 → 过闸 → 执行 → 把结果当不可信输入回填
src/sandbox.ts   进程级沙箱：环境变量白名单 + 超时必杀
```

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace

# 验收入口：逐项打印 ✅/❌ 后按结果设置退出码
MOCK=1 SELFTEST=1 pnpm start

# 常驻模式：起一个 HTTP 服务，自己 curl 着玩（Ctrl-C 退出）
MOCK=1 pnpm start
curl -s localhost:3022/chat -H 'content-type: application/json' \
  -d '{"message":"帮我看看订单 ORD-2001 的情况"}'
curl -s 'localhost:3022/chat?scope=readonly' -H 'content-type: application/json' \
  -d '{"message":"帮我退掉订单 ORD-2001"}'
```

`MOCK=1` 下**零外部服务**：不需要数据库、不需要 Docker、不需要 API key。模型出口打了桩，
但桩**不是「一律拒绝」**——它会照着上下文里的祈使句真的改变行为，否则这个实验就白做了。
去掉 `MOCK=1` 并在 `.env` 里填 `OPENROUTER_API_KEY`，同一份业务代码会连上真模型；
此时自检会拒绝运行（真模型给不了确定性的「上钩 / 不上钩」），请用常驻模式手动体验。

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace，
> `pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. `MOCK=1 SELFTEST=1 pnpm start` 八项自检全部 ✅、退出码 0（`starter/` 原样跑是 2/8，
   第 3、4、5、6、7、8 项为 ❌，正好对应五个练习点）。
2. 第 1、2 项证明**假模型真的会上钩**：直接注入时回复里出现 `PWNED-CANARY`；
   间接注入时用户从头到尾只说了「帮我看看订单 ORD-2001」，模型却提议了 `apply_refund`——
   那句指令是 `query_order` 返回的订单备注字段带回来的。
3. 第 3 项证明**包裹是缓解不是闸门**：三个探针变体，包裹前 3/3 上钩，包裹后仍有 1/3 上钩
   （伪装成系统消息的那一种）；关键词检测只命中 2/3，客气口吻的那一种一个危险词都没有。
4. 第 4、5 项证明**权限侧是确定性的**：`apply_refund` 200 元一律转人工、30 元自动放行、
   `memory_search` 的 `topK=50` 直接拒绝；只读会话里 `apply_refund` 被白名单挡下，
   模型凭空编出来的 `run_shell` 同样被挡下。整个被说服的那一轮，实际退款 0 笔。
5. 第 6、7 项证明**沙箱与密钥**：子进程读 `OPENROUTER_API_KEY` 得到 `undefined`，
   死循环被超时杀掉；日志出口 `redact()` 之后搜不到密钥明文。
6. 第 8 项是端到端：同一条带注入的消息从 HTTP 打进来，返回体里没有暗号、
   `apply_refund` 没有执行、退款台账为空。`pnpm typecheck` 通过，没有 `any`。

## 常见坑

- **把检测当闸门。** 「加个正则过滤危险关键词」是本章最常见的错误答案。自检第 3 项就是在量它：
  客气口吻的那个探针一个危险词都不含，关键词检测直接漏掉；而伪装成系统消息的那一种连包裹
  都骗得过去。检测只能当告警信号，能拦住动作的只有 `enforceToolPolicy` 那一句。
- **只校验用户输入。** 间接注入那条指令不是用户打的，是**你自己的工具**返回的。
  凡是工具返回结果与检索到的文档，一律当不可信输入——这是本章唯一需要背下来的结论。
- **包裹标签自己被注入。** `wrapUntrusted` 如果不先把内容里自带的闭合标签剥掉，
  攻击者写一个闭合标签就能让后半段跑到包裹之外，包裹方案自己成了注入点。
- **判定顺序写反。** 白名单必须在参数检查之前判。反过来的话，一个模型凭空编出来的工具名
  会因为在 `paramLimits` 里查不到而被一路放行——自检第 5 项里的 `run_shell` 就是在测这个。
- **参数缺失当成放行。** `call.args[limit.field]` 取到 `undefined` 时如果直接跳过上限检查，
  攻击者只要不传那个字段就绕过了整道闸。默认拒绝，不是默认放行。
- **沙箱把 `process.env` 整个递给子进程。** 这是「看起来隔离了、其实没有」的典型：
  进程是独立了，密钥却跟着过去了。子进程的环境必须是白名单拷出来的新对象。
- **只在日志里脱敏，忘了错误信息。** 异常堆栈里经常夹着带密钥的 URL，
  未捕获异常打印出来就是一次泄漏。`redact()` 要放在**所有**对外出口上，包括 `catch` 的那一支。
