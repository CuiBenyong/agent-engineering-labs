# D20 实验：proactive job + 通知抽象

> 目标：写一个会主动给用户发消息的 Job，并给它装上三道闸——按用户时区算本地时间、
> 命中安静时段就推迟到窗口结束、同一个用户当天超过 3 条就拦下——而且这三道闸全部在
> 生成内容**之前**判断，被拦下的消息一次模型调用的钱都不花。通知渠道走 provider 抽象，
> 换渠道时业务代码一行不改。做完你就能回答「为什么半夜给欧洲用户发了推送」和
> 「这条消息凭什么现在发」这两个真实会被追问的问题。

## 你会学到

- 实现一个按用户时区计算"现在是否适合发送"的函数，并处理夏令时的两种反常
- 实现 quiet hours 配置与判断逻辑，重点是跨午夜区间怎么写才不会恒为 false
- 实现每日发送上限计数器（按用户维度，且按用户本地日历日切天）
- 定义一个通知 provider 接口，实现两个具体渠道，并写清重试与幂等语义
- 跑一次定时 Job，验证时区、安静时段、上限三条规则都在投递前生效

## 目录

- `starter/`：挖了 5 个练习点的起始代码，`MOCK=1` 下可以直接跑
- `solution/`：参考答案
- `docker-compose.yml`：本 lab 自己的 Redis 与 Postgres，只有跑真实版才需要

两个变体的 `src/` 结构相同，业务代码只写了一遍：

```text
src/index.ts        入口：自检 / 常驻两种模式，以及三个用户三个时区的档案表
src/clock.ts        可注入时钟：自检要在一毫秒内跨过午夜与夏令时，不能读系统时间
src/gates.ts        三道闸：UTC 转本地、跨午夜的安静时段、按本地日历日的每日上限
src/notify.ts       NotificationProvider 接口 + 站内信 / 短信两个渠道 + 重试语义
src/job.ts          Job 主流程：过闸 → 生成正文（唯一网络出口）→ 投递 → 落流水
src/infra/index.ts  Store 接口 + 内存实现 + 唯一的选择点
src/infra/real.ts   ioredis（计数器 + 延后队列）+ pg（发送流水）的真实实现
```

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace

# 验收入口：用快进时钟跑完三个时区、一次跨午夜、一次跨本地日历日，逐项打印 ✅/❌ 后退出
MOCK=1 SELFTEST=1 pnpm start

# 常驻模式：每分钟跑一轮，给三个用户各排一条候选（Ctrl-C 退出）
MOCK=1 pnpm start
MOCK=1 NOTIFY_CHANNEL=sms pnpm start   # 换个渠道，业务代码一行不改
```

`MOCK=1` 下**零外部服务**：不需要 Redis、不需要 Postgres、不需要 Docker、不需要 API key。
计数器、延后队列、发送流水走的是 `src/infra/index.ts` 里的内存实现（不是打桩——
原子自增占坑、按到期时间取出、幂等键去重都真的实现了一遍），时钟是可注入的假时钟，
所以自检能在一毫秒内跨过用户本地的午夜，你不用真等到第二天。

想跑真实版：

```bash
docker compose up -d   # 在本 lab 根目录，起 redis:7-alpine 与 pgvector/pgvector:pg16
cd solution
REDIS_URL=redis://127.0.0.1:6520 \
DATABASE_URL=postgres://koda:koda@127.0.0.1:5520/koda \
MOCK=1 SELFTEST=1 pnpm start          # 同一份业务代码，基础设施那一行会打印 real
docker compose down -v                # 收工（也是重跑前的必做动作，见常见坑）
```

去掉 `MOCK=1` 并在 `.env` 里填 `OPENROUTER_API_KEY`，正文就由真模型来写；此时被三道闸
拦下的每一条，省下的都是真金白银。

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. `MOCK=1 SELFTEST=1 pnpm start` 六项自检全部 ✅，退出码为 0（`starter/` 原样跑只有第 6 项 ✅）。
2. 第 1、2 项证明时区与跨午夜判断正确：同一个 UTC 瞬时 `2026-09-05T23:30Z` 在上海是次日 07:30（安静）、
   在纽约是 19:30（可发）、在伦敦是次日 00:30（安静）；`22:00–08:00` 这个区间对 22:00 / 00:00 / 07:59
   都判"静"，对 21:59 / 08:00 判"可发"。夏令时那两天分别判成 gap 与 ambiguous。
3. 第 3 项证明安静时段内是**推迟不是丢弃**：上海用户本地 23:30 的那条被推到次日 08:00
   （UTC `2026-09-06T00:00:00Z`）并在那一刻真的发出；只有在窗口结束前就过期的那条才被丢弃。
4. 第 4 项证明每日上限按**用户本地日历日**：纽约用户当天连排 5 条，前 3 条发出、第 4 条起被拦；
   跨过纽约本地午夜之后额度重置，又能发 1 条。
5. 第 5、6 项证明成本与渠道：9 条候选只发出 5 条，模型调用恰好 5 次、白花 $0.000000
   （闸若放在生成之后要白花 $0.003000）；短信渠道限流后重试 1 次成功，收件箱里仍然只有 1 条。

## 常见坑

- **服务器在 UTC，就以为全世界都在 UTC。** 不带时区地读 `getUTCHours()` 判断"现在是不是半夜"，
  代码不报错、测试也能过，只是给欧洲用户在凌晨三点推了消息。时区必须存 IANA 标识
  （`Asia/Shanghai`）而不是 `+08:00` 偏移量——偏移量会随夏令时变，存下来的那一刻它就过期了。
- **跨午夜的安静时段写成了"且"。** `start <= now && now < end` 对 13:00–14:00 是对的，
  对 22:00–08:00 恒为 false。start 大于 end 时条件要改成"或"：`now >= start || now < end`。
  这个坑的可怕之处在于它**只在跨午夜的配置上错**，而绝大多数测试数据都不跨午夜。
- **命中安静时段就把消息丢了。** 丢弃和推迟是两个产品决定：只有"过期即作废"的消息该丢
  （比如"这单 30 分钟后自动取消"），其余的都该推迟到窗口结束。判据是消息自己带的 `expiresAt`，
  不是发送方当时的心情。
- **每日计数按 UTC 日切天。** 键写成 `notify:count:<userId>:<UTC 日期>`，东八区用户在本地
  08:00 之前发的消息会算进前一天的额度，于是他早上收到的那条被"昨天"的额度挡住。
  计数的"天"必须是**用户本地日历日**。
- **闸放在了生成之后。** 顺序错了程序照样跑、发出去的消息也一模一样，唯一的区别是每条被拦下的
  消息你都已经付过一次模型调用的钱。自检第 5 项就是在量这笔钱。
- **真实版重跑前要 `docker compose down -v`。** Redis 里的每日计数器和 Postgres 里的发送流水
  是持久的，第二次跑同一份自检时额度早被上一次用光了，第 4 项会以"一条都没发出"的形式变红——
  这不是代码坏了，是状态没清。
