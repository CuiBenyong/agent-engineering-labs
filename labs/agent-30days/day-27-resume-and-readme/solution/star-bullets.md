# STAR 简历要点（示范样例）

> 一句话公式：**在（约束）下，为了（目标），我（具体技术动作），把（指标）从 X 改善到 Y。**
>
> **下面每一个数字都是本仓库的实验真跑出来的**，命令写在每条的「数字来源」里，你可以复现。
> 这份是参照物不是答案——你的项目细节和我的不一样，照搬会在第一个追问就露馅。

## 1. agent-service（W1，D7）

**一句话定位**：把单个 Agent 封装成带流式输出和优雅停机的 HTTP 服务，一个容器起得来。

**数字来源**：

```bash
cd labs/agent-30days/day-07-agent-service-docker/solution
PORT=3907 MOCK=1 SELFTEST=1 pnpm start
```

自检第 3、4 项的原始输出：

```text
[3/4] POST /chat → 200，Content-Type: text/event-stream; charset=utf-8 ✅
      收到 103 个 delta 事件、1 个 done 事件
[断开] 客户端已离开，生成 6 个片段后停止
[4/4] 客户端读到 5 个片段就断开：服务端一共生成了 6 个片段 ✅ 断开后停止生成
```

**最终这一条：**

> 在「用户随时会关掉页面、而每个 token 都在计费」的约束下，为了让服务端不为已经离开的客户端白烧钱，我在 SSE 推流循环里接上了请求的中止信号并在每次 `yield` 前检查，把一次被中途放弃的会话的服务端生成量从 **103 个片段**（全量生成完才发现没人接）降到 **6 个片段**（客户端读了 5 个就断开，服务端只多生成 1 个即停）。_测量条件：本地单进程、`MOCK=1 SELFTEST=1`、单条约 103 字的模拟回复。_

**自检**：

- [x] X 和 Y 出自哪一项自检说得出来：X 是第 3 项的 103 个 delta（完整回复的总量），Y 是第 4 项的 6
- [x] 测量条件写了：本地单进程、MOCK 模式、约 103 字的回复
- [x] 「具体技术动作」写的是接中止信号、在 `yield` 前检查，不是「优化了性能」

**可预期的追问与我的答案**：

- _「103 和 6 不是一个量纲吧？」_——同一个量纲，都是服务端实际生成的片段数；差别在于客户端在第 5 个片段就走了。这一条要主动说清楚，不要等他问。
- _「怎么知道真的停了而不是只是不发了？」_——自检里打的那行 `[断开] 客户端已离开，生成 6 个片段后停止` 是在生成器内部打的，不是在 HTTP 层。

## 2. mini-koda（W2，D8–D14）

**一句话定位**：Gateway 与 worker 池分离的 Agent 执行平台，用消息总线解耦，保证同一用户的消息严格保序。

**数字来源**：

```bash
cd labs/agent-30days/day-10-sharding-lease/solution
MOCK=1 SELFTEST=1 pnpm start
```

自检第 1、4、5 项的原始输出：

```text
[1/5] shardOf 稳定且分布均匀：同一 userId 五次都落在 shard 34；2000 个用户占 256/256 个 shard，最大桶 19 条（理想 8） ✅
[t+0.66s] 模拟 kill -9：worker-A 停续约、不 release，内存里仍记着持有 68
[t+3.42s] shard 68 在失联 2.75s 后被 worker-B 接手（TTL 3000ms）
[4/5] handoff 之后同用户顺序没乱：u-1000 的处理顺序 [1, 2, 3, 4, 5, 6]，后三条由 worker-B 处理 ✅
[5/5] 脑裂防护（续约校验持有者 + 写入带 fencing token）：worker-A 拿旧号 225 续约被拒、写入被拒 ✅
```

**最终这一条：**

> 在「worker 会被随时 kill、而同一用户的消息不能乱序」的约束下，为了让副本挂掉时不丢消息也不乱序，我给分片加了 `SET NX` + TTL 的租约、把「校验持有者 + 续期」合成一个原子步、并给每次写入带上 fencing token，使得持有者假死后 **2.75 秒**由另一副本接手，接手前后同一用户的消息序号仍是连续的 `[1,2,3,4,5,6]`，且旧持有者用过期代号 225 的续约与写入**双双被拒**。_测量条件：本地单进程内起 2 个 worker、内存版基础设施、2000 个模拟用户散在 256 个分片上（最大桶 19 条，理想 8）；自检把生产口径的 TTL 30s / 续约 10s 等比压缩 10 倍成 3s / 1s。_

**自检**：

- [x] 有前后对照：`[1,2,3,4,5,6]` 是 handoff **之后**仍然有序，对照的是「没有租约时同一用户会被两个 worker 并发处理」
- [x] 规模参数写在测量条件里：2 个 worker、2000 用户、256 分片、TTL 压缩倍数
- [x] 和另外两条不重复：这一条讲分布式与状态，D7 那条讲协议与流式

**可预期的追问与我的答案**：

- _「2.75 秒是怎么来的？」_——TTL 是 3 秒，失联到被抢走的实际耗时 2.75 秒，因为抢占方是轮询检测的。生产口径 TTL 是 30 秒，对应的接手时间也是这个量级。
- _「fencing token 和 TTL 过期不是一回事吗？」_——不是。TTL 只保证「别人抢得到」，fencing token 保证「旧的那个醒来之后写不进去」。少了后者就是脑裂。

## 3. mini-multi-agent（W3，D15–D21）

**一句话定位**：Planner–Executor–Critic 三角色的多 Agent 编排服务，带共享工作区、工具预算与评审回路。

**数字来源**：

```bash
cd labs/agent-30days/day-17-planner-executor-critic/solution
MOCK=1 SELFTEST=1 pnpm start
```

自检第 1、2 项的原始输出（同一张图，只换 reducer）：

```text
[1/5] concat reducer 下的重复写入：3 件子任务写出 6 条记录，重复 id t-1-order t-2-shipping t-3-address；按 id 查第一条拿到的是过期的 pending 版本 ✅
[2/5] 按 id 原地更新的 reducer：工作区 3 条、重复 id 0 个，按 id 查拿到的是 done 版本 ✅
```

**最终这一条：**

> 在「多个执行者并行写同一份图状态」的约束下，为了让共享工作区不出现同一子任务的多个版本，我把 `workspace` 通道的 reducer 从数组追加换成按 id 原地更新，把 3 件子任务并行执行后留下的记录数从 **6 条（3 个重复 id，按 id 查到的是过期的 pending 版本）** 收敛到 **3 条（0 个重复，查到的是 done 版本）**。_测量条件：本地单进程、`MOCK=1`、同一张图只替换 reducer 做对照，3 件并行子任务。_

**自检**：

- [x] 能引出至少两个我答得上来的追问（见下）
- [x] 没有出现任何我没跑过的规模数字

**可预期的追问与我的答案**：

- _「为什么默认的追加 reducer 不行？」_——累加通道做不了减法。执行者返回的是「这件子任务的最新状态」，追加语义会把它接在旧版本后面，于是同一个 id 有两条记录；后面任何按 id 取第一条的代码拿到的都是过期版本，**而且不报错**。
- _「那为什么不干脆让执行者写全量数组？」_——并行写全量就是互相覆盖，最后一个写入的赢，另外两件子任务的结果直接消失。reducer 存在的意义就是把「怎么合并」从调用方手里拿走。

## 收尾：三条一起看

**（1）它们讲的是三种不同的能力吗？** 是：

| 条目             | 能力面                   | 面试官会往哪追                |
| ---------------- | ------------------------ | ----------------------------- |
| agent-service    | 协议与流式、资源生命周期 | SSE、中止信号、计费           |
| mini-koda        | 分布式与状态、故障恢复   | 租约、脑裂、保序、幂等        |
| mini-multi-agent | 编排与共享状态           | reducer、预算、评审回路、降级 |

三条各占一面，没有一条在讲「我会用 Docker」。

**（2）删掉所有形容词之后还读得通吗？** 读得通——三条里几乎没有形容词，撑住句子的是动词（接上中止信号、合成原子步、换 reducer）和数字（103→6、2.75 秒、6→3）。这是自检里最好用的一条：**形容词是数字缺席时的填充物。**
