# 先思考再回答模板（先想再说）· 示范

> 用法：任务复杂、错误代价高、或需要人审计推理过程时用。批量简单任务不要用——分析段是输出 token，按输出价计费。
> 核心是给「想」和「答」各留一个标签，程序只取答案段。

## 模板

```text
（一句话交代任务）

先在 <analysis> 标签里：
- 维度一
- 维度二
- 维度三

然后在 <answer> 标签里只放（代码 / 结论），不要重复分析。
```

## 程序怎么用

程序只解析 `<answer>` 与 `</answer>` 之间的内容；`<analysis>` 段展示给审阅者，并随任务记录存档，不进入后续流程。

## 什么时候不用

1. **批量打标 / 分类。** 一千条评论各判一个情绪标签，分析段的输出 token 是结论的十几倍，成本直接翻一个量级，而且没人会看一千段分析。直接用结构化输出。
2. **交互式补全。** 编辑器里的行内补全要求几百毫秒返回，分析段会把首字延迟拉到几秒。要么不写分析段，要么依赖模型内部的 thinking 并把 effort 调低。

## 示例（示例任务：给 TODO API 补输入校验和单元测试）

```text
下面是 POST /todos 的现有实现，请给它补上输入校验。

<current_code>
router.post('/todos', (req, res) => {
  const todo = { id: nanoid(), done: false, ...req.body }
  store.push(todo)
  res.status(201).json(todo)
})
</current_code>

先在 <analysis> 标签里逐条分析：
- 请求体里哪些字段目前完全没有校验
- 每一个缺口在生产里会导致什么具体问题（举一个恶意或误操作的输入）
- 你打算用什么 zod 规则拦住它，以及为什么选这条规则而不是更宽或更严的

然后在 <answer> 标签里只给修改后的完整函数（含 zod schema 定义），不要重复分析、不要解释。
```

预期输出会分成两段：分析段大约十几行，逐条对应三个维度；答案段只有一个代码块。代码审查时把分析段贴在 PR 描述里，CI 里的自动化只取答案段落盘。
