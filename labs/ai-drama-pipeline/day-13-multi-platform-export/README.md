# D13 实验：多平台导出矩阵与封面标题候选生成挑选环节

> 目标：把一集成片一次渲染出来，再按三个目标平台各封装一版，全程只重编码必要的那几次；顺手把标题与封面文案做成「批量出候选 + 打分挑前三」，最后把发布后的播放数据映射回流水线上的具体环节。做完你会拿到一份能直接照着上传的发布物料清单。

## 你会学到

- 定义三个目标平台的规格表，按表批量导出成片与封面
- 让模型批量生成标题与封面文案候选，再用打分函数挑出前三
- 实现一次渲染多次封装，用日志证明重编码次数被压到最少
- 设计并实现数据回收的数据结构，把播放数据映射回具体环节
- 跑完导出流程并输出一份发布清单，逐项可勾选

## 目录

- `starter/`：挖了 5 个练习的起始代码，`MOCK=1` 下可以直接跑
- `solution/`：参考答案
- `src/providers/`、`src/ffmpeg.ts`、`src/run.ts`、`src/dag.ts`：**来自 D1，本天不改**（每个 lab 独立，不跨 lab import）
- `src/probe.ts`：ffprobe 的最小封装，只取封装决策要用的那几个字段
- `src/platforms.ts`：平台规格表与封装决策（流复制还是重编码）
- `src/titles.ts`：候选生成、打分、封面文案的兜底
- `src/feedback.ts`：播放数据的数据结构与「掉幅 → 环节」映射

## 怎么跑

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 MINIMAX_API_KEY；没有 key 先用 MOCK=1
MOCK=1 pnpm start     # 离线模拟，五步一次跑完
WORK_DIR=~/drama-out pnpm start            # 真实厂商（产物写仓库外：花过钱的素材别放临时目录）
```

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

### 规格表里最重要的一列是「这条数字从哪来的」

`src/platforms.ts` 的每个平台都有一个 `sourceOfTruth`：

| 值                   | 含义                                                 |
| -------------------- | ---------------------------------------------------- |
| `official-doc`       | 平台官方开发者文档白纸黑字写着的，代码可以拿来做判定 |
| `check-your-console` | 官方文档站上查不到，必须去你自己账号后台的规格页确认 |

本实验里只有 TikTok 是 `official-doc`（出处是它的 Content Posting API 媒体传输指南）。
**抖音与快手的时长 / 分辨率 / 码率 / 封面尺寸一律留空**，代码在遇到这类平台时按母版原样流复制，
并往发布清单里塞一条「上传前去后台核对」。编一个看起来很专业的数字，比留空危险得多——
它会让你在上传失败时怀疑代码，而不是怀疑那个数字。

## 验收标准

1. `MOCK=1 pnpm start` 跑完五步，日志里出现「重编码 0 次；流复制封装 4 次」——三个平台的成片全部走流复制
2. 封面那一步打印「取帧 1 次，复制 3 份，缩放 0 次」
3. 五条标题候选各自打印分数与逐项依据，前三名按分数排出来（同分按 id 定序，两次运行结果完全一致）
4. 封面文案那一行显示「模型返回不可用，回落本地模板」——离线模式下模型回的是占位文本，被兜底挡住了，没有印上封面
5. 两个平台的播放数据诊断结论不同：完播率高的那个只有一条「保持」，低的那个能定位到具体镜头 id 与剧本环节
6. 发布清单里带着抖音与快手的「去后台核对规格」两条，以及一条指向 D11 的生成内容标识检查

## 常见坑

1. **换容器就以为要重编码。** 换封装（mp4 到 mov）和换编码是两件事，`-c copy` 就能换容器；超时长也一样，`-t` 配 `-c copy` 直接切，不需要重新压一遍。
2. **concat 列表里写相对路径。** concat 解复用器把列表里的路径按**列表文件所在目录**解析，不是按当前工作目录。一律写绝对路径，能省掉一整类玄学报错。
3. **让模型一次给出最终标题。** 那等于把质量下限交给运气。正确形态是「按不同角度各出一版 + 一个确定性的打分函数收敛」，下限由打分函数兜住。
4. **打分函数同分时不给决胜键。** 同分候选的相对顺序取决于排序实现，两次运行可能挑出不同的前三，你会以为模型不稳定。加一条按 id 的决胜键就好了。
5. **回收的数据只做成报表。** 「留存曲线」本身不可执行。每条结论都要落到一个 stage 上——落不到环节的指标，看了也改不了。
