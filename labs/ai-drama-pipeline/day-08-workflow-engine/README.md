# D8 实验：支持断点续跑与成本台账的最小工作流引擎

> 目标：把 D7 那条「一步失败就从头再来」的顺序脚本，换成一个有节点状态、有产物缓存、
> 能从断点接着跑的引擎。验收只看一个数字：第二次运行的付费接口调用次数是不是 0。

## 你会学到

- 定义节点与依赖的数据结构，实现按拓扑序调度并记录节点状态
- 把第一周的六个环节改写成节点，产物按内容寻址落盘
- 让引擎在重跑时跳过已完成节点，用日志证明没有重复调用付费接口
- 在第四个节点注入失败，续跑时确认只从该节点往后执行
- 输出一份按节点分列的成本与耗时台账

## 目录

- `starter/`：挖了 4 个练习的起始代码，`MOCK=1` 下可以直接跑（但它既不缓存也不续跑）
- `solution/`：参考答案
- `src/providers/`、`src/ffmpeg.ts`、`src/run.ts` **来自 D1，本天不改**
- `src/episode.ts`、`src/timeline.ts`、`src/compose.ts` **来自 D6，本天不改**
- 本天的主要工作在两个文件：
  - `src/dag.ts`：**来自 D1，本天把它从「按图跑一遍」扩成正式引擎**——指纹、状态持久化、缓存命中、断点续跑
  - `src/nodes.ts`：第一周六个环节改写成的六个节点

产物分两层，这是这一天的核心布局：

```
work/
├── cache/<nodeId>/<fingerprint>/     产物，按内容寻址；同样的输入永远写到同一个目录
└── runs/<runId>/
    ├── state.json                    这次运行里每个节点的状态、耗时、花费、指纹
    ├── run.json                       成本台账
    └── output/                        从 compose 的缓存目录取出来的成片、字幕、封面
```

缓存是全局的，状态是每次运行一份。**幂等来自缓存，断点续跑来自状态。**

## 怎么跑

需要本机装好 ffmpeg（含 `ffprobe`）：

```bash
brew install ffmpeg                      # macOS
sudo apt-get install -y ffmpeg           # Debian / Ubuntu
```

```bash
cd starter            # 或 solution
pnpm install --ignore-workspace
cp .env.example .env  # 填 MINIMAX_API_KEY；没有 key 就一直用 MOCK=1

MOCK=1 pnpm start                              # 第一次：六个节点全执行
MOCK=1 pnpm start                              # 第二次：六个节点全命中缓存，付费调用 0 次
INJECT=failnode:clips MOCK=1 pnpm start        # 在指定节点注入失败（这里是第四个节点 clips）
MOCK=1 pnpm start                              # 续跑：前三个节点跳过，从 clips 往后补
IDEA="废柴保安捡到一把能开任何门的钥匙" RUN_ID=run-demo-002 MOCK=1 pnpm start   # 换一句话，全部连锁失效
```

> 说明：`starter/` 与 `solution/` 都不属于仓库根 pnpm workspace（根 `pnpm-workspace.yaml` 只包含
> `apps/*`），`pnpm install` 时要加 `--ignore-workspace`。

## 验收标准

1. 第一次 `MOCK=1 pnpm start` 六个节点全部「执行」，末尾打印「本次付费接口调用 15 次」。
2. 紧接着再跑同一条命令，六个节点全部「命中缓存」，耗时 0ms、折算花费 ¥0.0000、**付费接口调用 0 次**。
3. `INJECT=failnode:clips MOCK=1 pnpm start`（先清掉 `work/`）之后：`clips` 记为 ❌ 且台账里它有 ¥3.0000 的花费，`voice` 与 `compose` 记为 ⏸ 未跑，进程非 0 退出。
4. 去掉 `INJECT` 再跑同一条命令：`script / assets / frames` 命中缓存（0 次调用），`clips / voice / compose` 执行，成片落到 `work/runs/<runId>/output/`。
5. 换一句话并换一个 `RUN_ID` 再跑：六个节点的指纹全部与之前不同，全部重新执行——说明依赖指纹的连锁失效是生效的。

## 常见坑

- **幂等键里漏了依赖的指纹，是最常见也最难查的错。** 只哈希自己的输入，上游换了剧本你还在用旧的镜头文件，程序不报错，成片就是不对。四个成分一个都不能少：节点 id、实现版本、自己的输入、全部依赖的指纹。
- **反过来，键里放了不该放的东西，缓存就永远不命中。** `runId`、时间戳、随机数、绝对路径，放进去等于每次都是新键，你会以为缓存写坏了，其实是键设计错了。
- **判断「做没做完」要看磁盘上的产物，不要只看状态文件。** 文件可能被手删，状态可能来自另一次运行。本实验的判据是「这个指纹目录下 outputs 里的每个文件都在」。
- **失败节点的残产物不要删。** 留着它，下一次跑到这里「文件齐不齐」一看便知；删了反而丢掉了信息。但也别把残产物当成功的，`outputs` 必须**全部**存在才算命中。
- **改了实现要记得把 `version` 加一。** 否则你拿着新代码读到旧产物，这种 bug 能查一整天。
- **本实验的幂等粒度是节点，不是镜头。** `clips` 里第三镜失败，续跑时四镜会一起重做——前两镜的钱白花了。把粒度拆到「一镜一个节点」当然更省，代价是任务图会大很多、调度也更复杂。并行粒度与失败半径的取舍在 D9 展开。
- **依赖指纹会带来过度失效。** 换一句话之后 `assets` 其实读到的还是同一份人物卡，却因为上游指纹变了而重新生成。更省的做法是对依赖的**产物内容**做哈希，而不是对依赖的键做哈希；代价是每次都要把产物读一遍。小图省，大视频不省——这条取舍值得你自己在项目里量一次再定。
